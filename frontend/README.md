# Caravansara web site

The guest and host parts of the site (specs/005-frontend-guest, specs/008-host-pages). Guests can search by city
or on the map, open a listing, sign up and log in, upload a profile picture, book and pay (payment is simulated),
see their trips, cancel, and review. Hosts make a listing in eight steps with at least three photos, then keep it:
status and rejection reason, edits with a warning when an approved listing goes back to review, photos (order,
cover, labels), off and on, bookings and reviews. The site is in Persian, right-to-left with Vazirmatn, at `/fa`
(the default), and in English at `/en`. The admin panel (feature 009) is in the same app but answers only on the admin host (`ADMIN_HOST`, `admin.localhost:3001` in compose): the review queue, each listing with its exact address, approve, and reject with a reason.

Why each piece is built the way it is: [`docs/backend-design.md`](../docs/backend-design.md), section «فرانت‌اند وب».

## Run

```bash
# whole system, with the site at http://localhost:3001 (Grafana has 3000)
docker compose up --build

# or only the site, on an API that is already running
cp .env.example .env.local
npm ci
npm run dev            # http://localhost:3001
```

Node 24 (`.nvmrc`). Package versions are exact and at least two weeks old; `package-lock.json` is committed.

## Checks (the same as CI)

```bash
npm run gen:api && git diff --exit-code src/api/schema.d.ts   # the client matches backend/openapi.json
npm run lint && npm run format:check
npm run typecheck
npm run test -- --coverage   # Vitest; 90% gate for src/lib and src/api
npm run build
```

Messages live in `messages/fa.json` and `messages/en.json`, both generated by `python3 scripts/messages_source.py`.
Every key there has both languages, so the two files can never disagree. Edit the script, never the JSON files.

## Layout

```
src/
  app/
    [locale]/          pages: home, search, listings/[id], login, register, account, book/[listingId],
                       trips, trips/[bookingId], trips/[bookingId]/review,
                       host (my listings), host/new?step=1..8, host/listings/[id]?tab=details|photos|bookings|reviews,
                       admin, admin/login, admin/listings/[id] (admin host only)
    admin-api/         admin log-in/out (token in the HttpOnly cv_admin cookie) and the forwarder to /api/v1/admin/*
    api/v1/[...path]/  forwards /api/v1 to the API (one origin, no CORS)
    session/           login, register, refresh, logout: the refresh token in the HttpOnly cv_refresh cookie
  proxy.ts             language prefix, the CSP with a fresh nonce, and 404 for /api/v1/auth/*
  api/                 typed clients: browser (token, refresh on 401) and server (no token, no cache)
  lib/                 the rules, each with its tests: session and the cross-tab lock, Jalali calendar, city time,
                       money (rial as toman), search state, booking draft and booking rules, avatar, errors,
                       listing draft and form rules, image check, photo upload, review fields, listing status
  components/          ui (shadcn style on Radix), brand (logo, hero, arch frame), home (categories, city rows),
                       search, date, listing, booking, account, auth, layout, host (wizard, steps, photos, editor)
  i18n/                next-intl routing and messages
```

## Rules worth knowing

- **Colours:** only in `src/app/globals.css`, as tokens (the caravansara theme, `specs/007-caravansara-theme`).
  `src/no-raw-colors.test.ts` refuses a colour anywhere else, and `src/theme.test.ts` checks every text and
  background pair against WCAG AA. Buttons and links use the darker copper `#9a5418`, because white on the
  diagrams' copper is below AA.
- **UI elements (feature 026):** every control comes from shadcn/ui in `src/components/ui/`: Button, Input,
  Textarea, Select, DropdownMenu, Tabs, RadioGroup, Checkbox, Dialog, Popover, Command (the city box, on `cmdk`)
  and ScrollArea (the sideways rows). They are written in shadcn's style on `radix-ui` with this site's tokens,
  so a new one should be copied from the shadcn docs and its colours changed to the tokens, not added with
  `npx shadcn add` as is (that brings shadcn's own colour names, which `no-raw-colors.test.ts` and the theme
  do not have). `components.json` tells the CLI where things live. `Providers` sets Radix's `DirectionProvider`
  from the page's language, so menus, selects and tabs open and move with the arrow keys in right-to-left order.
  The Jalali calendars (`DateRangePicker`, `AvailabilityCalendar`) keep their own day buttons: shadcn's Calendar
  is `react-day-picker`, and changing to it is a separate decision. Native scroll bars (page, dialogs, lists)
  are thin and sand-coloured from `globals.css`; the page itself is not in a ScrollArea, so the sticky header
  and the browser's own scrolling stay.
- **The arch:** the class `arch` (the tall doorway) is a CSS mask, for decoration only. Listing photos are plain
  rounded rectangles since feature 017; `ArchFrame` puts a photo, or a warm placeholder, in one. A page that marks
  itself `data-wide` (the home page) gets up to 1920 px; the others stay at 1280 px.

- **Tokens:** a token is never kept where page scripts can read it after a reload. The access token is only in
  memory. The refresh token is only in the `cv_refresh` cookie, which page scripts cannot read. ESLint refuses
  `localStorage`.
- **Refreshing:** runs under the browser lock `cv-refresh`, one tab at a time. The API ends every session when a
  refresh token is used twice, so two tabs refreshing at once would log the user out everywhere.
- **Pages without a token:** search and listing pages render on the server without a token; account, booking,
  trips and review pages render in the browser.
- **Profile picture:** checked in the browser first (size, type, first bytes), then sent in one `PUT /me/avatar`
  with the file as the body; the API checks it again before storing anything (`specs/006-avatar-upload-via-api`).
  The `/api/v1` proxy streams bodies to the API and refuses one over 5 MB + 64 KB with the API's own 413.
- **Admin panel:** `proxy.ts` serves `/{locale}/admin…` and `/admin-api/…` only when the Host is `ADMIN_HOST`, and
  nothing else there; unset, there is no panel. The admin token never reaches page scripts. Every decision is
  sent with the `review_version` seen, so a host's change in the meantime gets 409 and the new version is shown.
- **Host pages:** a listing is created only at the last step, then its photos upload two at a time and are put
  in order; the draft (answers only, not files) is in `sessionStorage` as `cv-listing-draft`. At least three
  photos is a rule of the site only (`MIN_PHOTOS`). Rial prices are typed in toman and sent ×10. The fields that
  send an approved listing back to review are listed once in `lib/reviewFields.ts`.
- **Errors:** every API error code has a message in both languages. A test reads the codes from the backend
  source.
- **Time:** dates that decide cancelling and reviewing are counted in the listing city's time zone, as the API
  counts them.

## Boutique home design

The home page uses an atmospheric Persian courtyard cover, an overlapping search bar, olive actions and
ivory surfaces. The decorative cover (`src/assets/hero-boutique.jpg`) is AI-generated, not a photo of a
bookable property. The original courtyard asset and animated travel scene remain in the project; the scene
now sits below the city rows. Collection links use existing property-type and pets filters. Both Persian
and English are supported. `e2e/tests/boutique-home.spec.ts` checks responsive widths, accessibility, mobile
search and category navigation. Set `BOUTIQUE_WEB` to test an alternate local preview port.
