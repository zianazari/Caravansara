# Measurements: فرانت‌اند وب، بخش ۱ (SC-003)

اندازه‌گیری در 2026-11-08، روی stack محلی (`docker compose`، Mac، Docker Desktop)، با image ساخته‌شده‌ی سایت (`next start`، حالت production).

## روش

- **ابزار:** Lighthouse نصب نبود، و `npx lighthouse` کد را از بیرون دانلود می‌کرد. پس همان سنجه‌ها با خود Google Chrome و Playwright اندازه گرفته شدند.
- **شرایط:** مانند پیش‌تنظیم موبایل Lighthouse:
  - صفحه‌ی ۴۱۲×۸۲۳ با `deviceScaleFactor: 2`.
  - شبکه: ۱۵۰ میلی‌ثانیه تأخیر، ۱٫۶ Mbps دانلود و ۷۵۰ kbps آپلود (`Network.emulateNetworkConditions`).
  - CPU: چهار برابر کندتر (`Emulation.setCPUThrottlingRate`).
- **سنجه‌ها:** از `PerformanceObserver`:
  - LCP از `largest-contentful-paint`.
  - CLS از `layout-shift`.
  - TBT: بخشِ بیش از ۵۰ میلی‌ثانیه‌ی هر long task پس از FCP. این همان جانشین آزمایشگاهی Lighthouse برای INP است، چون INP کلیک واقعی می‌خواهد.
- **تکرار:** هر صفحه سه بار با cache خالی بار شد، و میانه گزارش می‌شود.
- **داده‌ها:** API موقتاً با `db/bulk/compose.bulk.yml` روی `caravansara_bulk` (۱۰۰٬۰۰۰ آگهی) رفت و سپس برگشت. هیچ داده‌ای نوشته نشد.

هدف SC-003 برای هر سه صفحه برآورده شد: LCP ≤ ۲٫۵ s، INP ≤ ۲۰۰ ms (TBT کمتر از ۱۰ ms)، و CLS ≤ ۰٫۱. بار اول جستجو (۱٫۳۸ s) کندتر بود، چون پایگاه داده و cache صفحه هنوز گرم نشده بودند.

## محدودیت این اندازه‌گیری

- **عکس:** آگهی‌های داده‌ی حجیم عکس ندارند، پس LCP آن‌ها متن است. روی پایگاه داده‌ی اصلی (`caravansara`) هم LCP صفحه‌ی آگهی‌ای با عکس (۰٫۶۲ s) و صفحه‌ی جستجو (۰٫۶۷ s) برابر FCP بود. عکس‌های آن پایگاه داده را تست‌های e2e گذاشته‌اند، و این‌ها تصویر واقعی نیستند.
- **پایگاه داده‌ی دمو:** `caravansara_demo` عکس واقعی دارد، اما هنوز در migration `0001` است، یعنی پیش از کارهای ۰۰۲ تا ۰۰۴. پس API امروز با آن خطای `column l.review_status does not exist` می‌دهد. migration آن بدون اجازه‌ی مالک پروژه انجام نشد، چون داده‌ی دمو را تغییر می‌دهد. اندازه‌گیری LCP با عکس واقعی پس از به‌روز شدن دمو باقی می‌ماند.
- **عکس‌ها بهینه نمی‌شوند:** عکس‌ها مستقیم از storage می‌آیند (`images.unoptimized`). در production باید یک CDN اندازه‌ی مناسب را بدهد، و این در `docs/backend-design.md` ثبت است.

## SC-009: بالا آمدن سیستم

پس از `docker compose --profile observability down` (بدون `-v`)، فرمان `docker compose -f docker-compose.yml -f e2e/compose.e2e.yml --profile observability up -d --build` ۲۰ ثانیه طول کشید، چون لایه‌های image در cache بودند. اولین پاسخ 200 از `http://localhost:3001/fa` یک ثانیه پس از پایان آن آمد: ۲۱ ثانیه از آغاز. هدف (کمتر از ۲ دقیقه) برآورده شد. build بی‌cache (`npm ci` و `next build`) بیشتر طول می‌کشد، اما جزو این سنجه نیست. داده‌ها ماندند: دمو ۷۹۰ و bulk ۱۰۰٬۰۰۰ آگهی.

## SC-001: سفر کامل مهمان

یک اسکریپت Playwright در Chrome، با عرض ۳۹۰ پیکسل و حالت موبایل، مسیر کامل را روی stack واقعی رفت، و هر ۱۸ گامش پاس شد، بدون هیچ خطای صفحه یا کنسول:

۱. جستجو با پیشنهاد شهر، تقویم شمسی و مهمان‌ها.
۲. فیلتر امکانات.
۳. صفحه‌ی آگهی.
۴. «رزرو» بدون حساب، که به ورود و ثبت‌نام می‌رود و پس از آن به همان رزرو برمی‌گردد.
۵. نگه‌داشت با شمارش معکوس ۱۵ دقیقه‌ای.
۶. پرداخت، و دیدن نشانی دقیق و ساعت ورود به وقت آمستردام.
۷. بررسی اینکه هیچ توکنی در storage یا کوکی خواندنی نیست. تنها کوکی خواندنی `NEXT_LOCALE` (زبان) بود.
۸. رزرو دوم و لغو آن.
۹. سفرهای من.
۱۰. آواتار پیش‌فرض، آپلود JPEG، رد شدن فایل متنی با نام `.png`، و حذف عکس.
۱۱. همان رزرو در `/en`.
۱۲. خروج.

اسکریپت زمان یک انسان را نمی‌سنجد. SC-001 (کمتر از ۵ دقیقه برای یک کاربر تازه، بدون راهنما) هنوز با یک نفر، ترجیحاً کسی جز سازنده، اندازه گرفته نشده است.
