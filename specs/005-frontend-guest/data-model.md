# Data Model: فرانت‌اند وب، بخش ۱

این کار هیچ جدول، ستون یا migration تازه‌ای ندارد (research R1). تنها داده‌ی تازه فایل عکس پروفایل در storage است، که نشانی‌اش در ستون موجود `users.avatar_url` می‌نشیند (بخش «آواتار»). این سند وضعیت‌هایی را تعریف می‌کند که سایت نگه می‌دارد. برای هر کدام می‌گوید کجا نگه داشته می‌شود، چه قاعده‌ای دارد، و چرا آنجاست.

## نشست (Session)

| بخش | کجا | عمر | قاعده |
| --- | --- | --- | --- |
| `access_token` و زمان پایانش | حافظه‌ی صفحه (یک ماژول، نه React state سراسری قابل خواندن از بیرون) | ۱۵ دقیقه (`expires_in`) | ۶۰ ثانیه پیش از پایان، یا با پاسخ `token_expired` یا `invalid_token`، تازه می‌شود. با بارگذاری دوباره‌ی صفحه از بین می‌رود و از کوکی دوباره ساخته می‌شود |
| `refresh_token` | کوکی `cv_refresh`: `HttpOnly`، `Secure` در production، `SameSite=Strict`، `Path=/session` | ۳۰ روز (`refresh_token_days`) | فقط route handlerهای `/session/*` آن را می‌خوانند و می‌نویسند. با هر تازه کردن، کوکی تازه جایش را می‌گیرد |
| کاربر جاری (`UserOut`) | cache TanStack Query (`["me"]`) | تا خروج | پس از ورود، ثبت‌نام و ویرایش پروفایل تازه می‌شود |

**گذارها:**

```text
بی‌نشست --login/register--> وارد
وارد --access رو به پایان--> [قفل cv-refresh] --refresh موفق--> وارد (توکن تازه در BroadcastChannel)
                                              --refresh ناموفق (401)--> بی‌نشست (کوکی پاک، بازگشت به ورود با returnTo)
وارد --logout--> بی‌نشست (refresh در API باطل، کوکی پاک، پیام logout در BroadcastChannel)
```

**قواعد:**
- هیچ‌کدام از دو توکن در `localStorage`، `sessionStorage`، IndexedDB یا کوکی قابل خواندن با اسکریپت نیست (FR-012، SC-006).
- در هر مرورگر فقط یک زبانه در هر لحظه تازه می‌کند (research R4).

## انتخاب جستجو (Search state)

همه‌ی انتخاب‌ها در query string نشانی صفحه هستند (FR-020). نام‌ها همان نام پارامترهای API‌اند، تا صفحه آن‌ها را بی‌تغییر بفرستد.

| پارامتر | نوع | قاعده |
| --- | --- | --- |
| `city_id` | عدد | یا این، یا `lat`، `lng` و `radius_km`، نه هر دو |
| `lat`، `lng` | عدد | مرکز جستجوی شعاعی |
| `radius_km` | عدد | از ۱ تا ۱۰۰ (بازه‌ی سیستم)، پیش‌فرض ۵ |
| `check_in`، `check_out` | `YYYY-MM-DD` میلادی | با هم، و `check_out` پس از `check_in`. نمایش در تقویم زبان صفحه |
| `adults`، `children`، `infants`، `pets` | عدد صحیح | پیش‌فرض `adults=1`. نوزاد در ظرفیت حساب نمی‌شود |
| `amenity_ids` | فهرست عدد | آگهی باید همه را داشته باشد |
| `sort` | مقدار enum قرارداد | `distance` فقط با جستجوی شعاعی |
| `offset` | عدد | صفحه‌بندی با `limit` ثابت ۲۰ |

نشانی نامعتبر، مثلاً `radius_km=500`، به نزدیک‌ترین مقدار مجاز برگردانده می‌شود یا کنار گذاشته می‌شود، و صفحه خطا نمی‌دهد. پاسخ `invalid_search_area` پیام ترجمه‌شده می‌گیرد.

## پیش‌نویس رزرو (Booking draft)

| فیلد | منبع |
| --- | --- |
| `listing_id`، `check_in`، `check_out`، `adults`، `children`، `infants`، `pets` | انتخاب کاربر در صفحه‌ی آگهی |
| `idempotency_key` | `crypto.randomUUID()`، یک بار برای هر پیش‌نویس |
| `booking_id` | پس از ساخته شدن نگه‌داشت |

- **کجا:** در `sessionStorage` با کلید `cv-booking-draft`. فقط همان زبانه آن را می‌بیند، و با بستن زبانه پاک می‌شود (research R13).
- **قاعده:**
  - هر تغییر در فیلدهای انتخاب کلید تازه می‌سازد.
  - فرستادن دوباره‌ی همان پیش‌نویس کلید را نگه می‌دارد.
  - پس از پرداخت یا لغو، پیش‌نویس پاک می‌شود.

## نمای رزرو در صفحه (Booking view)

از `BookingOut` ساخته می‌شود و این چیزها را به آن اضافه می‌کند:

| مقدار محاسبه‌شده | قاعده |
| --- | --- |
| `remainingMs` | `hold_expires_at − (now + skew)`. `skew` از سرآیند `Date` پاسخ می‌آید (research R12). فقط برای `pending` معنی دارد |
| `canPay` | `status = pending` و `remainingMs > 0` |
| `canCancel` | `status ∈ {pending, confirmed}` و امروزِ شهر آگهی (`listing.timezone`) پیش از `check_in` است (research R9) |
| `cancelDeadline` | آغاز روز `check_in` به وقت شهر آگهی، که به‌صورت «تا پایان روز X به وقت Y» نمایش داده می‌شود |
| `canReview` | `status = completed`، رزرو نظر ندارد، و امروزِ شهر آگهی ≤ `check_out + 14 روز` |
| `group` | `upcoming` اگر `check_out` ≥ امروزِ شهر و وضعیت `pending` یا `confirmed` باشد؛ وگرنه `past` |

همه‌ی این قاعده‌ها فقط برای نمایش‌اند. پاسخ API مرجع نهایی است، و خطای آن پیام ترجمه‌شده می‌گیرد (FR-024).

**یک نکته‌ی سنجیده:** `BookingOut` فیلدی برای «نظر دارد» ندارد. پس `canReview` برای رزرو دارای نظر از روی خطای `already_reviewed` به‌روز می‌شود: پس از آن خطا، گزینه پنهان می‌شود و پیام نشان داده می‌شود. فهرست نظرهای خود کاربر در API نیست. این محدودیت در Assumptions plan ثبت است.

## آواتار (Avatar)

| بخش | کجا | قاعده |
| --- | --- | --- |
| فایل عکس | storage، کلید `avatars/{user_id}/{uuid}.{png\|jpg}` | PNG یا JPEG، حداکثر ۵٬۲۴۲٬۸۸۰ بایت. اندازه و امضای محتوا در `PUT /me/avatar` سنجیده می‌شوند (contracts/api.md) |
| نشانی | `users.avatar_url` (ستون موجود) | `null` یعنی آواتار پیش‌فرض. سایت هر نشانی را که با `NEXT_PUBLIC_MEDIA_BASE_URL` شروع نشود هم پیش‌فرض نشان می‌دهد (FR-041). هر کاربر در هر لحظه حداکثر یک فایل فعال دارد، و فایل قبلی پس از commit پاک می‌شود |
| آواتار پیش‌فرض | فقط در سایت ساخته می‌شود و ذخیره نمی‌شود | حرف اول `full_name` (با `Intl.Segmenter`) روی رنگ `palette[user.id % 8]`. هر رنگ با متن سفید کنتراست ≥ 4.5:1 دارد. `alt` آن نام کاربر است |

**گذارها:**

```text
پیش‌فرض --upload-url + آپلود به storage + PUT--> عکس
عکس --upload-url + آپلود + PUT--> عکس تازه (فایل قبلی پاک)
عکس --DELETE--> پیش‌فرض (فایل پاک)
هر حالت --PUT رد شده (اندازه، محتوا، کلید)--> همان حالت قبلی (فایل ردشده پاک)
```

**بررسی سمت سایت، پیش از آپلود (FR-038):**
- `file.size` ≤ ۵٬۲۴۲٬۸۸۰.
- `file.type` یکی از `image/png` یا `image/jpeg`.
- ۸ بایت اول فایل، که با `file.slice(0, 8)` خوانده می‌شوند، امضای PNG یا JPEG باشند.

اگر هر کدام برقرار نباشد، پیام ترجمه‌شده می‌آید و هیچ درخواستی فرستاده نمی‌شود. سرور همین بررسی‌ها را دوباره انجام می‌دهد و مرجع نهایی است.

## مبلغ (Money)

| ورودی | نمایش |
| --- | --- |
| `{ amount: "123456789.00", currency: "IRR" }` | فارسی: «۱۲٬۳۴۵٬۶۷۸٫۹ تومان»؛ چون اعشار نمی‌خواهیم، تقسیم بر ۱۰ گرد نمی‌شود، و رقم پس از ممیز فقط وقتی هست که مبلغ ریالی بر ۱۰ بخش‌پذیر نباشد. انگلیسی: «12,345,678.9 Toman» |
| `{ amount: "120.00", currency: "EUR" }` | فارسی: «‎€۱۲۰٫۰۰» با `Intl` و زبان `fa`. انگلیسی: «€120.00» |

- **قاعده:** محاسبه روی رشته‌ی decimal یا BigInt انجام می‌شود، نه `number` (research R10).

## پیام‌ها (Messages)

`frontend/messages/fa.json` و `en.json`، با ساختار یکسان:

| بخش | محتوا |
| --- | --- |
| `common`، `nav`، `search`، `listing`، `booking`، `trips`، `review`، `account` | متن صفحه‌ها |
| `errors.<code>` | یک پیام برای هر کد خطای بکند (research R7)، از جمله `image_too_large`، `invalid_image` و `invalid_avatar_url` (R20)، و `errors.unknown` |
| `amenities.<English name>`، `amenityCategories.<English name>` | ترجمه‌ی ۳۱ امکان و دسته‌ها (research R11) |
| `propertyTypes.<enum>` | نوع اقامتگاه |
| `cities.<English name>` | ترجمه‌ی شهرهای سیستم؛ اگر نبود، نام API |

- **قاعده:** دو فایل دقیقاً یک مجموعه کلید دارند، و این با تست سنجیده می‌شود.
