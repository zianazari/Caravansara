# Research: قیمت ریالی بدون سرریز

همه‌ی فرض‌های این سند با منبع واقعی سنجیده شده‌اند: کد فعلی، PostgreSQL 16 + PostGIS واقعی (`postgis/postgis:16-3.4`، در یک پایگاه داده‌ی موقت)، Pydantic نصب‌شده‌ی پروژه، و سایت اجاره‌ی روزانه‌ی ایرانی. دلیل: در کار ۰۰۱، دو فرض research موقع پیاده‌سازی عوض شدند.

## R1. جای واقعی خطای ۵۰۰

**یافته:** ورودی آگهی همین امروز سقف دارد: `Money = Annotated[Decimal, Field(max_digits=10, decimal_places=2)]` در `listings/schemas.py`. پس قیمت ۱۰۰٬۰۰۰٬۰۰۰ (۹ رقم صحیح + ۲ اعشار = ۱۱ رقم) امروز با ۴۲۲ `validation_error` رد می‌شود، نه ۵۰۰. خطای ۵۰۰ فقط در `POST /bookings` رخ می‌دهد: `rules.total_price` جمع را حساب می‌کند و ستون `bookings.total_price` آن را نمی‌پذیرد (`22003 numeric field overflow`). این خطا در `except IntegrityError` گرفته نمی‌شود، چون `22003` از خانواده‌ی `DataError` است.

**نتیجه:** هم سقف ورودی و هم ستون‌ها باید پهن شوند. پهن کردن فقط ستون، قیمت ۱۰۰ میلیون را هنوز رد می‌کند.

## R2. پهنای ستون

**Decision:** `NUMERIC(14,2)` برای هر پنج ستون (`listings.price_per_night`، `listings.cleaning_fee`، `bookings.nightly_price`، `bookings.cleaning_fee`، `bookings.total_price`). بیشترین مقدار: ۹۹۹٬۹۹۹٬۹۹۹٬۹۹۹٫۹۹.

**Rationale:** بدترین جمع مجاز = سقف × ۳۶۵ + سقف = ۳۶۶٬۰۰۰٬۰۰۰٬۰۰۰٫۰۰، که در `NUMERIC(14,2)` جا می‌شود (روی PostgreSQL واقعی آزموده شد). این حاشیه تا `max_nights = 998` کافی است. همه‌ی ستون‌ها یک پهنا دارند، چون قیمت شب رزرو کپی قیمت آگهی است و هزینه‌ی نظافت هم.

**Alternatives considered:**
- `NUMERIC(19,4)`: چهار رقم اعشار برای هیچ ارزی در این پروژه لازم نیست، و دو رقم اعشار تازه‌ای می‌سازد که API باید درباره‌اش تصمیم بگیرد.
- `BIGINT` به کوچک‌ترین واحد ارز: تغییر بزرگ در قرارداد API و همه‌ی کد قیمت. برای این خطا لازم نیست.
- پهنای جدا برای ستون جمع: ساده‌تر نیست، و یک قاعده‌ی دیگر برای یادآوری می‌سازد.

## R3. migration و بازگشت آن

**Decision:** migration تازه‌ی `0002`: هر جدول با یک `ALTER TABLE … ALTER COLUMN … TYPE NUMERIC(14,2)`. downgrade همان را به `NUMERIC(10,2)` برمی‌گرداند.

**یافته‌ها روی PostgreSQL واقعی** (جدولی با ۱۰۰٬۰۰۰ ردیف و همان `CHECK`ها):

| آزمون | نتیجه |
| --- | --- |
| پهن کردن `(10,2)` → `(14,2)` | بدون بازنویسی جدول (`pg_relation_filenode` همان ماند). فقط metadata عوض می‌شود، پس روی `caravansara_bulk` (۱٫۹ گیگابایت) هم فوری است. قفل `ACCESS EXCLUSIVE` لحظه‌ای است. |
| `CHECK`ها | بعد از پهن کردن همان می‌مانند. |
| باریک کردن با مقدار بزرگ ذخیره‌شده | `ERROR: 22003: numeric field overflow`؛ همه‌ی ردیف‌ها با همان مقدار ماندند. |
| باریک کردن وقتی همه‌ی مقدارها جا می‌شوند | انجام شد (با بازنویسی جدول، که برای بازگشت پذیرفتنی است). |

**Rationale:** رفتار خود PostgreSQL همان چیزی است که spec برای بازگشت می‌خواهد (توقف بدون از دست رفتن داده). پس downgrade کد اضافه‌ای برای بررسی لازم ندارد. هر migration در تراکنش خودش اجرا می‌شود (`transaction_per_migration=True` در `backend/migrations/env.py`). پس downgrade شکست‌خورده هیچ ستونی را نیمه‌کاره باریک نمی‌کند، و تست همین را بررسی می‌کند.

**Alternatives considered:** downgrade که مقدار بزرگ را به سقف قدیم ببُرد: داده را بی‌صدا عوض می‌کند، که spec رد کرده است.

## R4. سقف ورودی و قرارداد API

**Decision:** `Money = Annotated[Decimal, Field(max_digits=12, decimal_places=2, le=MAX_PRICE)]` با `MAX_PRICE = Decimal("1000000000.00")` در `listings/schemas.py`. بیش از سقف: ۴۲۲ `validation_error` با `loc` فیلد، مثل همه‌ی محدودیت‌های فیلد امروز.

**یافته (Pydantic نصب‌شده):** JSON schema حاصل `{"anyOf": [{"exclusiveMinimum": 0.0, "maximum": 1000000000.0, "type": "number"}, {"type": "string"}]}` است. یعنی سقف در `openapi.json` دیده می‌شود (FR-006). نوع خطا `less_than_equal` است، و `1000000000.00` پذیرفته می‌شود. شاخه‌ی `string` در قرارداد سقف ندارد. این امروز برای `exclusiveMinimum` هم همین است، و سرور در هر دو حالت آن را بررسی می‌کند.

**نکته:** `max_digits=12` به‌تنهایی تا ۹٬۹۹۹٬۹۹۹٬۹۹۹٫۹۹ را می‌پذیرد. `le` سقف واقعی است، و `max_digits` فقط جلوی ورودی بی‌معنا با رقم زیاد را می‌گیرد.

## R5. نگهبان جمع رزرو

**Decision:** تابع تازه در `bookings/rules.py` که اگر جمع از `MAX_STORED_AMOUNT = Decimal("999999999999.99")` (ظرفیت `NUMERIC(14,2)`) بیشتر شود، `Unprocessable("amount_too_large", …)` بیندازد. `create_booking` آن را پیش از ساختن ردیف صدا می‌زند.

**Rationale:** با سقف ورودی و `max_nights = 365` این خطا رخ نمی‌دهد (R2). ولی `max_nights` تنظیم است، و spec (FR-004) می‌گوید هیچ مبلغی نباید ۵۰۰ بدهد. بررسی پیش از درج پیام روشن می‌دهد و هیچ ردیفی نمی‌سازد. خود ستون همچنان نگهبان نهایی است (اصل I: کد برنامه فقط برای پیام روشن). کد تازه لازم است، چون هیچ فیلد ورودی‌ای اشتباه نیست.

**Alternatives considered:** گرفتن `22003` بعد از درج و تبدیل آن به ۴۲۲: بعد از رفت‌وبرگشت به پایگاه داده رخ می‌دهد، و `22003` ممکن است از ستون دیگری بیاید و پیام را گمراه کند.

## R6. جستجو

**یافته:** `search/repository.py` جمع را در SQL حساب می‌کند: `{nights} * l.price_per_night + l.cleaning_fee AS total_price`. نتیجه‌ی ضرب `numeric` در PostgreSQL پهنای نامحدود دارد، پس جستجو امروز هم سرریز نمی‌کند. فقط تست لازم است، تا FR-009 (جمع جستجو برابر جمع رزرو) ثابت شود.

## R7. قیمت واقعی بازار ایران برای دمو

**منبع:** صفحه‌های جاباما ([تهران](https://www.jabama.com/city-tehran)، [مرکز تهران](https://www.jabama.com/all?areas=tehran-center)، [استان تهران](https://www.jabama.com/province-tehran))، 2026-11-05. قیمت‌ها به تومان و برای هر شب‌اند (۱ تومان = ۱۰ ریال):

| نوع | تومان برای هر شب | ریال برای هر شب |
| --- | --- | --- |
| ارزان‌ترین اقامتگاه‌ها | از حدود ۲۴۹ هزار | حدود ۲٫۵ میلیون |
| یک‌خوابه | حدود ۱ تا ۱٫۷۵ میلیون | ۱۰ تا ۱۷٫۵ میلیون |
| دوخوابه | حدود ۲ تا ۸٫۵ میلیون | ۲۰ تا ۸۵ میلیون |
| سه‌خوابه | حدود ۴٫۷ میلیون | حدود ۴۷ میلیون |

**یافته:** بازه‌ی «۲۰ تا ۱۰۰ میلیون ریال» در future-work برای خانه‌ی کوچک و اتاق زیاد بود. spec اصلاح شد: خانه‌ی کامل تهران ۱۰ تا ۱۰۰ میلیون، و اتاق ۲٫۵ تا ۱۰ میلیون ریال.

**Decision (قاعده‌ی تغییر `fa_listings.json`):**

| شهر | خانه‌ی کامل | اتاق (خصوصی و اشتراکی) |
| --- | --- | --- |
| تهران | قیمت فعلی × ۵ (۲۲٫۵ تا ۹۷٫۵ میلیون)؛ گران‌ترین آگهی دقیقاً ۱۰۰٬۰۰۰٬۰۰۰ | قیمت فعلی × ۲، حداکثر ۱۰ میلیون |
| اصفهان و شیراز | قیمت فعلی × ۴ (۱۸ تا ۸۰ میلیون) | قیمت فعلی × ۲، حداکثر ۱۰ میلیون |

هزینه‌ی نظافت با همان ضریب. دلیل ضریب ثابت: ترتیب نسبی قیمت‌ها که در کار ۰۰۱ با توصیف هر آگهی جور شده بود، می‌ماند.

**بررسی‌های سازنده‌ی دمو (`build_demo_seed.py`):** بازه‌ی ۲٫۵ تا ۲۰ میلیون جای خود را به «خانه‌ی کامل ۱۰ تا ۱۰۰ میلیون، اتاق ۲٫۵ تا ۱۰ میلیون» می‌دهد. طول رزروهای ریالی از ۱–۴ به ۱–۱۴ شب، مثل بقیه‌ی دمو. بررسی `MAX_PRICE_COLUMN` (۹۹٬۹۹۹٬۹۹۹٫۹۹) حذف می‌شود، و بررسی تازه به جای آن می‌آید: هر جمع کمتر از `MAX_STORED_AMOUNT` باشد. `tests/test_demo_data.py` امروز `top < 99_999_999.99` را بررسی می‌کند، و برعکس می‌شود (SC-005).
