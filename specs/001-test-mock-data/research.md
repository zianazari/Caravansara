# Research: داده‌ی تست و ماک بیشتر و متنوع‌تر

**Feature**: [spec.md](spec.md) | **Plan**: [plan.md](plan.md) | **Date**: 2026-11-05

هر بخش یک تصمیم است، با دلیل و گزینه‌هایی که کنار گذاشته شدند.

## R1. شهرها و snapshotهای Inside Airbnb

- **Decision**: چهار شهر فعلی می‌مانند و دو شهر Inside Airbnb و سه شهر ایران اضافه می‌شوند:

  | شهر | کشور | ارز | منطقه‌ی زمانی | منبع |
  | --- | --- | --- | --- | --- |
  | Amsterdam | NL | EUR | Europe/Amsterdam | Inside Airbnb 2026-09-16 |
  | Lisbon | PT | EUR | Europe/Lisbon | Inside Airbnb 2026-09-19 |
  | Copenhagen | DK | DKK | Europe/Copenhagen | Inside Airbnb 2026-09-25 |
  | Stockholm | SE | SEK | Europe/Stockholm | Inside Airbnb 2026-09-25 |
  | London | GB | GBP | Europe/London | Inside Airbnb 2026-09-17 (`united-kingdom/england/london`) |
  | New York City | US | USD | America/New_York | Inside Airbnb 2026-09-14 (`united-states/ny/new-york-city`) |
  | Tehran | IR | IRR | Asia/Tehran | متن فارسی ساختگی |
  | Isfahan | IR | IRR | Asia/Tehran | متن فارسی ساختگی |
  | Shiraz | IR | IRR | Asia/Tehran | متن فارسی ساختگی |

  نتیجه: ۹ شهر، ۷ کشور، ۶ ارز و ۴ اختلاف ساعت با UTC (۰، ۱+، ۵−، ۳:۳۰+). FR-010 حداقل ۸ شهر، ۶ کشور، ۴ ارز و ۳ منطقه‌ی زمانی می‌خواهد.
- **Rationale**: تاریخ‌ها از صفحه‌ی get-the-data در 2026-11-05 خوانده شده‌اند. لندن و نیویورک دو ارز تازه (GBP و USD) می‌آورند. نیویورک تنها شهر پشت UTC است، پس خطاهای «امروز در شهر» را نشان می‌دهد: وقتی در UTC فردا شده، در نیویورک هنوز امروز است. Asia/Tehran اختلاف نیم‌ساعته دارد و این حالت مرزی خوبی برای محاسبه‌ی زمان است.
- **Alternatives considered**: Oslo (NOK) و Istanbul فقط یک ارز یا یک منطقه‌ی زمانی دیگر اضافه می‌کردند. Tokyo و Toronto هم داده دارند، ولی فایل دانلود را بزرگ‌تر می‌کنند و چیزی بیش از لندن و نیویورک نشان نمی‌دهند. Dubai در Inside Airbnb نیست.

## R2. سهم هر شهر در داده‌ی دمو

- **Decision**: ۱۲۵ آگهی برای هر شهر Inside Airbnb (۷۵۰ آگهی)، تا ۱۵ نظر انگلیسی برای هر آگهی، و ۴۰ آگهی فارسی (تهران ۱۶، اصفهان ۱۲، شیراز ۱۲). در کل ۷۹۰ آگهی.
- **Rationale**: FR-011 و FR-017 همین حداقل‌ها را می‌خواهند. با ۱۵ نظر برای هر آگهی، حدود ۱۰ هزار نظر به دست می‌آید. فایل `seed_demo.sql` از ۱٫۱ مگابایت به حدود ۷ مگابایت می‌رسد، که زیر سقف ۲۰ مگابایت SC-008 است.
- **Alternatives considered**: بیش از ۱۲۵ آگهی برای هر شهر، فایل SQL را به بیش از ۲۰ مگابایت می‌رساند و بارگذاری را از ۲ دقیقه کندتر می‌کند (SC-001). جای اندازه‌ی بزرگ، داده‌ی حجیم است.

## R3. عکس‌های دمو (پاسخ Q2: تصویر ساختگی)

- **Decision**: یک اسکریپت توسعه (`db/demo/build_demo_photos.py`) که با `uv run --with pillow` اجرا می‌شود، برای هر برچسب اتاق یک فایل JPEG می‌سازد: یک رنگ برای هر نوع اتاق، نام اتاق، و یک شکل ساده. این فایل‌ها در `db/demo/photos/` در git نگه داشته می‌شوند، همراه با `manifest.json` که ابعاد هر فایل را دارد. فرمان `seed-demo` همین فایل‌ها را زیر کلید هر عکس در MinIO قرار می‌دهد.

  برچسب‌ها و ابعاد:

  | برچسب اتاق | ابعاد |
  | --- | --- |
  | Living room | 1200×800 |
  | Bedroom | 1200×800 |
  | Kitchen | 1200×800 |
  | Bathroom | 800×1200 (عمودی) |
  | Exterior | 1600×900 |
  | Dining area | 1200×800 |
  | Workspace | 1200×900 |
  | Balcony | 900×1200 (عمودی) |

- **Rationale**:
  - فایل‌ها در git می‌مانند، پس بارگذاری دمو به Pillow و اینترنت نیاز ندارد و نتیجه همیشه یکسان است (FR-013). نسخه‌ی Pillow روی خروجی اثری ندارد، چون فایل یک بار ساخته و نگه داشته می‌شود.
  - ۸ فایل کوچک حدود ۳۰۰ کیلوبایت به مخزن اضافه می‌کنند (SC-008).
  - چند نسبت ابعاد مختلف، گالری و جای خالی پیش از بارگذاری را در UI می‌آزماید.
  - یک فایل برای چند کلید کافی است، چون `storage_key` باید یکتا باشد، ولی محتوای فایل لازم نیست.
- **Alternatives considered**:
  - Pillow به‌عنوان وابستگی اجرای بکند: کتابخانه‌ی بزرگی به image اضافه می‌کند، فقط برای داده‌ی دمو.
  - ساخت PNG فقط با کتابخانه‌ی استاندارد: نوشتن متن روی تصویر بدون فونت سخت است.
  - یک فایل جدا برای هر آگهی: حدود ۴ هزار فایل، بی‌آنکه چیز تازه‌ای نشان دهد.
- **پیامد**: `db/demo/photo_sources.csv` (نشانی عکس‌های واقعی میزبان‌ها) حذف می‌شود، چون دیگر عکس واقعی دانلود نمی‌شود. این عکس‌ها مال میزبان‌ها بودند، پس حذفشان ریسک حریم خصوصی را هم کم می‌کند.

## R4. تعداد و برچسب عکس هر آگهی

- **Decision**: هر آگهی بین ۳ تا ۸ عکس دارد. عکس `sort_order = 0` همیشه Living room است، یا Bedroom برای اتاق خصوصی. بعد از آن، به تعداد اتاق‌های خواب (حداکثر ۳) عکس `Bedroom 1..n` می‌آید. Kitchen و Bathroom همیشه هستند. Exterior، Dining area، Workspace و Balcony بر اساس امکانات آگهی و با RNG ثابت اضافه می‌شوند. Balcony فقط وقتی هست که آگهی امکان Balcony داشته باشد، و Workspace فقط با Dedicated workspace.

  `room_tag` همان برچسب انگلیسی است (`Bedroom 2`)، `caption` خالی است و `sort_order` از ۰ پیوسته جلو می‌رود.
- **Rationale**: FR-012 می‌خواهد برچسب‌ها متفاوت و ترتیب پیوسته باشد. وقتی عکس با امکانات آگهی بخواند، دمو باورپذیر می‌شود. برچسب انگلیسی کلید ثابتی است که UI ترجمه می‌کند، همان‌طور که با کد خطا رفتار می‌کند.
- **Alternatives considered**: برچسب فارسی برای آگهی‌های فارسی: داده را دوزبانه و ترجمه را ناممکن می‌کند.

## R5. حالت‌های مرزی در داده‌ی دمو

- **Decision**: حالت‌های مرزی در `build_demo_seed.py` روی آگهی‌ها و رزروهای مشخصی ساخته می‌شوند، و فهرست آن‌ها با شناسه در `db/demo/README.md` می‌آید (SC-005). همه‌ی تاریخ‌ها نسبت به زمان بارگذاری و در منطقه‌ی زمانی شهر آگهی هستند:

  | حالت | رکورد | تاریخ‌ها |
  | --- | --- | --- |
  | نگه‌داشت نزدیک انقضا | رزرو `pending` مهمان دمو در Amsterdam | `hold_expires_at = now() + interval '4 minutes'`، ورود ۲۰ روز بعد |
  | رزرو منقضی | رزرو `expired` مهمان دمو | `hold_expires_at = now() - interval '2 days'` |
  | اقامت ۳۶۵ شبه | رزرو `confirmed` در Lisbon | ورود ۳۰ روز بعد، خروج ۳۶۵ شب بعد از ورود |
  | آخرین روز مجاز | رزرو `confirmed` در Stockholm | ورود = امروزِ شهر + ۳۶۵ |
  | تحویل همان روز | دو رزرو `confirmed` پشت‌سرهم روی یک آگهی Copenhagen | خروج اولی = ورود دومی |
  | آگهی غیرفعال با رزرو | یک آگهی London با `is_active = false`، یک اقامت پایان‌یافته و یک رزرو آینده | |
  | آگهی بدون نظر | یک آگهی فعال New York City، بدون نظر | |

  «امروزِ شهر» در SQL به شکل `(now() AT TIME ZONE '<tz>')::date` نوشته می‌شود، نه `CURRENT_DATE`.
- **Rationale**:
  - مهلت نگه‌داشت ۱۵ دقیقه است، پس فقط تاریخ نسبی معنا دارد. ۴ دقیقه زیر سقف «کمتر از ۵ دقیقه»ی FR-014 است، و worker چند دقیقه بعد آن را منقضی می‌کند (US2، سناریوی ۲).
  - `max_days_ahead` در `rules.py` با «امروزِ شهر» مقایسه می‌شود. `CURRENT_DATE` تاریخ UTC سرور است، و نزدیک نیمه‌شب برای شهری مثل Stockholm یک روز اختلاف دارد. پس رزرو «آخرین روز مجاز» با آن نادرست می‌شد.
  - پایگاه داده قانون «حداکثر ۳۶۵ شب» و «حداکثر یک سال جلوتر» را بررسی نمی‌کند، فقط API بررسی می‌کند. پس حالت مرزی باید دقیقاً روی مرز باشد، نه بیرون از آن، تا داده با API سازگار بماند.
- **Alternatives considered**: یک فایل SQL جدا برای حالت‌های مرزی: دو فایل باید با هم بارگذاری شوند، و شناسه‌ها از هم جدا می‌شوند.

## R6. محتوای فارسی

- **Decision**: ۴۰ آگهی فارسی در فایل `db/demo/fa_listings.json` با دست نوشته می‌شوند: عنوان، توضیح، محله، نوع ملک، ظرفیت، قیمت به ریال، امکانات و ۲ تا ۴ نظر. مختصات در محله‌های واقعی‌اند، ولی نشانی ساختگی است (`پلاک ۱۲، کوچه‌ی نمونه، …`). `build_demo_seed.py` این فایل را می‌خواند و مثل آگهی‌های دیگر به SQL تبدیل می‌کند، با میزبان‌ها و مهمان‌های ساختگی فارسی‌نام.

  متن‌ها عمداً این‌ها را دارند (FR-018):
  - عدد فارسی و لاتین در کنار هم: «۲ اتاق خواب»، «Wi-Fi 100Mbps»
  - کلمه‌ی لاتین وسط جمله فارسی
  - دست‌کم یک توضیح بیش از ۱۰۰۰ نویسه
  - دست‌کم یک نظر کمتر از ۲۰ نویسه («عالی بود!»)
  - نیم‌فاصله
  - نقل‌قول و پرانتز
- **Rationale**: Inside Airbnb متن فارسی ندارد. JSON را بی‌آنکه SQL بلد باشی می‌شود خواند و ویرایش کرد. چون داده‌ی دست‌نوشته است، RNG فقط برای رزروها و ستاره‌ها به کار می‌رود، و خروجی همچنان یکسان است.
- **Alternatives considered**:
  - ترجمه‌ی ماشینی آگهی‌های Inside Airbnb: متن ترجمه‌شده درباره‌ی آمستردام در تهران باورپذیر نیست.
  - ساخت متن از قالب و تکه‌جمله: متن‌ها تکراری می‌شوند و مشکلات واقعی RTL، مثل طول‌های مختلف، را نشان نمی‌دهند.
- **قیمت**: IRR بدون اعشار، بین ۲٬۵۰۰٬۰۰۰ تا ۲۰٬۰۰۰٬۰۰۰ ریال برای هر شب (۲۵۰ هزار تا ۲ میلیون تومان). ستون‌های قیمت `NUMERIC(10,2)` هستند و حداکثر ۹۹٬۹۹۹٬۹۹۹٫۹۹ را می‌پذیرند. پس `total_price` هر رزرو فارسی باید زیر این سقف بماند: رزروهای فارسی حداکثر ۴ شب‌اند. `build_demo_seed.py` این سقف را بررسی می‌کند و اگر رد شود، با خطا متوقف می‌شود.

  > **یافته‌ی مهم**: این سقف یک محدودیت واقعی schema برای ریال است، نه فقط برای داده‌ی دمو. قیمت واقعی بازار تهران (حدود ۲ تا ۱۰ میلیون تومان، یعنی ۲۰ تا ۱۰۰ میلیون ریال برای هر شب) با یک رزرو چندشبه از سقف رد می‌شود، و API به‌جای خطای ۴۲۲ با خطای پایگاه داده (`numeric field overflow`) شکست می‌خورد. Assumptions در spec می‌گوید schema در این قابلیت تغییر نمی‌کند، پس این مورد به‌عنوان کار جدا در `docs/future-work.md` ثبت می‌شود (پیشنهاد: `NUMERIC(14,2)` یا `NUMERIC(19,4)`، با migration و downgrade).

## R7. بارگذاری catalog بدون پاک کردن داده (افزودن شهر به پایگاه داده‌ی موجود)

- **Decision**: `seed_locations.sql` و `seed_amenities.sql` با `ON CONFLICT DO NOTHING` افزایشی می‌شوند، و فرمان `caravansara seed` همیشه اجرا می‌شود و تعداد ردیف‌های تازه را گزارش می‌کند («catalog up to date: 5 new cities»)، نه اینکه رد شود.
- **Rationale**: امروز `seed` وقتی catalog ردیفی داشته باشد، رد می‌شود. یعنی پایگاه داده‌ی توسعه‌ی شما هیچ‌وقت لندن و تهران را نمی‌گیرد. اجرای افزایشی فقط ردیف تازه اضافه می‌کند، پس داده‌ی شما (Sara، Omid، رزرو 1797) دست نمی‌خورد. `migrate` در compose همین فرمان را اجرا می‌کند، پس `docker compose up` کافی است.
- **Alternatives considered**: یک migration داده در Alembic: catalog امروز seed است، نه migration، و این کار دو منبع برای فهرست شهرها می‌ساخت.
- **پیامد**: تست `test_seed_skips_an_existing_catalog` به «اجرای دوباره ردیفی اضافه نمی‌کند و شهرهای موجود را تغییر نمی‌دهد» تغییر می‌کند.

## R8. داده‌ی حجیم: کجا و چطور (پاسخ Q1: `caravansara_bulk`)

- **Decision**: فرمان `caravansara seed-bulk` در بسته‌ی بکند (`caravansara.devdata`) پیاده می‌شود:
  1. نام پایگاه داده‌ی هدف را از `database_url` تنظیمات می‌گیرد و پایگاه داده را به `caravansara_bulk` عوض می‌کند. `--database` نام دیگری را می‌پذیرد، ولی هرگز نام پایگاه داده‌ی تنظیمات را.
  2. اگر پایگاه داده نباشد، آن را با `CREATE DATABASE` می‌سازد (از پایگاه داده‌ی `postgres` همان سرور)، سپس `migrate` و `seed` را روی آن اجرا می‌کند.
  3. اگر `users` یا `listings` ردیفی داشته باشند، بدون تغییر متوقف می‌شود. `--replace` اول پایگاه داده‌ی هدف را `DROP` و دوباره می‌سازد، ولی فقط اگر نام آن با `_bulk` تمام شود.
  4. در `environment = production` اجرا نمی‌شود.
  5. همه‌ی جدول‌ها را در یک تراکنش با `COPY ... FROM STDIN` (قالب متنی) پر می‌کند، و در پایان sequenceها را جلو می‌برد.
- **Rationale**:
  - FR-008: پایگاه داده‌ی توسعه هرگز هدف نیست، و کاربر فقط با عوض کردن `CARAVANSARA_DATABASE_URL` به داده‌ی حجیم وصل می‌شود.
  - FR-007: یک تراکنش یعنی اگر کار وسط راه قطع شود، هیچ ردیفی نمی‌ماند.
  - فرمان در image بکند است، پس `docker compose run --rm migrate caravansara seed-bulk` بدون نصب چیزی روی میزبان کار می‌کند.
  - `COPY` متنی، `geography` را به شکل EWKT (`SRID=4326;POINT(lon lat)`) می‌پذیرد. `copy_records_to_table` دودویی asyncpg برای geography رمزگذار ندارد.
  - `COPY FROM` مقدار صریح ستون identity (`GENERATED ALWAYS`) را می‌پذیرد. این در 2026-11-05 روی `postgis/postgis:16-3.4` آزموده و تأیید شد، همراه با EWKT برای `geography`. پس به جدول موقت و `INSERT ... OVERRIDING SYSTEM VALUE SELECT` نیازی نیست.
  - ستون تولیدی `stay` در فهرست ستون‌های `COPY` نمی‌آید.
- **Alternatives considered**:
  - اسکریپت جدا در `db/` که CSV بنویسد و `psql \copy` بخواند: فایل میانی چند گیگابایتی می‌ساخت (خلاف FR-005)، و به psql روی میزبان نیاز داشت.
  - نمونه‌ی PostgreSQL جدا (گزینه‌ی B در Q1): پاسخ شما A بود.

## R9. قانون‌ها در زمان بارگذاری حجیم

- **Decision**: هیچ قید، ایندکس یا triggerی خاموش نمی‌شود (FR-006): نه `no_double_booking`، نه `reviews_completed_check`، نه `reviews_rating_sync`. تولیدکننده خودش بازه‌های غیرهم‌پوشان می‌سازد، و پایگاه داده آن را دوباره تضمین می‌کند.
- **Rationale**: اگر تولیدکننده اشتباه کند، بارگذاری با خطای 23P01 شکست می‌خورد. این همان چیزی است که اصل I قانون اساسی می‌خواهد. trigger امتیاز برای هر نظر یک `UPDATE` روی آگهی اجرا می‌کند. برآورد: حدود ۱ میلیون نظر × ۰٫۲ میلی‌ثانیه، یعنی حدود ۴ دقیقه، که داخل بودجه‌ی ۳۰ دقیقه‌ی SC-002 است. زمان واقعی در اجرای اول اندازه گرفته می‌شود (اصل VII).
- **Alternatives considered**: خاموش کردن trigger امتیاز و یک `UPDATE` در پایان: شاید سریع‌تر باشد، ولی FR-006 صریحاً آن را منع می‌کند. اگر اندازه‌گیری از ۳۰ دقیقه بیشتر شد، این تصمیم با عدد دوباره بررسی می‌شود.

## R10. تولید یکسان و کم‌حافظه

- **Decision**:
  - هر آگهی RNG خودش را دارد: `random.Random(f"{seed}:{listing_id}")`.
  - رزروها و نظرهای یک آگهی فقط از RNG همان آگهی ساخته می‌شوند. پس هر جدول را می‌شود جدا و به‌صورت جریانی تولید کرد، بی‌آنکه ۲ میلیون رزرو در حافظه بماند.
  - شناسه‌ی رزروها به ترتیب آگهی و به‌صورت پیوسته داده می‌شود.
  - `idempotency_key = uuid5(NAMESPACE, f"bulk-{seed}-{booking_id}")`.
  - «امروز» با `--today` (پیش‌فرض: امروز به UTC) ورودی تولیدکننده است.
- **Rationale**: FR-004 و SC-004 خروجی یکسان را با «همان ورودی» می‌خواهند، و تاریخ مرجع بخشی از ورودی است. RNG جداگانه‌ی هر آگهی یعنی تغییر یک آگهی بقیه را جابه‌جا نمی‌کند. حافظه با اندازه‌ی یک آگهی بالا می‌رود، نه با کل داده.
- **Alternatives considered**: یک RNG سراسری و همه‌چیز در حافظه: حدود ۱ گیگابایت حافظه برای ۲ میلیون tuple، و ترتیب تولید جدول‌ها را به هم گره می‌زد.

## R11. پروفایل شهرها برای داده‌ی حجیم

- **Decision**: اسکریپت `db/bulk/build_city_profiles.py` (فقط کتابخانه‌ی استاندارد) از فایل‌های cache‌شده‌ی Inside Airbnb برای هر شهر Inside Airbnb یک خلاصه‌ی آماری می‌سازد و آن را در `db/bulk/city_profiles.json` می‌نویسد. این فایل در git است (حدود ۲۰۰ کیلوبایت):
  - سهم هر نوع ملک
  - صدک‌های ۰ تا ۱۰۰ قیمت شبانه برای هر نوع ملک
  - توزیع ظرفیت، و اتاق خواب/تخت/حمام بر اساس ظرفیت
  - احتمال هر امکان catalog
  - میانگین و پراکندگی امتیاز
  - توزیع `estimated_occupancy_l365d` (شب‌های رزروشده در یک سال گذشته)، که میزان پر بودن تقویم از آن ساخته می‌شود
  - تعداد آگهی برای هر میزبان
  - سهم رزرو با نظر: ثابت ۰٫۵

  **تغییر هنگام پیاده‌سازی (2026-11-05)**: به‌جای `availability_365`، از ستون `estimated_occupancy_l365d` استفاده شد. دلیل: میانه‌ی `availability_365` در Amsterdam فقط ۱۴ روز است، چون بیشتر میزبان‌ها تقویم را می‌بندند، نه چون پر است. `estimated_occupancy_l365d` برآورد خود Inside Airbnb از شب‌های رزروشده است (میانگین حدود ۵۰ شب در سال در هر شش شهر). سهم نظر ۰٫۵ است، چون مدل اشغال Inside Airbnb همین را فرض می‌کند، و برآورد آن از روی همین فرض ساخته شده است.
  - ۵۰۰ نقطه‌ی نمونه‌ی مختصات، گرد شده به ۳ رقم اعشار

  `seed-bulk` فقط همین JSON را می‌خواند.
- **Rationale**: FR-003 توزیع را از داده‌ی واقعی می‌خواهد. با پروفایل نگه‌داشته‌شده، داده‌ی حجیم بدون اینترنت و بدون ۱٫۵ گیگابایت cache ساخته می‌شود، و ورودی برای همه یکسان است (FR-004). مختصات گرد شده و جابه‌جاشده، و Inside Airbnb خودش آن‌ها را حدود ۱۵۰ متر جابه‌جا می‌کند. پس هیچ آگهی واقعی را نمی‌شود از روی آن پیدا کرد.
- **Alternatives considered**: خواندن مستقیم CSVها در `seed-bulk`: به cache حجیم داخل container و دانلود قبلی نیاز داشت.
- **شهرهای ایران در داده‌ی حجیم نیستند**، چون داده‌ی واقعی برای ساختن پروفایل ندارند.

## R12. اندازه، زمان‌ها و تعداد ردیف‌ها در داده‌ی حجیم

- **Decision**: اندازه با `--listings` تعیین می‌شود (پیش‌فرض ۱۰۰٬۰۰۰)، و بقیه به همان نسبت:
  - میزبان‌ها: تعداد آگهی ÷ میانگین آگهی هر میزبان در پروفایل، وزن‌دار با اندازه‌ی شهر (حدود ۶۰ هزار)
  - مهمان‌ها: ۳ × تعداد آگهی (۳۰۰ هزار)
  - رزروها: هر آگهی در بازه‌ی ۲ سال گذشته (با میزان اشغال پروفایل) و ۱ سال آینده (با ۴۰٪ آن، چون رزرو دور کمتر است). اقامت‌ها ۱ تا ۱۴ شب‌اند، با میانگین حدود ۴ شب. اندازه‌گیری روی ۲۰ هزار آگهی: حدود ۳۰ رزرو برای هر آگهی، یعنی حدود ۳ میلیون برای ۱۰۰ هزار آگهی (FR-002: ≥ ۲ میلیون).

    **تغییر هنگام پیاده‌سازی**: طرح اول ۳ سال گذشته بود. با اشغال واقعی حدود ۵۰ شب در سال، این به حدود ۵ میلیون رزرو می‌رسید، که بیش از دو برابر هدف بود و بارگذاری را کند می‌کرد.
  - وضعیت رزروها: گذشته `completed`، به‌علاوه‌ی ۶٪ `cancelled`. آینده `confirmed`، به‌علاوه‌ی ۸٪ `cancelled`. حدود ۰٫۱٪ `pending` با مهلت باز، و ۲٪ `expired`.
  - نظرها: نیمی از اقامت‌های پایان‌یافته (حدود ۱٫۲ میلیون برای ۱۰۰ هزار آگهی)، با متن کوتاه انگلیسی که از ۳۰ عبارت ساختگی ترکیب می‌شود.
  - عکس‌ها: ۳ ردیف `listing_photos` برای هر آگهی با کلید `bulk/listings/<id>/<n>.jpg`، بدون فایل در MinIO.
  - امکانات: نمونه‌گیری از احتمال‌های پروفایل.
- **Rationale**: بخش ۳ کارهای آینده (بررسی ایندکس) به ردیف عکس و امکانات در جستجو نیاز دارد. فایل عکس برای اندازه‌گیری لازم نیست، و طبق Edge Cases، نبودن عکس نمایش را نمی‌شکند. متن نظر روی ایندکس‌ها اثری ندارد، پس متن ساختگی کافی است.
- **Alternatives considered**: متن واقعی نظرها در پروفایل: چند مگابایت متن، بی‌آنکه برای کارایی چیزی اضافه کند.

## R13. ابزار ساخت داده برای تست‌ها (factory)

- **Decision**: ماژول `backend/tests/factories.py` با کلاس `Factory` و fixture به نام `factory`:
  - `await factory.user(name="guest")`: کاربر را از راه API ثبت می‌کند و `User` با توکن برمی‌گرداند (همان `register`).
  - `await factory.listing(host=None, **overrides)`: آگهی را از راه API می‌سازد. اگر میزبان داده نشود، میزبان تازه می‌سازد.
  - `await factory.booking(status="confirmed", check_in=..., check_out=..., listing=None, guest=None, hold_expires_at=None)`: رزرو را مستقیم در پایگاه داده درج می‌کند، در هر وضعیت و هر تاریخی.
  - `await factory.stay(ended_days_ago=1)`: میانبُر برای اقامت پایان‌یافته‌ای که هنوز می‌شود برایش نظر نوشت. میزبان، مهمان، آگهی و رزرو را با یک فراخوانی می‌سازد.
  - `await factory.expire_hold(booking_id, ago=timedelta(minutes=1))`: مهلت را به گذشته می‌برد.

  تست‌های موجود که با `insert_booking` و `UPDATE bookings SET hold_expires_at` کار می‌کنند، به factory منتقل می‌شوند (FR-021). `test_database_rules.py` قانون‌های پایگاه داده را می‌آزماید، پس SQL مستقیمِ `INSERT INTO reviews` و `UPDATE listings` در آن می‌ماند. SC-007 فقط ساختن وضعیت رزرو را شامل می‌شود.
- **Rationale**: آنچه API می‌تواند بسازد (کاربر، آگهی) از راه API ساخته می‌شود، تا تست به جزئیات جدول وابسته نباشد و توکن داشته باشد. فقط وضعیت‌هایی که API عمداً نمی‌سازد (گذشته، منقضی، پایان‌یافته) مستقیم درج می‌شوند. قیدها و triggerها روی آن‌ها اجرا می‌شوند، پس هیچ قانونی دور زده نمی‌شود (FR-020).
- **Alternatives considered**:
  - factory_boy یا polyfactory: برای مدل‌های sync و ORM ساخته شده‌اند، و با API و asyncpg ما جور نیستند. یک کلاس کوچک کافی است.
  - همه‌چیز از راه SQL: کاربر بدون توکن و آگهی بدون `public_location` درست، تست‌ها را شکننده‌تر می‌کرد.
