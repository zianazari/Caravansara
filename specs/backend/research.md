### R3. عکس‌های دمو (پاسخ Q2: تصویر ساختگی)

- **Decision**: یک اسکریپت توسعه (`db/demo/build_demo_photos.py`) که با `uv run --with pillow` اجرا می‌شود، برای هر برچسب اتاق یک فایل JPEG می‌سازد: یک رنگ برای هر نوع اتاق، نام اتاق، و یک شکل ساده. این فایل‌ها در `db/demo/photos/` در git نگه داشته می‌شوند، همراه با `manifest.json` که ابعاد هر فایل را دارد. فرمان `seed-demo` همین فایل‌ها را زیر کلید هر عکس در MinIO قرار می‌دهد.

  برچسب‌ها و ابعاد:

  | برچسب اتاق | ابعاد |
  | --- | --- |
  | Living room | 1200×800 |
  | Bedroom | 1200×800 |
  | Kitchen | 1200×800 |
  | Bathroom | 800×1200 (عمودی) |
  | Exterior | 1600×900 |
  | Dining area | 1200×800 |
  | Workspace | 1200×900 |
  | Balcony | 900×1200 (عمودی) |

- **Rationale**:
  - فایل‌ها در git می‌مانند، پس بارگذاری دمو به Pillow و اینترنت نیاز ندارد و نتیجه همیشه یکسان است (FR-013). نسخه‌ی Pillow روی خروجی اثری ندارد، چون فایل یک بار ساخته و نگه داشته می‌شود.
  - ۸ فایل کوچک حدود ۳۰۰ کیلوبایت به مخزن اضافه می‌کنند (SC-008).
  - چند نسبت ابعاد مختلف، گالری و جای خالی پیش از بارگذاری را در UI می‌آزماید.
  - یک فایل برای چند کلید کافی است، چون `storage_key` باید یکتا باشد، ولی محتوای فایل لازم نیست.
- **Alternatives considered**:
  - Pillow به‌عنوان وابستگی اجرای بکند: کتابخانه‌ی بزرگی به image اضافه می‌کند، فقط برای داده‌ی دمو.
  - ساخت PNG فقط با کتابخانه‌ی استاندارد: نوشتن متن روی تصویر بدون فونت سخت است.
  - یک فایل جدا برای هر آگهی: حدود ۴ هزار فایل، بی‌آنکه چیز تازه‌ای نشان دهد.
- **پیامد**: `db/demo/photo_sources.csv` (نشانی عکس‌های واقعی میزبان‌ها) حذف می‌شود، چون دیگر عکس واقعی دانلود نمی‌شود. این عکس‌ها مال میزبان‌ها بودند، پس حذفشان ریسک حریم خصوصی را هم کم می‌کند.

### R4. تعداد و برچسب عکس هر آگهی

- **Decision**: هر آگهی بین ۳ تا ۸ عکس دارد. عکس `sort_order = 0` همیشه Living room است، یا Bedroom برای اتاق خصوصی. بعد از آن، به تعداد اتاق‌های خواب (حداکثر ۳) عکس `Bedroom 1..n` می‌آید. Kitchen و Bathroom همیشه هستند. Exterior، Dining area، Workspace و Balcony بر اساس امکانات آگهی و با RNG ثابت اضافه می‌شوند. Balcony فقط وقتی هست که آگهی امکان Balcony داشته باشد، و Workspace فقط با Dedicated workspace.

  `room_tag` همان برچسب انگلیسی است (`Bedroom 2`)، `caption` خالی است و `sort_order` از ۰ پیوسته جلو می‌رود.
- **Rationale**: FR-012 می‌خواهد برچسب‌ها متفاوت و ترتیب پیوسته باشد. وقتی عکس با امکانات آگهی بخواند، دمو باورپذیر می‌شود. برچسب انگلیسی کلید ثابتی است که UI ترجمه می‌کند، همان‌طور که با کد خطا رفتار می‌کند.
- **Alternatives considered**: برچسب فارسی برای آگهی‌های فارسی: داده را دوزبانه و ترجمه را ناممکن می‌کند.

### R5. حالت‌های مرزی در داده‌ی دمو

- **Decision**: حالت‌های مرزی در `build_demo_seed.py` روی آگهی‌ها و رزروهای مشخصی ساخته می‌شوند، و فهرست آن‌ها با شناسه در `db/demo/README.md` می‌آید (SC-005). همه‌ی تاریخ‌ها نسبت به زمان بارگذاری و در منطقه‌ی زمانی شهر آگهی هستند:

  | حالت | رکورد | تاریخ‌ها |
  | --- | --- | --- |
  | نگه‌داشت نزدیک انقضا | رزرو `pending` مهمان دمو در Amsterdam | `hold_expires_at = now() + interval '4 minutes'`، ورود ۲۰ روز بعد |
  | رزرو منقضی | رزرو `expired` مهمان دمو | `hold_expires_at = now() - interval '2 days'` |
  | اقامت ۳۶۵ شبه | رزرو `confirmed` در Lisbon | ورود ۳۰ روز بعد، خروج ۳۶۵ شب بعد از ورود |
  | آخرین روز مجاز | رزرو `confirmed` در Stockholm | ورود = امروزِ شهر + ۳۶۵ |
  | تحویل همان روز | دو رزرو `confirmed` پشت‌سرهم روی یک آگهی Copenhagen | خروج اولی = ورود دومی |
  | آگهی غیرفعال با رزرو | یک آگهی London با `is_active = false`، یک اقامت پایان‌یافته و یک رزرو آینده | |
  | آگهی بدون نظر | یک آگهی فعال New York City، بدون نظر | |

  «امروزِ شهر» در SQL به شکل `(now() AT TIME ZONE '<tz>')::date` نوشته می‌شود، نه `CURRENT_DATE`.
- **Rationale**:
  - مهلت نگه‌داشت ۱۵ دقیقه است، پس فقط تاریخ نسبی معنا دارد. ۴ دقیقه زیر سقف «کمتر از ۵ دقیقه»ی FR-014 است، و worker چند دقیقه بعد آن را منقضی می‌کند (US2، سناریوی ۲).
  - `max_days_ahead` در `rules.py` با «امروزِ شهر» مقایسه می‌شود. `CURRENT_DATE` تاریخ UTC سرور است، و نزدیک نیمه‌شب برای شهری مثل Stockholm یک روز اختلاف دارد. پس رزرو «آخرین روز مجاز» با آن نادرست می‌شد.
  - پایگاه داده قانون «حداکثر ۳۶۵ شب» و «حداکثر یک سال جلوتر» را بررسی نمی‌کند، فقط API بررسی می‌کند. پس حالت مرزی باید دقیقاً روی مرز باشد، نه بیرون از آن، تا داده با API سازگار بماند.
- **Alternatives considered**: یک فایل SQL جدا برای حالت‌های مرزی: دو فایل باید با هم بارگذاری شوند، و شناسه‌ها از هم جدا می‌شوند.

### R6. محتوای فارسی

- **Decision**: ۴۰ آگهی فارسی در فایل `db/demo/fa_listings.json` با دست نوشته می‌شوند: عنوان، توضیح، محله، نوع ملک، ظرفیت، قیمت به ریال، امکانات و ۲ تا ۴ نظر. مختصات در محله‌های واقعی‌اند، ولی نشانی ساختگی است (`پلاک ۱۲، کوچه‌ی نمونه، …`). `build_demo_seed.py` این فایل را می‌خواند و مثل آگهی‌های دیگر به SQL تبدیل می‌کند، با میزبان‌ها و مهمان‌های ساختگی فارسی‌نام.

  متن‌ها عمداً این‌ها را دارند (FR-018):
  - عدد فارسی و لاتین در کنار هم: «۲ اتاق خواب»، «Wi-Fi 100Mbps»
  - کلمه‌ی لاتین وسط جمله فارسی
  - دست‌کم یک توضیح بیش از ۱۰۰۰ نویسه
  - دست‌کم یک نظر کمتر از ۲۰ نویسه («عالی بود!»)
  - نیم‌فاصله
  - نقل‌قول و پرانتز
- **Rationale**: Inside Airbnb متن فارسی ندارد. JSON را بی‌آنکه SQL بلد باشی می‌شود خواند و ویرایش کرد. چون داده‌ی دست‌نوشته است، RNG فقط برای رزروها و ستاره‌ها به کار می‌رود، و خروجی همچنان یکسان است.
- **Alternatives considered**:
  - ترجمه‌ی ماشینی آگهی‌های Inside Airbnb: متن ترجمه‌شده درباره‌ی آمستردام در تهران باورپذیر نیست.
  - ساخت متن از قالب و تکه‌جمله: متن‌ها تکراری می‌شوند و مشکلات واقعی RTL، مثل طول‌های مختلف، را نشان نمی‌دهند.
- **قیمت**: IRR بدون اعشار، بین ۲٬۵۰۰٬۰۰۰ تا ۲۰٬۰۰۰٬۰۰۰ ریال برای هر شب (۲۵۰ هزار تا ۲ میلیون تومان). ستون‌های قیمت `NUMERIC(10,2)` هستند و حداکثر ۹۹٬۹۹۹٬۹۹۹٫۹۹ را می‌پذیرند. پس `total_price` هر رزرو فارسی باید زیر این سقف بماند: رزروهای فارسی حداکثر ۴ شب‌اند. `build_demo_seed.py` این سقف را بررسی می‌کند و اگر رد شود، با خطا متوقف می‌شود.

  > **یافته‌ی مهم**: این سقف یک محدودیت واقعی schema برای ریال است، نه فقط برای داده‌ی دمو. قیمت واقعی بازار تهران (حدود ۲ تا ۱۰ میلیون تومان، یعنی ۲۰ تا ۱۰۰ میلیون ریال برای هر شب) با یک رزرو چندشبه از سقف رد می‌شود، و API به‌جای خطای ۴۲۲ با خطای پایگاه داده (`numeric field overflow`) شکست می‌خورد. Assumptions در spec می‌گوید schema در این قابلیت تغییر نمی‌کند، پس این مورد به‌عنوان کار جدا در `docs/future-work.md` ثبت می‌شود (پیشنهاد: `NUMERIC(14,2)` یا `NUMERIC(19,4)`، با migration و downgrade).

### R7. بارگذاری catalog بدون پاک کردن داده (افزودن شهر به پایگاه داده‌ی موجود)

- **Decision**: `seed_locations.sql` و `seed_amenities.sql` با `ON CONFLICT DO NOTHING` افزایشی می‌شوند، و فرمان `caravansara seed` همیشه اجرا می‌شود و تعداد ردیف‌های تازه را گزارش می‌کند («catalog up to date: 5 new cities»)، نه اینکه رد شود.
- **Rationale**: امروز `seed` وقتی catalog ردیفی داشته باشد، رد می‌شود. یعنی پایگاه داده‌ی توسعه‌ی شما هیچ‌وقت لندن و تهران را نمی‌گیرد. اجرای افزایشی فقط ردیف تازه اضافه می‌کند، پس داده‌ی شما (Sara، Omid، رزرو 1797) دست نمی‌خورد. `migrate` در compose همین فرمان را اجرا می‌کند، پس `docker compose up` کافی است.
- **Alternatives considered**: یک migration داده در Alembic: catalog امروز seed است، نه migration، و این کار دو منبع برای فهرست شهرها می‌ساخت.
- **پیامد**: تست `test_seed_skips_an_existing_catalog` به «اجرای دوباره ردیفی اضافه نمی‌کند و شهرهای موجود را تغییر نمی‌دهد» تغییر می‌کند.

### R8. داده‌ی حجیم: کجا و چطور (پاسخ Q1: `caravansara_bulk`)

- **Decision**: فرمان `caravansara seed-bulk` در بسته‌ی بکند (`caravansara.devdata`) پیاده می‌شود:
  1. نام پایگاه داده‌ی هدف را از `database_url` تنظیمات می‌گیرد و پایگاه داده را به `caravansara_bulk` عوض می‌کند. `--database` نام دیگری را می‌پذیرد، ولی هرگز نام پایگاه داده‌ی تنظیمات را.
  2. اگر پایگاه داده نباشد، آن را با `CREATE DATABASE` می‌سازد (از پایگاه داده‌ی `postgres` همان سرور)، سپس `migrate` و `seed` را روی آن اجرا می‌کند.
  3. اگر `users` یا `listings` ردیفی داشته باشند، بدون تغییر متوقف می‌شود. `--replace` اول پایگاه داده‌ی هدف را `DROP` و دوباره می‌سازد، ولی فقط اگر نام آن با `_bulk` تمام شود.
  4. در `environment = production` اجرا نمی‌شود.
  5. همه‌ی جدول‌ها را در یک تراکنش با `COPY ... FROM STDIN` (قالب متنی) پر می‌کند، و در پایان sequenceها را جلو می‌برد.
- **Rationale**:
  - FR-008: پایگاه داده‌ی توسعه هرگز هدف نیست، و کاربر فقط با عوض کردن `CARAVANSARA_DATABASE_URL` به داده‌ی حجیم وصل می‌شود.
  - FR-007: یک تراکنش یعنی اگر کار وسط راه قطع شود، هیچ ردیفی نمی‌ماند.
  - فرمان در image بکند است، پس `docker compose run --rm migrate caravansara seed-bulk` بدون نصب چیزی روی میزبان کار می‌کند.
  - `COPY` متنی، `geography` را به شکل EWKT (`SRID=4326;POINT(lon lat)`) می‌پذیرد. `copy_records_to_table` دودویی asyncpg برای geography رمزگذار ندارد.
  - `COPY FROM` مقدار صریح ستون identity (`GENERATED ALWAYS`) را می‌پذیرد. این در 2026-11-05 روی `postgis/postgis:16-3.4` آزموده و تأیید شد، همراه با EWKT برای `geography`. پس به جدول موقت و `INSERT ... OVERRIDING SYSTEM VALUE SELECT` نیازی نیست.
  - ستون تولیدی `stay` در فهرست ستون‌های `COPY` نمی‌آید.
- **Alternatives considered**:
  - اسکریپت جدا در `db/` که CSV بنویسد و `psql \copy` بخواند: فایل میانی چند گیگابایتی می‌ساخت (خلاف FR-005)، و به psql روی میزبان نیاز داشت.
  - نمونه‌ی PostgreSQL جدا (گزینه‌ی B در Q1): پاسخ شما A بود.

### R9. قانون‌ها در زمان بارگذاری حجیم

- **Decision**: هیچ قید، ایندکس یا triggerی خاموش نمی‌شود (FR-006): نه `no_double_booking`، نه `reviews_completed_check`، نه `reviews_rating_sync`. تولیدکننده خودش بازه‌های غیرهم‌پوشان می‌سازد، و پایگاه داده آن را دوباره تضمین می‌کند.
- **Rationale**: اگر تولیدکننده اشتباه کند، بارگذاری با خطای 23P01 شکست می‌خورد. این همان چیزی است که اصل I قانون اساسی می‌خواهد. trigger امتیاز برای هر نظر یک `UPDATE` روی آگهی اجرا می‌کند. برآورد: حدود ۱ میلیون نظر × ۰٫۲ میلی‌ثانیه، یعنی حدود ۴ دقیقه، که داخل بودجه‌ی ۳۰ دقیقه‌ی SC-002 است. زمان واقعی در اجرای اول اندازه گرفته می‌شود (اصل VII).
- **Alternatives considered**: خاموش کردن trigger امتیاز و یک `UPDATE` در پایان: شاید سریع‌تر باشد، ولی FR-006 صریحاً آن را منع می‌کند. اگر اندازه‌گیری از ۳۰ دقیقه بیشتر شد، این تصمیم با عدد دوباره بررسی می‌شود.

### R10. تولید یکسان و کم‌حافظه

- **Decision**:
  - هر آگهی RNG خودش را دارد: `random.Random(f"{seed}:{listing_id}")`.
  - رزروها و نظرهای یک آگهی فقط از RNG همان آگهی ساخته می‌شوند. پس هر جدول را می‌شود جدا و به‌صورت جریانی تولید کرد، بی‌آنکه ۲ میلیون رزرو در حافظه بماند.
  - شناسه‌ی رزروها به ترتیب آگهی و به‌صورت پیوسته داده می‌شود.
  - `idempotency_key = uuid5(NAMESPACE, f"bulk-{seed}-{booking_id}")`.
  - «امروز» با `--today` (پیش‌فرض: امروز به UTC) ورودی تولیدکننده است.
- **Rationale**: FR-004 و SC-004 خروجی یکسان را با «همان ورودی» می‌خواهند، و تاریخ مرجع بخشی از ورودی است. RNG جداگانه‌ی هر آگهی یعنی تغییر یک آگهی بقیه را جابه‌جا نمی‌کند. حافظه با اندازه‌ی یک آگهی بالا می‌رود، نه با کل داده.
- **Alternatives considered**: یک RNG سراسری و همه‌چیز در حافظه: حدود ۱ گیگابایت حافظه برای ۲ میلیون tuple، و ترتیب تولید جدول‌ها را به هم گره می‌زد.

### R11. پروفایل شهرها برای داده‌ی حجیم

- **Decision**: اسکریپت `db/bulk/build_city_profiles.py` (فقط کتابخانه‌ی استاندارد) از فایل‌های cache‌شده‌ی Inside Airbnb برای هر شهر Inside Airbnb یک خلاصه‌ی آماری می‌سازد و آن را در `db/bulk/city_profiles.json` می‌نویسد. این فایل در git است (حدود ۲۰۰ کیلوبایت):
  - سهم هر نوع ملک
  - صدک‌های ۰ تا ۱۰۰ قیمت شبانه برای هر نوع ملک
  - توزیع ظرفیت، و اتاق خواب/تخت/حمام بر اساس ظرفیت
  - احتمال هر امکان catalog
  - میانگین و پراکندگی امتیاز
  - توزیع `estimated_occupancy_l365d` (شب‌های رزروشده در یک سال گذشته)، که میزان پر بودن تقویم از آن ساخته می‌شود
  - تعداد آگهی برای هر میزبان
  - سهم رزرو با نظر: ثابت ۰٫۵

  **تغییر هنگام پیاده‌سازی (2026-11-05)**: به‌جای `availability_365`، از ستون `estimated_occupancy_l365d` استفاده شد. دلیل: میانه‌ی `availability_365` در Amsterdam فقط ۱۴ روز است، چون بیشتر میزبان‌ها تقویم را می‌بندند، نه چون پر است. `estimated_occupancy_l365d` برآورد خود Inside Airbnb از شب‌های رزروشده است (میانگین حدود ۵۰ شب در سال در هر شش شهر). سهم نظر ۰٫۵ است، چون مدل اشغال Inside Airbnb همین را فرض می‌کند، و برآورد آن از روی همین فرض ساخته شده است.
  - ۵۰۰ نقطه‌ی نمونه‌ی مختصات، گرد شده به ۳ رقم اعشار

  `seed-bulk` فقط همین JSON را می‌خواند.
- **Rationale**: FR-003 توزیع را از داده‌ی واقعی می‌خواهد. با پروفایل نگه‌داشته‌شده، داده‌ی حجیم بدون اینترنت و بدون ۱٫۵ گیگابایت cache ساخته می‌شود، و ورودی برای همه یکسان است (FR-004). مختصات گرد شده و جابه‌جاشده، و Inside Airbnb خودش آن‌ها را حدود ۱۵۰ متر جابه‌جا می‌کند. پس هیچ آگهی واقعی را نمی‌شود از روی آن پیدا کرد.
- **Alternatives considered**: خواندن مستقیم CSVها در `seed-bulk`: به cache حجیم داخل container و دانلود قبلی نیاز داشت.
- **شهرهای ایران در داده‌ی حجیم نیستند**، چون داده‌ی واقعی برای ساختن پروفایل ندارند.

### R12. اندازه، زمان‌ها و تعداد ردیف‌ها در داده‌ی حجیم

- **Decision**: اندازه با `--listings` تعیین می‌شود (پیش‌فرض ۱۰۰٬۰۰۰)، و بقیه به همان نسبت:
  - میزبان‌ها: تعداد آگهی ÷ میانگین آگهی هر میزبان در پروفایل، وزن‌دار با اندازه‌ی شهر (حدود ۶۰ هزار)
  - مهمان‌ها: ۳ × تعداد آگهی (۳۰۰ هزار)
  - رزروها: هر آگهی در بازه‌ی ۲ سال گذشته (با میزان اشغال پروفایل) و ۱ سال آینده (با ۴۰٪ آن، چون رزرو دور کمتر است). اقامت‌ها ۱ تا ۱۴ شب‌اند، با میانگین حدود ۴ شب. اندازه‌گیری روی ۲۰ هزار آگهی: حدود ۳۰ رزرو برای هر آگهی، یعنی حدود ۳ میلیون برای ۱۰۰ هزار آگهی (FR-002: ≥ ۲ میلیون).

    **تغییر هنگام پیاده‌سازی**: طرح اول ۳ سال گذشته بود. با اشغال واقعی حدود ۵۰ شب در سال، این به حدود ۵ میلیون رزرو می‌رسید، که بیش از دو برابر هدف بود و بارگذاری را کند می‌کرد.
  - وضعیت رزروها: گذشته `completed`، به‌علاوه‌ی ۶٪ `cancelled`. آینده `confirmed`، به‌علاوه‌ی ۸٪ `cancelled`. حدود ۰٫۱٪ `pending` با مهلت باز، و ۲٪ `expired`.
  - نظرها: نیمی از اقامت‌های پایان‌یافته (حدود ۱٫۲ میلیون برای ۱۰۰ هزار آگهی)، با متن کوتاه انگلیسی که از ۳۰ عبارت ساختگی ترکیب می‌شود.
  - عکس‌ها: ۳ ردیف `listing_photos` برای هر آگهی با کلید `bulk/listings/<id>/<n>.jpg`، بدون فایل در MinIO.
  - امکانات: نمونه‌گیری از احتمال‌های پروفایل.
- **Rationale**: بخش ۳ کارهای آینده (بررسی ایندکس) به ردیف عکس و امکانات در جستجو نیاز دارد. فایل عکس برای اندازه‌گیری لازم نیست، و طبق Edge Cases، نبودن عکس نمایش را نمی‌شکند. متن نظر روی ایندکس‌ها اثری ندارد، پس متن ساختگی کافی است.
- **Alternatives considered**: متن واقعی نظرها در پروفایل: چند مگابایت متن، بی‌آنکه برای کارایی چیزی اضافه کند.

### R13. ابزار ساخت داده برای تست‌ها (factory)

- **Decision**: ماژول `backend/tests/factories.py` با کلاس `Factory` و fixture به نام `factory`:
  - `await factory.user(name="guest")`: کاربر را از راه API ثبت می‌کند و `User` با توکن برمی‌گرداند (همان `register`).
  - `await factory.listing(host=None, **overrides)`: آگهی را از راه API می‌سازد. اگر میزبان داده نشود، میزبان تازه می‌سازد.
  - `await factory.booking(status="confirmed", check_in=..., check_out=..., listing=None, guest=None, hold_expires_at=None)`: رزرو را مستقیم در پایگاه داده درج می‌کند، در هر وضعیت و هر تاریخی.
  - `await factory.stay(ended_days_ago=1)`: میانبُر برای اقامت پایان‌یافته‌ای که هنوز می‌شود برایش نظر نوشت. میزبان، مهمان، آگهی و رزرو را با یک فراخوانی می‌سازد.
  - `await factory.expire_hold(booking_id, ago=timedelta(minutes=1))`: مهلت را به گذشته می‌برد.

  تست‌های موجود که با `insert_booking` و `UPDATE bookings SET hold_expires_at` کار می‌کنند، به factory منتقل می‌شوند (FR-021). `test_database_rules.py` قانون‌های پایگاه داده را می‌آزماید، پس SQL مستقیمِ `INSERT INTO reviews` و `UPDATE listings` در آن می‌ماند. SC-007 فقط ساختن وضعیت رزرو را شامل می‌شود.
- **Rationale**: آنچه API می‌تواند بسازد (کاربر، آگهی) از راه API ساخته می‌شود، تا تست به جزئیات جدول وابسته نباشد و توکن داشته باشد. فقط وضعیت‌هایی که API عمداً نمی‌سازد (گذشته، منقضی، پایان‌یافته) مستقیم درج می‌شوند. قیدها و triggerها روی آن‌ها اجرا می‌شوند، پس هیچ قانونی دور زده نمی‌شود (FR-020).
- **Alternatives considered**:
  - factory_boy یا polyfactory: برای مدل‌های sync و ORM ساخته شده‌اند، و با API و asyncpg ما جور نیستند. یک کلاس کوچک کافی است.
  - همه‌چیز از راه SQL: کاربر بدون توکن و آگهی بدون `public_location` درست، تست‌ها را شکننده‌تر می‌کرد.

## 002. قیمت ریالی بدون سرریز

همه‌ی فرض‌های این سند با منبع واقعی سنجیده شده‌اند: کد فعلی، PostgreSQL 16 + PostGIS واقعی (`postgis/postgis:16-3.4`، در یک پایگاه داده‌ی موقت)، Pydantic نصب‌شده‌ی پروژه، و سایت اجاره‌ی روزانه‌ی ایرانی. دلیل: در کار ۰۰۱، دو فرض research موقع پیاده‌سازی عوض شدند.

### R1. جای واقعی خطای ۵۰۰

**یافته:** ورودی آگهی همین امروز سقف دارد: `Money = Annotated[Decimal, Field(max_digits=10, decimal_places=2)]` در `listings/schemas.py`. پس قیمت ۱۰۰٬۰۰۰٬۰۰۰ (۹ رقم صحیح + ۲ اعشار = ۱۱ رقم) امروز با ۴۲۲ `validation_error` رد می‌شود، نه ۵۰۰. خطای ۵۰۰ فقط در `POST /bookings` رخ می‌دهد: `rules.total_price` جمع را حساب می‌کند و ستون `bookings.total_price` آن را نمی‌پذیرد (`22003 numeric field overflow`). این خطا در `except IntegrityError` گرفته نمی‌شود، چون `22003` از خانواده‌ی `DataError` است.

**نتیجه:** هم سقف ورودی و هم ستون‌ها باید پهن شوند. پهن کردن فقط ستون، قیمت ۱۰۰ میلیون را هنوز رد می‌کند.

### R2. پهنای ستون

**Decision:** `NUMERIC(14,2)` برای هر پنج ستون (`listings.price_per_night`، `listings.cleaning_fee`، `bookings.nightly_price`، `bookings.cleaning_fee`، `bookings.total_price`). بیشترین مقدار: ۹۹۹٬۹۹۹٬۹۹۹٬۹۹۹٫۹۹.

**Rationale:** بدترین جمع مجاز = سقف × ۳۶۵ + سقف = ۳۶۶٬۰۰۰٬۰۰۰٬۰۰۰٫۰۰، که در `NUMERIC(14,2)` جا می‌شود (روی PostgreSQL واقعی آزموده شد). این حاشیه تا `max_nights = 998` کافی است. همه‌ی ستون‌ها یک پهنا دارند، چون قیمت شب رزرو کپی قیمت آگهی است و هزینه‌ی نظافت هم.

**Alternatives considered:**
- `NUMERIC(19,4)`: چهار رقم اعشار برای هیچ ارزی در این پروژه لازم نیست، و دو رقم اعشار تازه‌ای می‌سازد که API باید درباره‌اش تصمیم بگیرد.
- `BIGINT` به کوچک‌ترین واحد ارز: تغییر بزرگ در قرارداد API و همه‌ی کد قیمت. برای این خطا لازم نیست.
- پهنای جدا برای ستون جمع: ساده‌تر نیست، و یک قاعده‌ی دیگر برای یادآوری می‌سازد.

### R3. migration و بازگشت آن

**Decision:** migration تازه‌ی `0002`: هر جدول با یک `ALTER TABLE … ALTER COLUMN … TYPE NUMERIC(14,2)`. downgrade همان را به `NUMERIC(10,2)` برمی‌گرداند.

**یافته‌ها روی PostgreSQL واقعی** (جدولی با ۱۰۰٬۰۰۰ ردیف و همان `CHECK`ها):

| آزمون | نتیجه |
| --- | --- |
| پهن کردن `(10,2)` → `(14,2)` | بدون بازنویسی جدول (`pg_relation_filenode` همان ماند). فقط metadata عوض می‌شود، پس روی `caravansara_bulk` (۱٫۹ گیگابایت) هم فوری است. قفل `ACCESS EXCLUSIVE` لحظه‌ای است. |
| `CHECK`ها | بعد از پهن کردن همان می‌مانند. |
| باریک کردن با مقدار بزرگ ذخیره‌شده | `ERROR: 22003: numeric field overflow`؛ همه‌ی ردیف‌ها با همان مقدار ماندند. |
| باریک کردن وقتی همه‌ی مقدارها جا می‌شوند | انجام شد (با بازنویسی جدول، که برای بازگشت پذیرفتنی است). |

**Rationale:** رفتار خود PostgreSQL همان چیزی است که spec برای بازگشت می‌خواهد (توقف بدون از دست رفتن داده). پس downgrade کد اضافه‌ای برای بررسی لازم ندارد. هر migration در تراکنش خودش اجرا می‌شود (`transaction_per_migration=True` در `backend/migrations/env.py`). پس downgrade شکست‌خورده هیچ ستونی را نیمه‌کاره باریک نمی‌کند، و تست همین را بررسی می‌کند.

**Alternatives considered:** downgrade که مقدار بزرگ را به سقف قدیم ببُرد: داده را بی‌صدا عوض می‌کند، که spec رد کرده است.

### R4. سقف ورودی و قرارداد API

**Decision:** `Money = Annotated[Decimal, Field(max_digits=12, decimal_places=2, le=MAX_PRICE)]` با `MAX_PRICE = Decimal("1000000000.00")` در `listings/schemas.py`. بیش از سقف: ۴۲۲ `validation_error` با `loc` فیلد، مثل همه‌ی محدودیت‌های فیلد امروز.

**یافته (Pydantic نصب‌شده):** JSON schema حاصل `{"anyOf": [{"exclusiveMinimum": 0.0, "maximum": 1000000000.0, "type": "number"}, {"type": "string"}]}` است. یعنی سقف در `openapi.json` دیده می‌شود (FR-006). نوع خطا `less_than_equal` است، و `1000000000.00` پذیرفته می‌شود. شاخه‌ی `string` در قرارداد سقف ندارد. این امروز برای `exclusiveMinimum` هم همین است، و سرور در هر دو حالت آن را بررسی می‌کند.

**نکته:** `max_digits=12` به‌تنهایی تا ۹٬۹۹۹٬۹۹۹٬۹۹۹٫۹۹ را می‌پذیرد. `le` سقف واقعی است، و `max_digits` فقط جلوی ورودی بی‌معنا با رقم زیاد را می‌گیرد.

### R5. نگهبان جمع رزرو

**Decision:** تابع تازه در `bookings/rules.py` که اگر جمع از `MAX_STORED_AMOUNT = Decimal("999999999999.99")` (ظرفیت `NUMERIC(14,2)`) بیشتر شود، `Unprocessable("amount_too_large", …)` بیندازد. `create_booking` آن را پیش از ساختن ردیف صدا می‌زند.

**Rationale:** با سقف ورودی و `max_nights = 365` این خطا رخ نمی‌دهد (R2). ولی `max_nights` تنظیم است، و spec (FR-004) می‌گوید هیچ مبلغی نباید ۵۰۰ بدهد. بررسی پیش از درج پیام روشن می‌دهد و هیچ ردیفی نمی‌سازد. خود ستون همچنان نگهبان نهایی است (اصل I: کد برنامه فقط برای پیام روشن). کد تازه لازم است، چون هیچ فیلد ورودی‌ای اشتباه نیست.

**Alternatives considered:** گرفتن `22003` بعد از درج و تبدیل آن به ۴۲۲: بعد از رفت‌وبرگشت به پایگاه داده رخ می‌دهد، و `22003` ممکن است از ستون دیگری بیاید و پیام را گمراه کند.

### R6. جستجو

**یافته:** `search/repository.py` جمع را در SQL حساب می‌کند: `{nights} * l.price_per_night + l.cleaning_fee AS total_price`. نتیجه‌ی ضرب `numeric` در PostgreSQL پهنای نامحدود دارد، پس جستجو امروز هم سرریز نمی‌کند. فقط تست لازم است، تا FR-009 (جمع جستجو برابر جمع رزرو) ثابت شود.

### R1. کوئری‌هایی که برنامه واقعاً می‌فرستد

**روش:** API محلی روی `caravansara_bulk` اجرا شد. تنظیم `log_min_duration_statement = 0`، فقط برای همان پایگاه داده، همه‌ی دستورها را با زمان و پارامتر در لاگ PostgreSQL نوشت. ۲۴ درخواست نماینده فرستاده شد (ورود، جستجوی شهری و شعاعی با پارامترهای مختلف، صفحه‌ی آگهی و نظرها، سفرهای من، آگهی‌های من، رزروهای آگهی، شهرها). ۱۷۲ دستور ضبط شد، با متن و پارامترها در [data/003-captured-sql.json](data/003-captured-sql.json). تنظیم لاگ بعد از آن برداشته شد. jobهای worker و نوشتن رزرو از روی کد (`bookings/repository.py`) ساخته و جدا اندازه گرفته شدند.

**زمان پاسخ API (کل، یک اجرا) و زمان خود پایگاه داده:**

| درخواست | API | پایگاه داده |
| --- | --- | --- |

| جستجوی شعاعی لندن ۱ km، بدون تاریخ | ۲۸۱ ms | — |

| صفحه‌ی آگهی، نظرها (اول و عمیق)، سفرهای من، آگهی‌های من، شهرها، ورود | ۹–۵۳ ms | ≤ ۵ ms برای هر دستور |

**ضبط دوم (هنگام implement، T009):** `GET /search/filters` (`amenity_counts`)، رزرو با idempotency (تکرار همان کلید)، پرداخت، لغو و refresh در ضبط اول نبودند. همین روش روی کپی آزمایشی `caravansara_bulk_lab` تکرار شد، و ۶۱ دستور به [data/003-captured-sql.json](data/003-captured-sql.json) اضافه شد (`"capture": 2`). یافته‌ی تازه: **پنل فیلترها برای لندن با تاریخ کندترین درخواست برنامه است.** شمارش آن در اجرای سرد ۳٬۲۶۲ ms طول کشید و شمارش امکانات ۳۷۸ ms، چون همان anti-join جستجو را برای همه‌ی آگهی‌ها اجرا می‌کند. این‌ها در فهرست کوئری‌ها هستند (`filters_*`).

**نتیجه:** تقریباً همه‌ی هزینه در دو جاست: جستجو، و رزروهای آگهیِ میزبان. بقیه‌ی کوئری‌ها روی داده‌ی حجیم هم زیر ۵ میلی‌ثانیه‌اند و ایندکس تازه لازم ندارند.

### R2. روش اندازه‌گیری

**یافته:** یک اجرای تنها قابل اعتماد نیست. همان جستجو یک بار سرد ۳٬۰۱۱ میلی‌ثانیه طول کشید و بعد ۹۵۱ و ۹۰۱ میلی‌ثانیه.

**Decision:** هر کوئری اول یک بار برای گرم کردن cache اجرا می‌شود، بعد ۵ بار با `EXPLAIN (ANALYZE, BUFFERS)`، و میانه‌ی `Execution Time` ملاک است. حجم خواندن (buffers)، نوع دسترسی و نام ایندکس‌ها از نقشه‌ی اجرا (`FORMAT JSON`) خوانده می‌شوند. دستورهای نوشتنی (`UPDATE`، `INSERT`) در `BEGIN … ROLLBACK` اجرا می‌شوند، تا داده عوض نشود.

**Alternatives considered:** زمان API (با `curl`): کد Python و شبکه را هم می‌گیرد و نوسانش بیشتر است. میانگین به‌جای میانه: یک اجرای سرد آن را خراب می‌کند.

### R3. جستجو: کجا وقت می‌رود

**روش:** `EXPLAIN (ANALYZE, BUFFERS)` روی همان SQL ضبط‌شده (جستجوی شهری لندن با تاریخ)، گرم.

| بخش نقشه | زمان | دلیل |
| --- | --- | --- |
| Nested Loop Anti Join: ۴۸٬۱۶۸ بار `Index Scan using no_double_booking` | حدود ۸۷۰ ms (۰٫۰۱۸ ms × ۴۸ هزار) | `NOT EXISTS` برای هر آگهی لندن جدا در ایندکس رزرو می‌گردد |
| `Parallel Seq Scan on listings` | ۱۹۰–۲۴۳ ms | جدول ۳۹۰ مگابایت است (حدود ۲ ردیف در هر صفحه، به‌خاطر متن توضیحات). `listings_city_idx` به کار نمی‌آید، چون لندن نیمی از جدول است |
| `Sort` (external merge، ۳٫۲ مگابایت روی دیسک) | حدود ۳۵ ms | مرتب‌سازی همه‌ی ۴۸ هزار ردیف |
| `WindowAgg` (`count(*) OVER ()`) | — | `total` در پاسخ API همه‌ی ردیف‌های منطبق را لازم دارد، پس `LIMIT 20` زود متوقف نمی‌شود |

**آزمایش‌ها** (روی کپی جدای `caravansara_bulk_lab`، در تراکنش‌هایی که rollback شدند):

| آزمایش | نتیجه |
| --- | --- |
| ایندکس GiST روی `stay` (partial، همان وضعیت‌های `EXCLUDE`) | برنامه‌ریز خودش آن را انتخاب نکرد (همان nested loop، ۱٬۳۵۵ ms) |
| همان، با `enable_nestloop = off` (فقط برای دیدن نقشه‌ی دیگر) | `Bitmap Index Scan` روی ایندکس تازه ۷٬۲۳۸ رزرو منطبق را در **حدود ۹۵ ms** پیدا کرد، و anti-join به hash رسید. ولی خواندن `listings` در همان اجرا (سرد) ۹۲۸ ms بود |

**نتیجه‌ها برای طرح:**
1. هزینه‌ی اصلی، پرس‌وجوی جدا برای هر آگهی است. اگر رزروهای منطبق یک بار پیدا شوند (ایندکس روی `stay`، و نوشتن کوئری به شکلی که برنامه‌ریز hash را انتخاب کند، با همان نتیجه)، این بخش از حدود ۸۷۰ به حدود ۱۰۰ میلی‌ثانیه می‌رسد.
2. خواندن ۳۹۰ مگابایت `listings` به‌تنهایی از هدف ۵۰ میلی‌ثانیه بیشتر است. یک ایندکس covering باریک برای ستون‌های جستجو (`city_id`, `is_active`, `max_guests`, ترتیب امتیاز، قیمت) می‌تواند خواندن جدول را با index-only scan جایگزین کند. باید اندازه گرفته شود.
3. جستجوی شهری لندن با تاریخ احتمالاً حتی بعد از این‌ها به ۵۰ میلی‌ثانیه نمی‌رسد، چون `total` شمارش ۴۵ هزار ردیف را لازم دارد و تغییر آن رفتار API را عوض می‌کند (FR-009). اگر نرسید، طبق FR-005 با عدد و دلیل ثبت می‌شود.

### R4. رزروهای آگهیِ میزبان

**یافته:** روی `bookings.listing_id` هیچ ایندکس B-tree وجود ندارد. ایندکس GiST قید `no_double_booking` فقط وضعیت‌های `pending`، `confirmed` و `completed` را دارد (`WHERE status = ANY (...)`)، پس شمارش و صفحه‌ی همه‌ی رزروهای یک آگهی (با `cancelled` و `expired`) کل جدول را می‌خواند: ۲۶۷ ms برای شمارش و ۱۳۲ ms برای صفحه.

**Decision (برای اندازه‌گیری):** B-tree روی `bookings (listing_id, check_in, id)`، هم‌ترتیب با `ORDER BY check_in, id` این کوئری. انتظار: هر دو کوئری زیر ۵ ms.

### R5. jobهای worker

| job | زمان (میانه‌ی ۳ اجرای گرم) | نقشه |
| --- | --- | --- |
| `expire_overdue_holds` | ۳۲ ms | `bookings_pending_hold_idx`، ۴۸۹ ردیف؛ خوب |
| `complete_finished_stays` (هر دقیقه) | **۱٬۴۴۰ ms**، با صفر ردیف نتیجه | `Seq Scan on bookings` روی ۳ میلیون ردیف، و محاسبه‌ی منطقه‌ی زمانی برای هر ۴۶۶ هزار رزرو `confirmed` |

**آزمایش:** ایندکس partial روی `bookings (check_out) WHERE status = 'confirmed'`، به‌اضافه‌ی کران امن `b.check_out <= ((now() AT TIME ZONE 'UTC') + interval '14 hours')::date` در کوئری. کران امن است، چون هیچ منطقه‌ی زمانی‌ای بیش از ۱۴+ ساعت از UTC جلوتر نیست، پس اقامتی که پایانش به وقت شهر گذشته، `check_out`ش حداکثر همان تاریخ است.

| حالت | زمان | ردیف‌ها، اگر `now()` ۳۰ روز جلوتر باشد |
| --- | --- | --- |
| کوئری فعلی | ۱٬۴۴۰ ms | ۴۳٬۷۴۲ |
| با کران و ایندکس partial | حدود ۴۴۰ ms | ۴۳٬۷۴۲ (یکسان) |

۳۰۰ میلی‌ثانیه‌ی باقی‌مانده hash join با کل `listings` است. ۳٬۲۷۸ رزرو با nested loop روی `listings_pkey` سریع‌تر خوانده می‌شوند، و این در پیاده‌سازی تنظیم و اندازه‌گیری می‌شود. تست‌های فعلی job (تغییر ساعت تابستانی، منطقه‌ی زمانی شهر) ثابت می‌کنند که کران رفتار را عوض نکرده است.

### R6. نوشتن

**روش:** ۱٬۰۰۰ رزرو تازه (`INSERT … SELECT generate_series`) در یک تراکنش با rollback، ۴ اجرا.

**خط پایه:** میانه‌ی **حدود ۲۴۰ ms** برای ۱٬۰۰۰ رزرو (۰٫۲۴ ms برای هر رزرو)، با ۶ ایندکس فعلی `bookings`. هر ایندکس تازه با همین آزمون سنجیده می‌شود.

### R7. ایندکس‌های فعلی و استفاده‌ی آن‌ها

**روش:** `pg_stat_user_indexes` روی `caravansara_bulk` بعد از بارگذاری و ترافیک R1، و `pg_get_indexdef` / `pg_get_constraintdef`.

| ایندکس | حجم | پشت قید؟ | تصمیم اولیه |
| --- | --- | --- | --- |
| `no_double_booking` (GiST، partial) | ۲۰۹ MB | `EXCLUDE` (اصل I) | می‌ماند |
| `bookings_idempotency_key_key` | ۱۱۹ MB | `UNIQUE` | می‌ماند. Hash جایگزین نمی‌شود: PostgreSQL می‌گوید `access method "hash" does not support unique indexes` (روی 16.4 آزموده شد) |
| `bookings_id_listing_id_guest_id_key` | ۱۱۷ MB | `UNIQUE`، هدف کلید خارجی سه‌ستونه‌ی `reviews` | می‌ماند |
| `bookings_guest_idx` | ۳۶ MB | نه | می‌ماند (سفرهای من، ≤ ۱ ms) |
| `listing_amenities_amenity_idx` | ۹ MB | نه؛ ولی کلید خارجی `amenity_id` آن را برای حذف یک امکان لازم دارد | ۰ استفاده؛ بررسی حذف با اندازه‌گیری فیلتر امکانات |
| `auth_attempts_lookup_idx` | ۸ kB | نه | در داده‌ی حجیم خالی است؛ BRIN فقط با جدول بزرگ معنا دارد |
| بقیه | کوچک | بیشترشان پشت `PRIMARY KEY` یا `UNIQUE` | می‌مانند |

ایندکس‌هایی که در R7 «۰ استفاده» دارند و پشت هیچ قیدی نیستند، بعد از اجرای کامل فهرست کوئری‌ها دوباره بررسی می‌شوند (FR-007).

### R8. نوع‌های ایندکس که فهرست می‌خواهد

| نوع | کوئری واقعی که به آن نیاز دارد | تصمیم |
| --- | --- | --- |
| B-tree | رزروهای آگهی (R4)، job پایان اقامت (R5) | اندازه‌گیری و احتمالاً افزودن |
| Partial | job پایان اقامت (`status = 'confirmed'`)، GiST روی `stay` | اندازه‌گیری |
| Covering (`INCLUDE`) | ستون‌های کارت جستجو، تا جدول ۳۹۰ مگابایتی خوانده نشود (R3) | اندازه‌گیری |
| GiST | `stay` برای جستجوی تاریخ (R3)؛ `public_location` (موجود) | اندازه‌گیری |
| SP-GiST | `public_location` در جستجوی شعاعی | مقایسه با GiST فعلی روی ۱، ۵ و ۲۰ کیلومتر (FR-011) |
| GIN با `pg_trgm` | پیشنهاد نام شهر: جدول ۹ ردیف دارد، و جستجوی فعلی پیشوندی (`ILIKE 'Lon%'`) در ۲٫۷ ms است | ساخته نمی‌شود. قابلیت جستجوی وسط کلمه امروز وجود ندارد (Assumptions) |
| BRIN | `auth_attempts`: در داده‌ی حجیم خالی است، و در کار عادی کوچک می‌ماند | ساخته نمی‌شود، با همین دلیل |
| Hash | `idempotency_key` | ساخته نمی‌شود: unique را پشتیبانی نمی‌کند (R7) |

### R9. `pg_stat_statements` و Grafana

| واقعیت | چطور سنجیده شد |
| --- | --- |
| بسته در تصویر `postgis/postgis:16-3.4` هست (`pg_available_extensions`) ولی بارگذاری نشده (`shared_preload_libraries` خالی) | `SHOW`، روی پایگاه داده‌ی compose |
| `CREATE EXTENSION pg_stat_statements` بدون preload موفق است، ولی خواندن آن خطا می‌دهد: `must be loaded via shared_preload_libraries` | روی کپی آزمایشی |
| postgres-exporter v0.17.1 کالکتور `--collector.stat_statements` دارد، که پیش‌فرض خاموش است | `--help` همان تصویر |

**Decision:**
- سرویس `db` در compose با `-c shared_preload_libraries=pg_stat_statements` اجرا می‌شود. یک بار restart لازم است.
- migration `0003` دستور `CREATE EXTENSION IF NOT EXISTS pg_stat_statements` را دارد. این روی پایگاه داده‌ی تست (بدون preload) هم موفق است، چون خواندن نمی‌شود.
- exporter با `--collector.stat_statements` اجرا می‌شود.
- یک پنل «کوئری‌های پرهزینه» به داشبورد اضافه می‌شود.

نام دقیق متریک‌های exporter در پیاده‌سازی از `/metrics` خودش خوانده شد (`observability/postgres-exporter/metrics.txt`)، و `tests/test_monitoring_config.py` همان را بررسی می‌کند. پنج متریک هست (`pg_stat_statements_calls_total`، `_seconds_total`، `_rows_total`، `_block_read_seconds_total`، `_block_write_seconds_total`)، با برچسب‌های `datname`، `queryid` و `user`. v0.17.1 هیچ گزینه‌ای برای فرستادن متن کوئری ندارد (`--help` همان تصویر). پس پنل `queryid` را نشان می‌دهد، و توضیح پنل می‌گوید متن کوئری با `SELECT query FROM pg_stat_statements WHERE queryid = …` پیدا می‌شود. هر سه عبارت پنل روی Prometheus واقعی ۱۰ سری برگرداندند، و Grafana پنل را بارگذاری کرد.

### R10. فهرست کوئری‌ها و ابزار اندازه‌گیری

**Decision:** فهرست کوئری‌ها فایل‌های SQL در `db/bulk/queries/` است، همان SQL ضبط‌شده در R1، با پارامترهای نماینده‌ای که از خود داده انتخاب می‌شوند (مثل پررزروترین آگهی و پرسفرترین مهمان). یک فایل `catalog.json` هر کوئری را به تابع کد مربوط (`module:function`) وصل می‌کند. فرمان `caravansara measure-queries` در بسته‌ی ابزار `caravansara.devdata` فهرست را با روش R2 اجرا می‌کند و جدول Markdown و JSON می‌نویسد.

**Rationale:** طبق اصل II (نسخه‌ی 1.1.0)، بسته‌ی ابزار فقط `core` را import می‌کند، پس نمی‌تواند repository ماژول‌ها را صدا بزند. SQL در فایل‌ها می‌ماند، و دو تست جلوی کهنه شدنش را می‌گیرند. تست اول: هر تابع repository و job یا در فهرست هست یا با دلیل کنار گذاشته شده است (SC-001). تست دوم: هر SQL فهرست روی پایگاه داده‌ی تست با `EXPLAIN` (بدون `ANALYZE`) اجرا می‌شود، پس نام ستون یا جدول اشتباه پیدا می‌شود.

**Alternatives considered:**
- ابزار که کد واقعی برنامه را با hook روی SQLAlchemy اجرا کند: SQL هرگز کهنه نمی‌شود، ولی بسته‌ی ابزار باید ماژول‌های کسب‌وکار را import کند، که اصل II رد می‌کند.
- فقط `pg_stat_statements`: کوئری‌های پرهزینه‌ی بار واقعی را نشان می‌دهد، ولی عدد پیش و پس روی همان پارامترها نمی‌دهد.

## 004. تأیید آگهی توسط مدیر سیستم (admin)

هر بند تصمیم، دلیل و گزینه‌های ردشده را دارد، و زیر «چطور سنجیده شد» می‌گوید فرض با کدام منبع واقعی بررسی شد (constitution، Development Workflow).

### R1. حساب admin: همان جدول `users` با ستون `kind`

- **Decision**: حساب admin یک ردیف در `users` است با `kind = 'admin'` (enum تازه‌ی `account_kind`: `member`, `admin`؛ پیش‌فرض `member`) و ستون `disabled_at`. admin فقط از `POST /api/v1/admin/auth/login` وارد می‌شود و توکنی با `type: "admin"` می‌گیرد. ورود عادی (`/auth/login`) حساب admin را با همان خطای `invalid_credentials` رد می‌کند.
- **Rationale**:
  - constitution اصل I می‌گوید یکتایی ایمیل را پایگاه داده نگه می‌دارد. با یک جدول، ایندکس یکتای فعلی روی `lower(email)` خودش جلوی ایمیل تکراری بین کاربر عادی و admin را می‌گیرد، حتی وقتی ثبت‌نام و فرمان هم‌زمان اجرا شوند (FR-012، US4/AC2).
  - جدا بودن نوع حساب با نوع توکن تضمین می‌شود: `current_user_id` فقط `type: "access"` را می‌پذیرد، پس توکن admin به هیچ endpoint میزبان یا مهمان نمی‌رسد. admin با ساختار سیستم نمی‌تواند آگهی ثبت کند یا رزرو کند (FR-007)، نه با یک if در هر endpoint.
  - هیچ فیلد ورودی عمومی `kind` ندارد، پس ثبت‌نام و ویرایش پروفایل هرگز admin نمی‌سازند (SC-005).
- **Alternatives considered**:
  - جدول جدای `admins`: یکتایی ایمیل بین دو جدول را پایگاه داده نمی‌تواند با constraint ساده نگه دارد. trigger بدون قفل در دو تراکنش هم‌زمان هر دو را قبول می‌کند. ردیف admin همچنین سیستم refresh token و محدودیت تلاش ورود را تکرار می‌کرد.
  - نقش اضافه روی کاربر عادی (`is_admin`): مالک پروژه رد کرد (Clarifications: مدیر نوع جدایی است و کاربر عادی هرگز مدیر نمی‌شود).
- **چطور سنجیده شد**:
  - `backend/src/caravansara/identity/models.py`: `users` فقط `email, password_hash, full_name, avatar_url, created_at` دارد و ستون نقش ندارد.
  - `migrations/versions/0001_initial_schema.py`: ایندکس یکتا روی `lower(email)` است.
  - `core/security.py`: `decode_access_token` هر `type` جز `"access"` را `invalid_token` می‌کند.
  - `identity/schemas.py`: `RegisterIn` و `ProfileUpdate` فیلد نقش ندارند، و Pydantic فیلد اضافه را نادیده می‌گیرد.

### R2. نشست admin: فقط access token کوتاه، و بررسی حساب در هر درخواست

- **Decision**:
  - ورود admin فقط access token می‌دهد (عمرش `admin_token_minutes`، پیش‌فرض 15)، بدون refresh token.
  - هر endpoint admin ردیف admin را با کلید اصلی می‌خواند. اگر `kind <> 'admin'` یا `disabled_at` پر باشد، `401 invalid_token` برمی‌گردد.
- **Rationale**:
  - FR-012 می‌گوید از کار انداختن «حداکثر تا پایان عمر نشست» اثر کند. خواندن ردیف در هر درخواست آن را بی‌درنگ می‌کند.
  - این خواندن با کلید اصلی است و هزینه‌اش ناچیز است، چون admin‌ها چند نفرند و درخواست‌هایشان کم است.
  - بدون refresh token، چرخش و کشف استفاده‌ی دوباره برای admin لازم نیست. هر ۱۵ دقیقه ورود دوباره برای ابزار بازبینی پذیرفتنی است.
- **Alternatives considered**: refresh token مثل کاربر عادی. کد و جدول بیشتری می‌خواست و سودی برای چند admin نداشت.
- **چطور سنجیده شد**: `core/config.py` (`access_token_minutes: int = 15`) و `identity/service.py` (`_issue_tokens` توکن refresh را در `refresh_tokens` با FK به `users` می‌نویسد).

### R3. محدودیت تلاش ورود admin

- **Decision**: ورود admin همان `auth_attempts` و همان سقف‌های `login_*` را به کار می‌برد، با `action = 'admin_login'`. شمارنده‌ی `caravansara_rate_limited_total` برچسب `admin_login` می‌گیرد.
- **Rationale**: پنل admin از اینترنت در دسترس است (constitution 1.3.0)، پس حدس رمز باید همان‌قدر سخت باشد که برای کاربر عادی. action جدا یعنی تلاش‌های ورود عادی سقف admin را پر نمی‌کنند، و برعکس.
- **Alternatives considered**: سقف سخت‌تر برای admin. هنوز عددی از مانیتورینگ ندارد. اگر لازم شد، فقط یک تنظیم است.
- **چطور سنجیده شد**: `identity/service.py` (`login` با `count_attempts(... "login" ...)`)، و `core/metrics.py` (برچسب‌های `RATE_LIMITED` از پیش ساخته می‌شوند).

### R4. ماژول تازه‌ی `moderation`

- **Decision**:
  - ماژول `caravansara.moderation` endpointهای admin را دارد: ورود، صف، جزئیات، تأیید و رد. جدول `admin_address_views` هم مال اوست.
  - وضعیت بازبینی آگهی و سابقه‌ی آن (`listing_review_events`) مال ماژول `listings` است، چون میزبان هم آن را عوض می‌کند (ساختن، ویرایش، ارسال دوباره).
  - `moderation` فقط از راه `listings.service` و `identity.service` کار می‌کند.
  - یک قرارداد import-linter تازه اضافه می‌شود، و `moderation` به فهرست ممنوعه‌ی قراردادهای دیگر می‌رود.
- **Rationale**: constitution اصل II برای ماژول تازه قرارداد می‌خواهد. وضعیت آگهی و قاعده‌ی «کدام ویرایش تأیید می‌خواهد» یک‌جا، کنار ویرایش آگهی، می‌ماند. پس همان قفل ردیف ویرایش و تصمیم را پشت سر هم اجرا می‌کند (R6).
- **Alternatives considered**:
  - endpointهای admin در `listings/router.py`: کار admin و میزبان در یک ماژول قاطی می‌شد.
  - جدول سابقه در `moderation`: ارسال دوباره‌ی میزبان (در `listings`) آن‌وقت باید `moderation` را صدا می‌زد، و چون `moderation` هم `listings` را صدا می‌زند، import دوطرفه پیش می‌آمد.
- **چطور سنجیده شد**: `backend/pyproject.toml`: قراردادهای `forbidden` برای هر ماژول، `allow_indirect_imports = true`، و قرارداد `core` با فهرست همه‌ی ماژول‌ها.

### R5. وضعیت بازبینی روی `listings`، بدون بازنویسی جدول

- **Decision**: migration `0006` این‌ها را اضافه می‌کند:
  - `review_status listing_review_status NOT NULL DEFAULT 'approved'`، و بعد `SET DEFAULT 'pending'`.
  - `submitted_at timestamptz`، بدون پیش‌فرض؛ سپس `SET DEFAULT now()`.
  - `rejection_reason text`.
  - `review_version integer NOT NULL DEFAULT 0`.
  - دو CHECK و یک ایندکس جزئی برای صف.
- **Rationale**:
  - ستون با پیش‌فرض ثابت در PostgreSQL 16 فقط metadata است. همه‌ی ردیف‌های موجود بی‌درنگ `approved` می‌شوند (FR-013، US5)، بدون UPDATE روی ۱۰۰ هزار ردیف و بدون قفل طولانی.
  - ردیف‌های تازه با پیش‌فرض بعدی، `pending`، ساخته می‌شوند (FR-001)، حتی اگر کدی آن را فراموش کند.
  - `now()` اگر هنگام ADD COLUMN پیش‌فرض باشد جدول را بازنویسی می‌کند، پس جدا گذاشته می‌شود.
- **Alternatives considered**: ستون nullable و یک UPDATE روی همه. ۱۰۰ هزار ردیف را بازنویسی می‌کرد و جدول را bloat می‌کرد؛ در ۰۰۳ دیدیم این اندازه‌گیری را خراب می‌کند.
- **چطور سنجیده شد**: روی `caravansara_bulk` (۱۰۰٬۰۰۰ آگهی، ۹۶٬۹۶۱ فعال)، داخل `BEGIN … ROLLBACK`:
  - `pg_relation_filenode('listings')` پیش و پس از ADD COLUMN هر دو 55000 ماند، یعنی بازنویسی نشد.
  - ADD COLUMN با پیش‌فرض: 11 ms. CHECK `review_status <> 'pending' OR submitted_at IS NOT NULL`: 34 ms. ایندکس `(submitted_at, id) WHERE review_status = 'pending'`: 48 ms.
  - همان ADD COLUMN روی `users`: 1 ms.

### R6. تصمیم‌های هم‌زمان: UPDATE شرطی با `review_version`

- **Decision**:
  - هر ویرایش توصیفی (FR-009) `review_version` را یکی بالا می‌برد. جزئیات admin آن را برمی‌گرداند، و تأیید یا رد همان را در بدنه می‌فرستد.
  - تصمیم این است: `UPDATE listings SET … WHERE id = :id AND review_status = 'pending' AND review_version = :v RETURNING …`. اگر هیچ ردیفی عوض نشود:
    - وضعیت دیگر `pending` نیست: `409 listing_not_pending`.
    - نسخه عوض شده: `409 listing_changed`.
  - ردیف سابقه در همان تراکنش نوشته می‌شود.
- **Rationale**:
  - constitution اصل I می‌گوید تغییر وضعیتی که می‌تواند مسابقه شود UPDATE شرطی است و شمار ردیف‌ها تصمیم می‌گیرد.
  - دو admin هم‌زمان: فقط یکی برنده می‌شود (FR-006).
  - میزبانی که هم‌زمان ویرایش می‌کند: ویرایش با `SELECT … FOR UPDATE` (کد امروز) قفل می‌گیرد و نسخه را بالا می‌برد. تأییدی که نسخه‌ی قدیمی را دیده رد می‌شود، پس هیچ نسخه‌ای بدون بازبینی عمومی نمی‌شود (Edge Cases).
- **Alternatives considered**: مقایسه‌ی `updated_at`. جدول این ستون را ندارد، و هر ویرایش غیرتوصیفی (قیمت) هم آن را عوض می‌کرد و تأیید را بی‌دلیل رد می‌کرد.
- **چطور سنجیده شد**: `listings/service.py` (`_get_owned` با `for_update=True` در همه‌ی ویرایش‌ها، از جمله عکس و امکانات)، و الگوی `bookings/repository.py` برای UPDATE شرطی پرداخت و لغو.

### R7. کدام ویرایش توصیفی است: مقایسه‌ی مقدار

- **Decision**: `listings.service` پیش از نوشتن، مقدار تازه را با مقدار فعلی مقایسه می‌کند:
  - فیلدهای آگهی: `title, description, property_type, city_id, neighborhood, address, latitude, longitude`. مختصات با همان گرد کردن ۶ رقمی که ذخیره می‌شود مقایسه می‌شوند.
  - امکانات: مجموعه‌ی تازه با مجموعه‌ی فعلی.
  - افزودن عکس: همیشه توصیفی است.
  - `caption` یا `room_tag` عکس: اگر مقدار عوض شود.
  - بقیه‌ی فیلدها (FR-010) وضعیت را عوض نمی‌کنند.
- **Rationale**: US3/AC5 می‌گوید فرستادن همان مقدار تغییر نیست. فرانت‌اند معمولاً کل فرم را می‌فرستد، و بدون مقایسه هر ذخیره‌ی قیمت آگهی را پنهان می‌کرد.
- **Alternatives considered**: هر کلیدی که در PATCH آمده. با US3/AC5 نمی‌خواند.
- **چطور سنجیده شد**: `listings/schemas.py` و `listings/service.py`:
  - `update_listing` با `model_dump(exclude_unset=True)` و `setattr` کار می‌کند.
  - `_set_location` مختصات را با `f"{lat:.6f}"` گرد می‌کند.
  - `set_amenities` کل مجموعه را جایگزین می‌کند.
  - `update_photo` فقط `caption` و `room_tag` را عوض می‌کند.

### R8. عمومی بودن: یک قاعده در سه جا

- **Decision**: «عمومی» یعنی `is_active AND review_status = 'approved'`. این قاعده سه جا اجرا می‌شود:
  - **جستجو و شمارش فیلترها:** `search/repository.py::_where` و `db/search_query.sql` شرط `l.review_status = 'approved'` را کنار `l.is_active` می‌گیرند.
  - **صفحه‌ی آگهی و نظرها:** `listings.service.get_listing` و `reviews.service.listing_reviews`. آگهی غیرعمومی فقط برای میزبانش و مهمانی که در آن رزرو زنده دارد دیده می‌شود (FR-019)؛ برای بقیه همان `404 not_found` است. `GET /listings/{id}/reviews` بیننده‌ی اختیاری می‌گیرد. امروز نظرهای آگهی غیرفعال برای همه دیده می‌شوند، در حالی که صفحه‌اش 404 است؛ FR-002 این ناهمخوانی را می‌بندد.
  - **رزرو تازه:** `bookings.service.create_booking` به‌جای `info.is_active` شرط `info.is_public` را بررسی می‌کند و همان `404` امروز را می‌دهد.
- **«رزرو زنده»:** وضعیت `pending` (با مهلت نگه‌داشتِ نگذشته)، `confirmed` یا `completed`. لغوشده و منقضی حساب نمی‌شوند (Edge Cases).
  - این بررسی یک `EXISTS` با SQL ساده روی جدول `bookings`، در `listings/repository.py`، است؛ همان کاری که `search/repository.py` امروز می‌کند.
  - اگر `listings` به‌جایش `bookings.service` را صدا بزند، import دوری می‌سازد، چون `bookings.service` در بالای فایل `listings.service` را import می‌کند.
- **Rationale**: FR-002 و SC-001 هر مسیر عمومی را می‌خواهند. مسیرهای امروز همین چهار تا هستند: جستجو، شمارش، صفحه، رزرو، به‌علاوه‌ی نظرها.
- **Alternatives considered**: ستون generated `is_public` با ساختن دوباره‌ی ایندکس‌های جزئی روی آن. ایندکس‌های ۱۰۰ هزار ردیفی را دوباره می‌ساخت، بی‌آنکه سودی اندازه‌گیری شود (R9).
- **چطور سنجیده شد**:
  - `grep is_active`: در `search/repository.py:50`، `listings/service.py::get_listing`، `bookings/service.py:72` و `db/search_query.sql`.
  - `reviews/service.py:66`: `listing_reviews` فقط `get_listing_info` را صدا می‌زند و `is_active` را نمی‌بیند.
  - `bookings/service.py:24`: `bookings.service` در بالای فایل `listings.service` را import می‌کند.

### R9. سرعت جستجو با شرط تازه (SC-008)

- **Decision**: ایندکس‌های جزئی `WHERE is_active` (`listings_city_idx`، `listings_public_location_idx`) دست نمی‌خورند. شرط `review_status` فقط یک Filter روی همان ردیف‌هاست.
- **Rationale**: تقریباً همه‌ی آگهی‌ها تأییدشده‌اند، پس شرط تازه ردیفی کم نمی‌کند که ایندکس تازه را توجیه کند. constitution اصل VII ایندکس بی‌اندازه‌گیری را نمی‌پذیرد.
- **Alternatives considered**: ایندکس‌های جزئی با `WHERE is_active AND review_status = 'approved'`. پلن عوض نمی‌شد، اما ساختن دوباره و migration بیشتری می‌خواست.
- **چطور سنجیده شد**: روی `caravansara_bulk`، داخل `BEGIN … ROLLBACK` با ستون آزمایشی و `ANALYZE`، شمارش لندن با `max_guests >= 2`:
  - بدون شرط: `Bitmap Index Scan on listings_city_idx`، 21.7 ms.
  - با شرط: همان پلن، Filter `rs = 'approved'`، 17.5 ms (اجرای دوم، کش گرم).
  - اندازه‌گیری کامل SC-008 با `caravansara measure-queries` در quickstart آمده است.

### R10. مانیتورینگ صف (FR-016)

- **Decision**:
  - **شمارنده:** `caravansara_listing_review_events_total{event}` با `submitted`، `approved` و `rejected`، در هر API که تصمیم یا ارسال را انجام می‌دهد.
  - **دو gauge:** `caravansara_listing_review_queue` (تعداد در انتظار) و `caravansara_listing_review_oldest_wait_seconds`. worker آن‌ها را در هر اجرا از پایگاه داده می‌خواند (`count(*)`, `min(submitted_at)` روی ایندکس جزئی صف).
  - Grafana یک ردیف تازه می‌گیرد.
- **Rationale**: هر copy از API شمارش خودش را دارد (`core/metrics.py`). اگر هر API عدد صف را بفرستد، Prometheus اعداد تکراری یا کهنه می‌دید. worker یک process است و هر دقیقه اجرا می‌شود، پس عدد صف دقیقاً یک منبع دارد.
- **Alternatives considered**: postgres-exporter با کوئری سفارشی. تنظیم بیشتر و جای دیگری برای منطق می‌خواست.
- **چطور سنجیده شد**: `core/metrics.py` (توضیح بالای فایل درباره‌ی شمارش جدا در هر process)، `jobs/runner.py` (`run_once` و `JobResult`)، و `observability/grafana/dashboards/caravansara.json`.

### R11. سابقه و دیدن نشانی دقیق

- **Decision**:
  - **`listing_review_events`:** فقط اضافه می‌شود (trigger هر UPDATE و DELETE را رد می‌کند). action آن `submitted`، `edited`، `resubmitted`، `approved` یا `rejected` است، با انجام‌دهنده (FK به `users`، میزبان یا admin)، `review_version` و دلیل برای رد. نوع `edited` ویرایشی است که آگهی تأییدشده را به صف برگرداند.
  - **`admin_address_views`:** یک ردیف برای هر `GET /admin/listings/{id}` (admin، آگهی، زمان)، در همان تراکنشی که پاسخ را می‌سازد (FR-018، SC-009).
- **Rationale**: FR-015 انجام‌دهنده و زمان را می‌خواهد. trigger این تضمین را به پایگاه داده می‌دهد، که اصل I برای قاعده‌های مهم ترجیح می‌دهد. نوشتن ردیف دیدن در همان تراکنش یعنی پاسخی بدون ثبت وجود ندارد.
- **Alternatives considered**: ثبت دیدن نشانی در log. constitution اصل V نشانی را در log ممنوع می‌کند، و log برای سابقه‌ی ماندگار ساخته نشده است.
- **چطور سنجیده شد**: constitution 1.3.0 اصل V («which admin, which listing, when»)، و trigger `reviews_rating_sync` در `0001_initial_schema.py` به‌عنوان الگوی trigger در این پروژه.

### R12. endpointهای admin روی زیردامنه‌ی خودشان

- **Decision**: endpointهای admin زیر `/api/v1/admin/*` در همان برنامه‌ی FastAPI هستند. تنظیم اختیاری `CARAVANSARA_ADMIN_HOST` کارشان را محدود می‌کند:
  - وقتی پر است، این endpointها برای `Host` دیگری `404 not_found` می‌دهند.
  - در development خالی است و همه‌جا کار می‌کنند.
  - همه در `openapi.json` و Swagger هستند.
- **Rationale**:
  - constitution 1.3.0 می‌گوید ابزار admin فقط روی زیردامنه‌ی خودش از اینترنت در دسترس است. این تنظیم آن را برای API هم اجراپذیر می‌کند، با چند خط و یک تست.
  - اصل III می‌خواهد Swagger همه‌ی endpointها را نشان دهد. spec هم تا ساخته شدن پنل بازبینی را از راه Swagger می‌خواهد.
  - محافظت اصلی ورود admin است؛ نشانی پنهان فقط دسترس را کم می‌کند.
- **Alternatives considered**: سرویس API جدا برای admin. constitution اصل II جدا کردن سرویس را بدون عدد مانیتورینگ نمی‌پذیرد.
- **چطور سنجیده شد**: `main.py` (همه‌ی routerها زیر `APIRouter(prefix=API_PREFIX)` با `docs_url="/docs"`)، و constitution 1.3.0 اصل V.

### R13. پاسخ به غیر admin (FR-020)

- **Decision**: درخواست به endpoint admin بدون توکن، با توکن کاربر عادی، یا با حساب admin از کار افتاده `401` با `invalid_token` یا `unauthorized` می‌گیرد، مثل امروز. هیچ داده‌ای از آگهی، و هیچ `404` یا `409` دیگری، پیش از احراز admin برنمی‌گردد.
- **Rationale**: ترتیب dependencyها تضمین می‌کند که وجود یا وضعیت آگهی فقط به admin گفته شود.
- **Alternatives considered**: `403 admin_only`. نوع حساب را لو می‌داد، و سودی برای کاربر عادی نداشت.
- **چطور سنجیده شد**: `core/errors.py` (`Unauthorized` با `code` پیش‌فرض `unauthorized`)، و `core/security.py` (`invalid_token`).

### R14. فرمان‌های سرور

- **Decision**:
  - `caravansara create-admin --email E --name N` رمز را از `CARAVANSARA_ADMIN_PASSWORD` می‌خواند، یا اگر خالی باشد دو بار با `getpass` می‌پرسد. قاعده‌ی رمز همان ثبت‌نام است: ۸ تا ۱۲۸ نویسه.
  - `caravansara disable-admin --email E` حساب را از کار می‌اندازد.
  - هر دو کد خروج 1 و پیام روشن دارند: ایمیلی که حساب دارد، ایمیلی که admin نیست، یا حسابی که از قبل از کار افتاده.
- **Rationale**: رمز در آرگومان فرمان در تاریخچه‌ی shell و `ps` دیده می‌شود. متغیر محیطی برای اسکریپت و e2e است، و `getpass` برای انسان.
- **Alternatives considered**: `--password`. به همان دلیل رد شد.
- **چطور سنجیده شد**: `cli.py` (`build_parser` با `sub.add_parser`، و الگوی خطای `BulkRefused`)، و `identity/schemas.py` (`password: str = Field(min_length=8, max_length=128)`).

### R15. داده‌ی دمو و داده‌ی حجیم (FR-014)

- **Decision**:
  - **دمو:** `db/demo/build_demo_seed.py` پس از INSERTها `UPDATE listings SET review_status = 'approved'` می‌نویسد. بعد دو حالت مرزی تازه می‌سازد:
    - `pending_listing`: در انتظار، با `submitted_at`.
    - `rejected_listing`: رد شده با دلیل.
  - همان builder یک حساب `admin@example.com` با `kind = 'admin'` و رمز همه‌ی حساب‌های دمو می‌سازد، و ردیف‌های سابقه را هم.
  - `seed-demo` در `environment = production` اجرا نمی‌شود.
  - **حجیم:** `devdata/bulk.py` ستون `review_status` را با `approved` در COPY می‌نویسد.
- **Rationale**:
  - با پیش‌فرض `pending` (R5)، INSERTهای امروز دمو آگهی‌ها را پنهان می‌کردند، و SC-002 می‌شکست.
  - آگهی ردشده بدون admin سابقه‌ی درستی نمی‌داشت (FR-015).
  - دمو امروز هم رمز شناخته‌شده دارد. پس جای درستش production نیست، و یک حساب admin با رمز شناخته‌شده این را جدی‌تر می‌کند.
  - فرمان `seed-demo` خودش روی سرور اجرا می‌شود، پس با اصل V («only by a command run on the server») می‌خواند.
- **Alternatives considered**: ردیف سابقه‌ی بی‌انجام‌دهنده برای دمو. FR-015 را می‌شکست.
- **چطور سنجیده شد**:
  - `db/seed_demo.sql:2088`: INSERT ستون `review_status` ندارد.
  - `build_demo_seed.py::write`: حالت `inactive_listing` با یک UPDATE پس از INSERT ساخته می‌شود.
  - `.cache/insideairbnb/` موجود است، پس builder بدون شبکه دوباره اجرا می‌شود و برای همان `--seed` خروجی یکسان می‌دهد.
  - `devdata/bulk.py:21-26`: `COLUMNS["listings"]`.
  - `cli.py::seed_demo`: هیچ بررسی production ندارد.

### R16. بازگرداندن migration

- **Decision**: `0006` downgrade:
  - آگهی‌های تأییدنشده را `is_active = false` می‌کند، تا هیچ آگهی بازبینی‌نشده‌ای با حذف ستون عمومی نشود.
  - حساب‌های admin را حذف می‌کند، چون بدون ستون `kind` به کاربر عادی با رمز تبدیل می‌شدند و می‌توانستند رزرو کنند.
  - سپس جدول‌ها، ستون‌ها و typeها را برمی‌دارد.
- **Rationale**: constitution می‌گوید هر migration downgrade دارد و تست می‌شود. FR-013 حذف آگهی، رزرو و نظر را ممنوع می‌کند، و این downgrade هیچ‌کدام را حذف نمی‌کند.
- **Alternatives considered**: حذف ساده‌ی ستون‌ها. آگهی‌های رد شده را بی‌درنگ عمومی می‌کرد.
- **چطور سنجیده شد**: `tests/test_migrations.py` (الگوی upgrade و downgrade کامل روی پایگاه داده‌ی واقعی).
