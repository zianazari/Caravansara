# کارهای آینده

این فهرست کارهایی است که بعد از تکمیل بکند نسخه‌ی اول انجام می‌شوند. هیچ‌کدام هنوز شروع نشده‌اند و طراحی فعلی در [backend-design.md](backend-design.md) آمده است.

## ترتیب پیشنهادی

| ترتیب | کار | پیش‌نیاز | دلیل این جایگاه |
| --- | --- | --- | --- |
| ۱ | بررسی ایندکس‌ها | بکند و داده‌ی دمو با حجم بالا | بدون داده و کوئری واقعی، انتخاب ایندکس حدسی است |
| ۲ | UI | API پایدار نسخه‌ی اول | صفحه‌ها به قرارداد API وابسته‌اند |
| ۳ | تست با Playwright | UI | این تست‌ها جریان واقعی کاربر را در مرورگر اجرا می‌کنند |
| ۴ | میکروسرویسی کردن | بار واقعی و نیاز اثبات‌شده | پرهزینه‌ترین کار است و تا نیاز مشخص نباشد سودی ندارد |

## ۱. بررسی انواع ایندکس‌های پایگاه داده

**هدف:** برای هر کوئری مهم، ایندکس مناسب با اندازه‌گیری انتخاب شود، نه با حدس. ایندکس اضافه نوشتن را کند می‌کند و فضا می‌گیرد، پس هر ایندکس باید هزینه‌اش را جبران کند.

| نوع ایندکس | کاربرد احتمالی در این پروژه |
| --- | --- |
| B-tree | کلیدهای خارجی، `reviews (listing_id, created_at)` و مرتب‌سازی |
| Partial | `is_active` و `hold_expires_at` برای `pending` |
| Covering (`INCLUDE`) | کارت نتایج جستجو بدون خواندن جدول |
| GiST | `public_location` و `EXCLUDE` روی `stay` |
| GIN | پیشنهاد خودکار نام شهر با `pg_trgm` |
| SP-GiST | مقایسه با GiST برای نقطه‌های جغرافیایی |
| BRIN | جدول‌های بزرگ و زمانی مثل `auth_attempts` |
| Hash | مقایسه با B-tree برای برابری ساده، مثل `idempotency_key` |

**کارها:**

- [ ] تولید داده‌ی حجیم و واقع‌نما، چون برنامه‌ریز PostgreSQL روی داده‌ی کم معمولاً ایندکس را انتخاب نمی‌کند.
- [ ] فهرست کردن کوئری‌های اصلی با `pg_stat_statements`، تا کار روی کوئری‌های پرهزینه‌ی واقعی متمرکز شود.
- [ ] مقایسه‌ی نوع ایندکس‌ها با `EXPLAIN (ANALYZE, BUFFERS)`، زمان نوشتن و حجم ایندکس.
- [ ] بررسی ایندکس‌های بی‌استفاده با `pg_stat_user_indexes`، چون فقط هزینه‌ی نوشتن دارند. `listings_latlng_idx` در 2026-11-02 حذف شد، چون جستجو به `public_location` منتقل شده بود.
- [ ] مقایسه‌ی نتیجه‌ی جستجوی شعاعی با شعاع و فیلتر تاریخ متفاوت، چون این ریسک در سند طراحی ثبت شده است.
- [ ] ثبت نتیجه‌ها و اعمال تغییرها با migration، تا هر تصمیم دلیل و عدد داشته باشد.

## ۲. UI

**هدف:** ساخت رابط کاربری وب برای مهمان و میزبان، چون نسخه‌ی اول فقط API دارد و کاربر نهایی نمی‌تواند از آن استفاده کند.

**کارها:**

- [ ] انتخاب فریم‌ورک و نحوه‌ی ذخیره‌ی توکن‌ها، چون این دو روی CORS و امنیت نشست اثر دارند.
- [ ] طراحی راست‌به‌چپ برای فارسی، چون از ابتدا اضافه کردن آن کم‌هزینه‌تر از اصلاح بعدی است.
- [ ] تصمیم درباره‌ی تقویم شمسی یا میلادی در انتخاب تاریخ، چون کاربر با آن تاریخ رزرو می‌کند.
- [ ] صفحه‌های مهمان: جستجو با شهر یا شعاع، نتایج و نقشه، آگهی، رزرو و پرداخت شبیه‌سازی‌شده، سفرها و ثبت نظر.
- [ ] صفحه‌های میزبان: مدیریت آگهی، آپلود عکس، امکانات و رزروها.
- [ ] حساب کاربری: ثبت‌نام، ورود و پروفایل.
- [ ] نمایش پیام فارسی برای کدهای خطای API، چون API فقط کد ماشینی و متن انگلیسی می‌دهد.
- [ ] نمایش شمارش معکوس نگه‌داشت ۱۵ دقیقه‌ای، تا مهمان مهلت پرداخت را از دست ندهد.

## ۳. تست با Playwright

**هدف:** اطمینان از کارکرد جریان‌های اصلی در مرورگر واقعی، چون تست‌های بکند مشکل‌های UI و اتصال آن به API را نمی‌بینند.

**کارها:**

- [ ] اجرای تست‌ها روی سیستم کامل با `docker compose`، تا محیط تست به محیط واقعی نزدیک باشد.
- [ ] ساخت داده‌ی مستقل برای هر تست، تا تست‌ها به هم وابسته نشوند.
- [ ] مسیر کامل مهمان: جستجو، رزرو، پرداخت، پایان اقامت و ثبت نظر.
- [ ] مسیر کامل میزبان: ساخت آگهی، آپلود عکس و دیدن رزرو.
- [ ] رزرو هم‌زمان با دو مرورگر، چون مهم‌ترین قانون سیستم باید از دید کاربر هم ثابت شود.
- [ ] حالت‌های خطا: پایان نگه‌داشت، کلیک دوباره و قطع شبکه هنگام رزرو.
- [ ] بررسی راست‌به‌چپ و نمایش موبایل، چون این خطاها در تست‌های بکند دیده نمی‌شوند.
- [ ] افزودن به CI با ذخیره‌ی trace و اسکرین‌شات خطا، تا علت شکست بدون تکرار محلی پیدا شود.

## ۴. میکروسرویسی کردن برنامه

**هدف:** جدا کردن ماژول‌ها به سرویس مستقل، فقط اگر نیاز واقعی وجود داشته باشد. میکروسرویس هزینه‌ی شبکه، استقرار، پایش و سازگاری داده دارد.

**شرط شروع؛ حداقل یکی باید با داده ثابت شود:**

- یک ماژول به مقیاس‌پذیری متفاوت نیاز دارد، مثلاً `search` بسیار پرترافیک‌تر از بقیه است.
- چند تیم مستقل روی ماژول‌ها کار می‌کنند و استقرار مشترک مانع کارشان شده است.
- خطای یک ماژول مکرراً کل سرویس را از کار می‌اندازد.

**چالش‌هایی که باید اول حل شوند:**

| وابستگی فعلی | مشکل بعد از جداسازی | جهت راه‌حل |
| --- | --- | --- |
| `EXCLUDE` روی `bookings` | باید در مالکیت یک سرویس بماند | سرویس `bookings` پایگاه داده‌ی خودش را داشته باشد |
| کلید خارجی `reviews` به `bookings` | بین دو پایگاه داده کلید خارجی ممکن نیست | بررسی رزرو با API یا رویداد |
| تریگر `avg_rating` روی `listings` | تریگر به جدول سرویس دیگر دسترسی ندارد | به‌روزرسانی امتیاز با رویداد |
| بررسی دسترسی‌پذیری در `search` | به داده‌ی رزرو نیاز دارد | ایندکس جستجوی جدا که با رویداد به‌روز می‌شود |
| JWT در `identity` | سرویس‌ها باید توکن را مستقل بررسی کنند | امضای نامتقارن و کلید عمومی مشترک |

**کارها:**

- [ ] اندازه‌گیری بار و خطا برای هر ماژول، چون تصمیم جداسازی باید بر پایه‌ی داده باشد.
- [ ] انتخاب اولین سرویس برای جداسازی. `search` نامزد مناسبی است، چون فقط می‌خواند و ریسک کمی برای قانون رزرو دارد.
- [ ] جدا کردن تدریجی با الگوی Strangler Fig، چون بازنویسی یک‌جا ریسک بالایی دارد.
- [ ] افزودن رویدادها با الگوی Outbox، تا رویدادی بین پایگاه داده و صف گم نشود.
- [ ] افزودن API Gateway، پایش توزیع‌شده و Contract Test، چون خطایابی بین سرویس‌ها بدون این‌ها سخت است.
- [ ] تحلیل دوباره‌ی نیاز به Redis یا صف پیام، چون ارتباط رویدادی شرایط تصمیم قبلی را تغییر می‌دهد.
