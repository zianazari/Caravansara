# کارهای آینده

این فهرست کارهای پیش روی پروژه است و فقط کارهایی را دارد که هنوز شروع نشده‌اند. کارهای انجام‌شده، یعنی پیاده‌سازی بکند نسخه‌ی اول، تکمیل تست‌های آن، مانیتورینگ (لاگ، متریک و trace)، داده‌ی تست و ماک (اولین کار با Spec Kit، در [specs/backend (001)](../specs/backend/))، پهن کردن ستون‌های قیمت برای ریال ([specs/backend (002)](../specs/backend/))، بازبینی روش Spec Kit (constitution نسخه‌ی 1.2.0)، بررسی ایندکس‌ها ([specs/backend (003)](../specs/backend/))، تأیید آگهی توسط مدیر سیستم ([specs/backend (004)](../specs/backend/)) و بخش مهمانِ سایت وب ([specs/005-frontend-guest/](../specs/005-frontend-guest/))، و تم کاروانسرایی سایت ([specs/007-caravansara-theme/](../specs/007-caravansara-theme/))، و آپلود عکس پروفایل از راه API ([specs/006-avatar-upload-via-api/](../specs/006-avatar-upload-via-api/))، در [backend-design.md](backend-design.md)، [backend/README.md](../backend/README.md) و [observability/README.md](../observability/README.md) ثبت شده‌اند.

## ۱. فرانت‌اند: صفحه‌های میزبان و پنل مدیر

**هدف:** ادامه‌ی سایت وب، تا میزبان و مدیر سیستم هم بدون Swagger کار کنند. بخش مهمان ساخته شده است (کار ۰۰۵، [specs/005-frontend-guest/](../specs/005-frontend-guest/))، و پایه‌ی آن آماده است: `frontend/`، نشست، ترجمه‌ها، تقویم شمسی، تومان، CSP، سرویس `web` و CI. تصمیم‌ها و دلیل هر ساختار در [backend-design.md](backend-design.md)، بخش «فرانت‌اند وب»، آمده‌اند.

**کارهای باقی‌مانده از تم کاروانسرایی (کار ۰۰۷).** چهار کار اول API تازه می‌خواهند (اصل III)، و دو کار آخر نه:

- [ ] **علاقه‌مندی‌ها:** قلب روی کارت و بخش «علاقه‌مندی‌ها» در نوار پایین گوشی. جدول تازه و endpointهای افزودن، برداشتن و فهرست می‌خواهد، و ذخیره برای حساب کاربر است، روی همه‌ی دستگاه‌ها. (پاسخ Q3 مالک پروژه، 2026-11-09)
- [ ] **دسته‌های تازه:** «خانه‌ی سنتی»، «کنار دریا»، «کویر» و مانند آن‌ها. جدول دسته، انتخاب در فرم میزبان، داده‌ی دمو و فیلتر جستجو می‌خواهد. (پاسخ Q2)
- [ ] **فیلتر نوع اقامتگاه در جستجو:** پارامتر `property_type` در `GET /search/listings`. با آن، دسته‌های «کل خانه»، «اتاق خصوصی» و «اتاق مشترک» شدنی می‌شوند. (research R5 کار ۰۰۷)
- [ ] **آگهی‌های «محبوب» در همه‌ی شهرها:** یک endpoint، به‌جای شش ردیف شهر. (گزینه‌ی B پرسش Q1، اگر روزی خواسته شود)
- [ ] **زمان یک کاربر تازه روی گوشی (SC-007، T050 کار ۰۰۷، پیگیری پس از pull request با تصمیم مالک پروژه، 2026-11-10):** از صفحه‌ی اول تا نتیجه‌ی جستجو برای یک شهر و تاریخ، بی راهنما، ترجیحاً با کسی جز سازنده؛ هدف کمتر از ۳۰ ثانیه. API نمی‌خواهد.
- [ ] **بار نقشه‌ی جستجو پس از اولین نمایش:** راه‌اندازی MapLibre در CPU کند (چهار برابر) یک کار طولانی حدود ۳۳۰ میلی‌ثانیه‌ای است. این از کار ۰۰۵ آمده، نه از تم ([measurements.md](../specs/007-caravansara-theme/measurements.md)). بار آن پس از اولین تعامل یا هنگام دیده شدن، زمان پاسخ صفحه‌ی جستجو را کم می‌کند. API نمی‌خواهد.

**کار ۰۰۸: صفحه‌های میزبان**

- [ ] مدیریت آگهی: ساخت، ویرایش، غیرفعال کردن، امکانات و رزروهای هر آگهی.
- [ ] وضعیت بازبینی و دلیل رد، و دکمه‌ی ارسال دوباره. API آن آماده است: فیلد `review` در `GET /me/listings`، و `POST /listings/{id}/resubmit`.
- [ ] آپلود عکس آگهی مستقیم به storage، با پیش‌نمایش، نوار پیشرفت، و بررسی اندازه و نوع پیش از ارسال، به همان روش بررسی آواتار در سایت. عکس آگهی، برخلاف عکس پروفایل پس از کار ۰۰۶، مستقیم به storage می‌رود. ترتیب و کاور، و برچسب اتاق. ترجمه‌ی کدهای خطای میزبان از قبل در فایل‌های ترجمه هست.
- [ ] پیوند «میزبان شوید» در سرصفحه، چون هر کاربر می‌تواند میزبان باشد.

**کار ۰۰۹: پنل مدیر**

- [ ] برنامه‌ای جدا با UI خودش، روی زیردامنه‌ی جدا و بدون پیوند از سایت اصلی (admin نشانی را می‌داند)، با همین پشته (Next.js، RTL و Vazirmatn)، برای صف بازبینی و تأیید یا رد. کار جدا با Spec Kit (تصمیم مالک پروژه، 2026-11-06). بکند آن انجام شده است ([backend-design.md](backend-design.md)، بخش «تأیید آگهی»)، و تا آن موقع بازبینی از راه API و Swagger شدنی است.

**کارهای باقی‌مانده از بخش مهمان (کار ۰۰۵)، که هر کدام تغییر API یا زیرساخت می‌خواهد:**

- [ ] **فیلد «نظر دارد» در `BookingOut`:** بدون آن، گزینه‌ی ثبت نظر برای رزروی که نظر دارد تا اولین تلاش دیده می‌شود. سایت فقط در همان زبانه آن را پنهان می‌کند.
- [ ] **ارسال خطاهای مرورگر و Core Web Vitals به Grafana:** endpoint تازه‌ای برای دریافت می‌خواهد (اصل III).
- [ ] **قاعده‌ی lifecycle در storage، فقط برای فایل‌های رهاشده:** از کار ۰۰۶ هیچ آپلودی بی ثبت در storage نمی‌ماند. فقط فایل قبلی‌ای که پاک کردنش پس از جایگزینی شکست خورده (و log شده: `avatar_delete_failed`، `avatar_cleanup_failed`) ممکن است زیر `avatars/` بماند. یک قاعده‌ی lifecycle یا کار دوره‌ای می‌تواند آن‌ها را پاک کند.
- [ ] **تنظیم CORS در storage در production:** تا مرورگر بتواند عکس آگهی را مستقیم آپلود کند. عکس پروفایل از کار ۰۰۶ از API می‌گذرد و CORS نمی‌خواهد. در توسعه، MinIO آن را از قبل می‌پذیرد.
- [ ] **ارائه‌دهنده‌ی کاشی نقشه در production:** کاشی‌های `tile.openstreetmap.org` بدون SLA هستند، و سیاست مصرفشان برای بار سنگین یا تجاری می‌گوید «use an alternative». با متغیر `NEXT_PUBLIC_MAP_TILE_URL` بدون تغییر کد عوض می‌شود.
- [ ] **reverse proxy جلوی سایت در production:** باید `X-Forwarded-For` را بگذارد، تا محدودیت تلاش نشانی واقعی را ببیند ([backend-design.md](backend-design.md)، «زیرساخت و تحویل»).
- [ ] **به‌روز کردن `caravansara_demo` به migration `0006`:** این پایگاه داده هنوز در `0001` است و API امروز با آن کار نمی‌کند. بدون آن، صفحه‌ها با عکس‌های واقعی دمو اندازه گرفته نشدند ([measurements.md](../specs/005-frontend-guest/measurements.md)).
- [ ] **زمان سفر کامل مهمان با یک انسان (SC-001، T083 کار ۰۰۵، پیگیری پس از pull request با تصمیم مالک پروژه، 2026-11-08):** یک کاربر تازه، ترجیحاً کسی جز سازنده، با گوشی و بدون راهنما، از جستجو تا رزرو قطعی؛ هدف کمتر از ۵ دقیقه. اسکریپت همین مسیر در Chrome پاس شده است ([measurements.md](../specs/005-frontend-guest/measurements.md)).
- [ ] **آزمودن Safari و Firefox (T085 کار ۰۰۵، به بعد گذاشته‌شده با تصمیم مالک پروژه، 2026-11-08):** مسیر کامل مهمان، و به‌ویژه اینکه Safari کوکی `Secure` نشست را روی `http://localhost` می‌پذیرد یا نه. اسکریپت مسیر برای Chrome آماده است. Safari 26.6.2 روی دستگاه هست، و برای اجرای خودکار باید «Allow remote automation» در تنظیمات Developer آن روشن شود.

**معیار پایان:** میزبان و مدیر سیستم همه‌ی جریان‌هایشان را بدون Swagger انجام دهند، روی موبایل، به فارسی راست‌به‌چپ و به انگلیسی، و CI فرانت سبز بماند.

## ۲. تست با Playwright

**هدف:** اطمینان از کارکرد جریان‌های اصلی در مرورگر واقعی، چون تست‌های بکند مشکل‌های UI و اتصال آن به API را نمی‌بینند.

تست‌های Playwright برای API در `e2e/` از قبل وجود دارند (ثبت در راهبرد تست `docs/backend-design.md`). تست‌های مرورگر در همان پروژه و با همان تنظیمات و helperها اضافه می‌شوند.

**کارها:**

- [ ] اجرای تست‌ها روی سیستم کامل با `docker compose`، تا محیط تست به محیط واقعی نزدیک باشد.
- [ ] ساخت داده‌ی مستقل برای هر تست، تا تست‌ها به هم وابسته نشوند.
- [ ] مسیر کامل مهمان: جستجو، رزرو، پرداخت، پایان اقامت و ثبت نظر.
- [ ] مسیر کامل میزبان: ساخت آگهی، آپلود عکس و دیدن رزرو.
- [ ] رزرو هم‌زمان با دو مرورگر، چون مهم‌ترین قانون سیستم باید از دید کاربر هم ثابت شود.
- [ ] حالت‌های خطا: پایان نگه‌داشت، کلیک دوباره و قطع شبکه هنگام رزرو.
- [ ] بررسی راست‌به‌چپ و نمایش موبایل، چون این خطاها در تست‌های بکند دیده نمی‌شوند.
- [ ] افزودن به CI با ذخیره‌ی trace و اسکرین‌شات خطا، تا علت شکست بدون تکرار محلی پیدا شود.

## ۳. سرویس ایمیل

**هدف:** فرستادن ایمیل به کاربر، اول برای نتیجه‌ی بازبینی آگهی (انجام شد، [backend-design.md](backend-design.md) بخش «تأیید آگهی»): «آگهی شما تأیید شد» یا «رد شد»، و با دلیل رد. امروز سیستم هیچ ایمیلی نمی‌فرستد.

**کارها:**

- [ ] spec با Spec Kit: کدام رویدادها ایمیل می‌فرستند. اول نتیجه‌ی بازبینی. بعد، اگر مالک پروژه بخواهد، تأیید رزرو و دو موردی که امروز در «خارج از دامنه»ی سند طراحی‌اند: تأیید ایمیل و بازیابی رمز.
- [ ] interface ایمیل در `core`، با پیاده‌سازی SMTP و پیاده‌سازی آزمایشی که فقط ایمیل‌ها را نگه می‌دارد، تا تست‌ها ایمیل واقعی نفرستند.
- [ ] فرستادن از worker، نه وسط درخواست API، با ثبت در جدول و تلاش دوباره. دلیل: کند یا خاموش بودن سرور ایمیل نباید تأیید آگهی را کند کند یا بشکند، و ایمیلی که فرستاده نشده نباید گم شود.
- [ ] متن فارسی و انگلیسی، به زبان کاربر.
- [ ] یک سرویس ایمیل محلی (مثل Mailpit) در `docker compose`، تا ایمیل‌ها در توسعه دیده شوند.
- [ ] متریک ایمیل‌های فرستاده‌شده و شکست‌خورده در Grafana، و هشدار برای صف ایمیلی که پیش نمی‌رود.

**معیار پایان:** میزبان پس از تأیید یا رد آگهی‌اش ایمیل بگیرد. خاموش بودن سرور ایمیل نه تأیید را متوقف کند و نه ایمیل را گم کند.

## ۴. کش کردن داده با Redis

**هدف:** کم کردن زمان پاسخ و بار PostgreSQL در خواندن‌های پرتکرار. نسخه‌ی اول عمداً Redis ندارد (بخش «چرا Redis نداریم» در [backend-design.md](backend-design.md))، و همان‌جا کش جستجوی پرترافیک یکی از شرط‌های افزودن آن آمده است. بررسی ایندکس انجام شده است، و این کار از متریک‌های مانیتورینگ موجود استفاده می‌کند، چون اول باید با عدد معلوم شود کدام endpoint کند و پرتکرار است، و کوئری کند اول با ایندکس درست شود.

**عددهای بررسی ایندکس** ([measurements.md](../specs/backend/measurements.md)، داده‌ی حجیم، میانه‌ی گرم روی لپ‌تاپ و با باتری):
- جستجوی شهری لندن با تاریخ ۶۵ ms است.
- جستجوی شعاعی ۵ km با تاریخ ۵۲ ms است.
- نامزد اصلی کش شمارش امکانات پنل فیلترها (`GET /search/filters`) است: ۱۸۳ تا ۲۳۳ ms. این کوئری ۶۵۷ هزار ردیف (آگهی، امکان) را برای ۴۵ هزار آگهی جمع می‌زند، پس ایندکس آن را سریع‌تر نمی‌کند، و شمارش‌ها برای یک شهر و تاریخ کم تغییر می‌کنند.
- شعاع ۲۰ km (۱۵۷ تا ۱۷۹ ms) و اقامت بیش از یک هفته در منطقه‌ی پرتراکم (۲۷۷ ms) هم بالاتر از هدف ۵۰ ms می‌مانند.

پیش از کش، دو تنظیم PostgreSQL هم با بار واقعی بررسی شود:
- **JIT.** وقتی یک اتصال یک بار JIT کند، کوئری‌های بعدی‌اش حدود ۳ برابر کند می‌شوند. `jit = off` یا `jit_above_cost` بالاتر برای این بار OLTP بررسی شود.
- **`shared_buffers`.** فعلاً ۱۲۸ MB پیش‌فرض است، در حالی که جدول رزرو با ایندکس‌هایش حدود ۱٫۴ GB است.

**قانون ثابت:** منطق رزرو به کش وابسته نمی‌شود. دسترسی‌پذیری هنگام رزرو همیشه از PostgreSQL و `EXCLUDE` بررسی می‌شود، چون داده‌ی کهنه‌ی کش نباید رزرو هم‌پوشان بسازد.

| داده | کش؟ | دلیل |
| --- | --- | --- |
| کشور، شهر و امکانات (پیشنهاد خودکار) | بله، با TTL بلند | تقریباً ثابت‌اند و فقط با seed تغییر می‌کنند |
| جزئیات عمومی آگهی، عکس‌ها و امتیاز | بله، با پاک شدن هنگام تغییر | زیاد خوانده و کم نوشته می‌شوند |
| نتیجه‌ی جستجو | فقط با TTL کوتاه، اگر اندازه‌گیری لازم بداند | با هر رزرو تغییر می‌کند و ترکیب پارامترهایش زیاد است |
| رزرو، دسترسی‌پذیری برای رزرو، توکن و داده‌ی هر کاربر | خیر | درستی مهم‌تر از سرعت است و داده‌ی شخصی نباید در کش مشترک بماند |
| نشانی دقیق آگهی | خیر | طبق سند طراحی خصوصی است |

**کارها:**

- [ ] انتخاب endpointهای هدف با متریک‌های موجود در Grafana (تعداد درخواست و p95 هر route)، چون کش روی endpoint کم‌ترافیک فقط پیچیدگی اضافه می‌کند.
- [ ] interface کش در `core`، با پیاده‌سازی Redis و پیاده‌سازی بی‌اثر برای تست، چون ماژول‌ها نباید مستقیم به Redis وابسته باشند و تست‌های فعلی باید بدون Redis هم اجرا شوند.
- [ ] الگوی cache-aside با کلید نسخه‌دار، مثل `v1:listing:{id}`، تا با تغییر شکل داده فقط پیشوند عوض شود و کش قدیمی خودبه‌خود کنار برود.
- [ ] پاک کردن کلید بعد از commit تراکنش در تغییر آگهی، عکس، امکانات و ثبت نظر (که `avg_rating` را تغییر می‌دهد). دلیل: پاک کردن پیش از commit اجازه می‌دهد درخواست دیگری داده‌ی قدیمی را دوباره در کش بگذارد.
- [ ] TTL با کمی پراکندگی تصادفی و جلوگیری از هجوم هم‌زمان روی کلید داغ، تا با انقضای هم‌زمان کلیدها همه‌ی درخواست‌ها با هم به PostgreSQL نرسند.
- [ ] رفتار هنگام از کار افتادن Redis: timeout کوتاه و خواندن مستقیم از PostgreSQL، چون کش نباید نقطه‌ی شکست کل سیستم شود.
- [ ] افزودن Redis به `docker compose` و CI با `maxmemory` و سیاست `allkeys-lru` و بدون persistence، چون داده‌ی کش از PostgreSQL بازسازی‌پذیر است.
- [ ] متریک نرخ hit و miss، زمان پاسخ Redis و evictionها، و `redis_exporter` در profile `observability`، تا اثر کش با عدد دیده شود.
- [ ] تست: hit دوم، پاک شدن کش پس از تغییر، کار کردن API با Redis خاموش، و اینکه کش کهنه رزرو هم‌پوشان نمی‌سازد.
- [ ] بررسی جداگانه‌ی انتقال rate limit به Redis، فقط اگر API با چند نمونه اجرا شود، چون شمارنده‌ی فعلی PostgreSQL برای یک نمونه کافی است.
- [ ] به‌روزرسانی بخش «چرا Redis نداریم» در `docs/backend-design.md` با تصمیم جدید و دلیلش.

**معیار پایان:** p95 endpointهای هدف روی داشبورد کاهش قابل اندازه‌گیری داشته باشد، نرخ hit دیده شود، و همه‌ی تست‌ها با Redis خاموش هم سبز باشند.

## ۵. میکروسرویسی کردن برنامه

**هدف:** جدا کردن ماژول‌ها به سرویس مستقل، فقط اگر نیاز واقعی وجود داشته باشد. میکروسرویس هزینه‌ی شبکه، استقرار، پایش و سازگاری داده دارد.

**شرط شروع؛ حداقل یکی باید با داده ثابت شود:**

- یک ماژول به مقیاس‌پذیری متفاوت نیاز دارد، مثلاً `search` بسیار پرترافیک‌تر از بقیه است.
- چند تیم مستقل روی ماژول‌ها کار می‌کنند و استقرار مشترک مانع کارشان شده است.
- خطای یک ماژول مکرراً کل سرویس را از کار می‌اندازد.

**چالش‌هایی که باید اول حل شوند:**

| وابستگی فعلی | مشکل بعد از جداسازی | جهت راه‌حل |
| --- | --- | --- |
| `EXCLUDE` روی `bookings` | باید در مالکیت یک سرویس بماند | سرویس `bookings` پایگاه داده‌ی خودش را داشته باشد |
| کلید خارجی `reviews` به `bookings` | بین دو پایگاه داده کلید خارجی ممکن نیست | بررسی رزرو با API یا رویداد |
| تریگر `avg_rating` روی `listings` | تریگر به جدول سرویس دیگر دسترسی ندارد | به‌روزرسانی امتیاز با رویداد |
| بررسی دسترسی‌پذیری در `search` | به داده‌ی رزرو نیاز دارد | ایندکس جستجوی جدا که با رویداد به‌روز می‌شود |
| JWT در `identity` | سرویس‌ها باید توکن را مستقل بررسی کنند | امضای نامتقارن و کلید عمومی مشترک |

**کارها:**

- [ ] اندازه‌گیری بار و خطا برای هر ماژول با متریک‌های موجود در Grafana، چون تصمیم جداسازی باید بر پایه‌ی داده باشد.
- [ ] انتخاب اولین سرویس برای جداسازی. `search` نامزد مناسبی است، چون فقط می‌خواند و ریسک کمی برای قانون رزرو دارد.
- [ ] جدا کردن تدریجی با الگوی Strangler Fig، چون بازنویسی یک‌جا ریسک بالایی دارد.
- [ ] افزودن رویدادها با الگوی Outbox، تا رویدادی بین پایگاه داده و صف گم نشود.
- [ ] افزودن API Gateway، پایش توزیع‌شده و Contract Test، چون خطایابی بین سرویس‌ها بدون این‌ها سخت است.
- [ ] تحلیل نیاز به صف پیام (Redis بخش ۴ یا ابزاری جدا)، چون ارتباط رویدادی شرایط تصمیم قبلی را تغییر می‌دهد.
