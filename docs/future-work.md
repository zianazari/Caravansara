# کارهای آینده

این فهرست کارهای پیش روی پروژه است، از پیاده‌سازی بکند نسخه‌ی اول تا کارهای بعد از آن. بخش ۱ انجام شده و بقیه هنوز شروع نشده‌اند. طراحی فعلی در [backend-design.md](backend-design.md) آمده است.

## ترتیب پیشنهادی

| ترتیب | کار | پیش‌نیاز | دلیل این جایگاه |
| --- | --- | --- | --- |
| ۱ | پیاده‌سازی بکند (انجام شد) | سند طراحی تأییدشده | همه‌ی کارهای بعدی به API و داده‌ی واقعی نیاز دارند |
| ۲ | افزایش داده‌ی تست و ماک | schema و تولیدکننده‌ی داده‌ی دمو | بررسی ایندکس و تست‌ها به داده‌ی بیشتر و متنوع‌تر نیاز دارند |
| ۳ | مانیتورینگ: لاگ، متریک و trace | بکند | بدون اندازه‌گیری، بررسی ایندکس و تصمیم میکروسرویس بر پایه‌ی حدس است |
| ۴ | بررسی ایندکس‌ها | بکند و داده‌ی دمو با حجم بالا | بدون داده و کوئری واقعی، انتخاب ایندکس حدسی است |
| ۵ | UI | API پایدار نسخه‌ی اول | صفحه‌ها به قرارداد API وابسته‌اند |

## ۱. پیاده‌سازی بکند نسخه‌ی اول

**هدف:** ساخت بکند FastAPI بر اساس [backend-design.md](backend-design.md)، به‌صورت برنامه‌ی ماژولار روی PostgreSQL. کد در [backend/](../backend/README.md) است و Swagger UI در `/docs` در دسترس است.

**کارها، به ترتیب مراحل سند طراحی:**

- [x] اسکلت پروژه، Docker، CI، migration اول و seed، چون همه‌ی ماژول‌ها روی این پایه ساخته می‌شوند.
- [x] `identity` و `catalog`، همراه با rate limit ورود و ثبت‌نام، چون بقیه‌ی endpointها به کاربر و شهر نیاز دارند.
- [x] `listings` و آپلود عکس با MinIO.
- [x] `bookings` و تست‌های هم‌زمانی، چون مهم‌ترین قانون سیستم جلوگیری از رزرو هم‌پوشان است.
- [x] `jobs` برای انقضای نگه‌داشت و completed شدن رزرو.
- [x] `reviews`.
- [x] `search`، که بعد از رزرو می‌آید چون بررسی دسترسی‌پذیری به آن وابسته است.
- [x] همگام‌سازی اسناد و داده‌ی دمو، تا اسناد با کد یکی بمانند و بررسی ایندکس داده داشته باشد.

**معیار پایان:** همه‌ی تست‌ها روی PostgreSQL واقعی سبز باشند و پوشش کد حداقل ۹۰٪ باشد، طبق راهبرد تست سند طراحی. نتیجه: ۱۲۴ تست سبز و پوشش ۹۷٫۸٪.

## ۲. افزایش تعداد داده‌های تست و ماک

**هدف:** داده‌ی بیشتر و متنوع‌تر برای دمو، تست و اندازه‌گیری کارایی. داده‌ی دمو فعلی ([db/demo/README.md](../db/demo/README.md)) از Inside Airbnb ساخته شده: ۲۰۰ آگهی در چهار شهر، ۱٬۷۹۳ رزرو و ۱٬۴۹۱ نظر. این حجم برای نمایش کافی است ولی برای بررسی ایندکس و بیشتر حالت‌های مرزی کم است.

**کارها:**

- [ ] افزایش آگهی و نظر واقعی با تغییر `LISTINGS_PER_CITY` و `REVIEWS_PER_LISTING` در `build_demo_seed.py`، چون توزیع قیمت، امتیاز و امکانات در داده‌ی واقعی طبیعی‌تر از داده‌ی ساختگی است.
- [ ] افزودن شهرها و کشورهای بیشتر از Inside Airbnb، از جمله شهری با ارز دیگر، چون جستجوی شهری و نمایش ارز باید روی چند حالت آزموده شود.
- [ ] چند عکس برای هر آگهی با `room_tag` و `sort_order` مختلف، چون Inside Airbnb فقط عکس اصلی را می‌دهد و صفحه‌ی آگهی و جابه‌جایی عکس‌ها بدون آن آزموده نمی‌شود.
- [ ] تولیدکننده‌ی داده‌ی حجیم (مثلاً ۱۰۰ هزار آگهی و چند میلیون رزرو) با توزیع گرفته‌شده از داده‌ی واقعی، چون بررسی ایندکس در بخش ۴ به آن وابسته است.
- [ ] بارگذاری داده‌ی حجیم با `COPY` به‌جای `INSERT`، و نگه نداشتن آن در git، چون فایل SQL میلیونی هم کند load می‌شود و هم repo را سنگین می‌کند.
- [ ] داده‌ی حالت‌های مرزی: نگه‌داشت `pending` نزدیک انقضا، رزرو `expired`، اقامت ۳۶۵ شبه، رزرو یک سال جلوتر، تحویل همان روز، آگهی غیرفعال و آگهی بدون نظر، چون قانون‌های سند طراحی دقیقاً در این مرزها می‌شکنند.
- [ ] متن فارسی و آگهی‌های نمونه در شهرهای ایران، چون Inside Airbnb داده‌ی فارسی ندارد و UI راست‌به‌چپ باید با متن واقعی فارسی آزموده شود.
- [ ] factory برای تست‌های بکند، جدا از داده‌ی دمو، چون تست‌ها نباید به داده‌ی مشترکی وابسته باشند که با بازسازی دمو تغییر می‌کند.

**معیار پایان:** داده‌ی دمو همچنان روی پایگاه داده‌ی خالی بدون خطا load شود، و داده‌ی حجیم با یک فرمان تولید و load شود.

## ۳. مانیتورینگ سیستم: لاگ، متریک و trace

**هدف:** دیدن وضعیت سیستم در هر لحظه و پیدا کردن علت خطا بدون حدس. سه نوع داده جمع می‌شود، چون هر کدام به سؤال متفاوتی جواب می‌دهد:

| نوع داده | به چه سؤالی جواب می‌دهد | ابزار پیشنهادی |
| --- | --- | --- |
| متریک | چه مقدار و چه‌قدر سریع؟ (تعداد درخواست، خطا، زمان پاسخ) | Prometheus |
| لاگ | دقیقاً چه اتفاقی افتاد؟ | Loki |
| trace | زمان یک درخواست در کدام بخش صرف شد؟ (API، کوئری، MinIO) | OpenTelemetry و Tempo |
| داشبورد و هشدار | همه‌ی موارد بالا در یک جا | Grafana |

این ابزارها را پیشنهاد می‌کنم چون متن‌باز و رایگان‌اند، با Docker اجرا می‌شوند و Grafana هر سه نوع داده را کنار هم نشان می‌دهد. OpenTelemetry استاندارد مستقل از فروشنده است و اگر بعداً ابزار عوض شود، کد برنامه تغییری نمی‌کند.

**کارها:**

- [ ] لاگ ساخت‌یافته‌ی JSON با `request_id` و `trace_id` در هر خط، چون جستجو و فیلتر روی متن آزاد سخت است و این شناسه‌ها لاگ را به trace وصل می‌کنند.
- [ ] ننوشتن داده‌ی حساس در لاگ: رمز، توکن، ایمیل کامل و نشانی دقیق آگهی. لاگ معمولاً دسترسی گسترده‌تری از پایگاه داده دارد و نشانی دقیق طبق سند طراحی خصوصی است.
- [ ] endpoint `/metrics` در FastAPI با متریک‌های RED (تعداد، خطا، زمان پاسخ) برای هر endpoint. برچسب باید الگوی مسیر باشد، مثل `/listings/{id}`، نه نشانی کامل، چون هر برچسب یکتا یک سری زمانی جدا در Prometheus می‌سازد.
- [ ] متریک‌های کسب‌وکار: رزرو ساخته‌شده، تأییدشده و منقضی‌شده، خطای رزرو هم‌پوشان (`23P01`)، برخورد با rate limit و تعداد نظرها. دلیل: مهم‌ترین قانون‌های سیستم باید در عمل هم دیده شوند.
- [ ] متریک worker: زمان آخرین اجرای موفق و تعداد نگه‌داشت‌های منقضی‌شده، چون اگر worker بایستد تاریخ‌ها قفل می‌مانند و هیچ خطایی در API دیده نمی‌شود.
- [ ] trace با OpenTelemetry برای FastAPI، SQLAlchemy و فراخوانی‌های S3، تا کندی یک جستجو یا آپلود تا کوئری مقصر دنبال شود.
- [ ] جمع‌آوری متریک PostgreSQL با `postgres_exporter` و متریک داخلی MinIO، چون بیشتر کندی‌ها از پایگاه داده می‌آید.
- [ ] داشبوردهای Grafana به‌صورت فایل در repo (provisioning)، تا هر محیط همان داشبورد را داشته باشد و تغییرش در git بررسی شود.
- [ ] هشدار برای نرخ خطای بالا، کندی جستجو، توقف worker و پر شدن اتصال‌های پایگاه داده. آستانه‌ها بعد از دیدن داده‌ی واقعی تنظیم می‌شوند، چون آستانه‌ی حدسی یا هشدار اضافه می‌دهد یا اصلاً هشدار نمی‌دهد.
- [ ] اجرای این ابزارها با profile جدا در `docker compose`، تا محیط توسعه‌ی روزانه سبک بماند و هر وقت لازم شد با یک فرمان بالا بیاید.
- [ ] تست وجود متریک‌ها و ثبت `request_id` در پاسخ و لاگ، تا با تغییر کد بی‌صدا از بین نروند.

**معیار پایان:** با `docker compose --profile observability up` داشبورد Grafana بالا بیاید. یک درخواست کند هم باید از روی متریک، تا trace و لاگ همان درخواست دنبال‌شدنی باشد.

## ۴. بررسی انواع ایندکس‌های پایگاه داده

**هدف:** برای هر کوئری مهم، ایندکس مناسب با اندازه‌گیری انتخاب شود، نه با حدس. ایندکس اضافه نوشتن را کند می‌کند و فضا می‌گیرد، پس هر ایندکس باید هزینه‌اش را جبران کند.

| نوع ایندکس | کاربرد احتمالی در این پروژه |
| --- | --- |
| B-tree | کلیدهای خارجی، `reviews (listing_id, created_at)` و مرتب‌سازی |
| Partial | `is_active` و `hold_expires_at` برای `pending` |
| Covering (`INCLUDE`) | کارت نتایج جستجو بدون خواندن جدول |
| GiST | `public_location` و `EXCLUDE` روی `stay` |
| GIN | پیشنهاد خودکار نام شهر با `pg_trgm` |
| SP-GiST | مقایسه با GiST برای نقطه‌های جغرافیایی |
| BRIN | جدول‌های بزرگ و زمانی مثل `auth_attempts` |
| Hash | مقایسه با B-tree برای برابری ساده، مثل `idempotency_key` |

**کارها:**

- [ ] بارگذاری داده‌ی حجیم بخش ۲، چون برنامه‌ریز PostgreSQL روی داده‌ی کم معمولاً ایندکس را انتخاب نمی‌کند.
- [ ] فهرست کردن کوئری‌های اصلی با `pg_stat_statements` و داشبورد PostgreSQL بخش ۳، تا کار روی کوئری‌های پرهزینه‌ی واقعی متمرکز شود.
- [ ] مقایسه‌ی نوع ایندکس‌ها با `EXPLAIN (ANALYZE, BUFFERS)`، زمان نوشتن و حجم ایندکس.
- [ ] بررسی ایندکس‌های بی‌استفاده با `pg_stat_user_indexes`، چون فقط هزینه‌ی نوشتن دارند. `listings_latlng_idx` در 2026-11-02 حذف شد، چون جستجو به `public_location` منتقل شده بود.
- [ ] مقایسه‌ی نتیجه‌ی جستجوی شعاعی با شعاع و فیلتر تاریخ متفاوت، چون این ریسک در سند طراحی ثبت شده است.
- [ ] ثبت نتیجه‌ها و اعمال تغییرها با migration، تا هر تصمیم دلیل و عدد داشته باشد.

## ۵. UI

**هدف:** ساخت رابط کاربری وب برای مهمان و میزبان، چون نسخه‌ی اول فقط API دارد و کاربر نهایی نمی‌تواند از آن استفاده کند.

**کارها:**

- [ ] انتخاب فریم‌ورک و نحوه‌ی ذخیره‌ی توکن‌ها، چون این دو روی CORS و امنیت نشست اثر دارند.
- [ ] طراحی راست‌به‌چپ برای فارسی، چون از ابتدا اضافه کردن آن کم‌هزینه‌تر از اصلاح بعدی است.
- [ ] تصمیم درباره‌ی تقویم شمسی یا میلادی در انتخاب تاریخ، چون کاربر با آن تاریخ رزرو می‌کند.
- [ ] صفحه‌های مهمان: جستجو با شهر یا شعاع، نتایج و نقشه، آگهی، رزرو و پرداخت شبیه‌سازی‌شده، سفرها و ثبت نظر.
- [ ] صفحه‌های میزبان: مدیریت آگهی، آپلود عکس، امکانات و رزروها.
- [ ] حساب کاربری: ثبت‌نام، ورود و پروفایل.
- [ ] نمایش پیام فارسی برای کدهای خطای API، چون API فقط کد ماشینی و متن انگلیسی می‌دهد.
- [ ] نمایش شمارش معکوس نگه‌داشت ۱۵ دقیقه‌ای، تا مهمان مهلت پرداخت را از دست ندهد.

## ۶. تست با Playwright

**هدف:** اطمینان از کارکرد جریان‌های اصلی در مرورگر واقعی، چون تست‌های بکند مشکل‌های UI و اتصال آن به API را نمی‌بینند.

**کارها:**

- [ ] اجرای تست‌ها روی سیستم کامل با `docker compose`، تا محیط تست به محیط واقعی نزدیک باشد.
- [ ] ساخت داده‌ی مستقل برای هر تست، تا تست‌ها به هم وابسته نشوند.
- [ ] مسیر کامل مهمان: جستجو، رزرو، پرداخت، پایان اقامت و ثبت نظر.
- [ ] مسیر کامل میزبان: ساخت آگهی، آپلود عکس و دیدن رزرو.
- [ ] رزرو هم‌زمان با دو مرورگر، چون مهم‌ترین قانون سیستم باید از دید کاربر هم ثابت شود.
- [ ] حالت‌های خطا: پایان نگه‌داشت، کلیک دوباره و قطع شبکه هنگام رزرو.
- [ ] بررسی راست‌به‌چپ و نمایش موبایل، چون این خطاها در تست‌های بکند دیده نمی‌شوند.
- [ ] افزودن به CI با ذخیره‌ی trace و اسکرین‌شات خطا، تا علت شکست بدون تکرار محلی پیدا شود.

## ۷. میکروسرویسی کردن برنامه

**هدف:** جدا کردن ماژول‌ها به سرویس مستقل، فقط اگر نیاز واقعی وجود داشته باشد. میکروسرویس هزینه‌ی شبکه، استقرار، پایش و سازگاری داده دارد.

**شرط شروع؛ حداقل یکی باید با داده ثابت شود:**

- یک ماژول به مقیاس‌پذیری متفاوت نیاز دارد، مثلاً `search` بسیار پرترافیک‌تر از بقیه است.
- چند تیم مستقل روی ماژول‌ها کار می‌کنند و استقرار مشترک مانع کارشان شده است.
- خطای یک ماژول مکرراً کل سرویس را از کار می‌اندازد.

**چالش‌هایی که باید اول حل شوند:**

| وابستگی فعلی | مشکل بعد از جداسازی | جهت راه‌حل |
| --- | --- | --- |
| `EXCLUDE` روی `bookings` | باید در مالکیت یک سرویس بماند | سرویس `bookings` پایگاه داده‌ی خودش را داشته باشد |
| کلید خارجی `reviews` به `bookings` | بین دو پایگاه داده کلید خارجی ممکن نیست | بررسی رزرو با API یا رویداد |
| تریگر `avg_rating` روی `listings` | تریگر به جدول سرویس دیگر دسترسی ندارد | به‌روزرسانی امتیاز با رویداد |
| بررسی دسترسی‌پذیری در `search` | به داده‌ی رزرو نیاز دارد | ایندکس جستجوی جدا که با رویداد به‌روز می‌شود |
| JWT در `identity` | سرویس‌ها باید توکن را مستقل بررسی کنند | امضای نامتقارن و کلید عمومی مشترک |

**کارها:**

- [ ] اندازه‌گیری بار و خطا برای هر ماژول با متریک‌های بخش ۳، چون تصمیم جداسازی باید بر پایه‌ی داده باشد.
- [ ] انتخاب اولین سرویس برای جداسازی. `search` نامزد مناسبی است، چون فقط می‌خواند و ریسک کمی برای قانون رزرو دارد.
- [ ] جدا کردن تدریجی با الگوی Strangler Fig، چون بازنویسی یک‌جا ریسک بالایی دارد.
- [ ] افزودن رویدادها با الگوی Outbox، تا رویدادی بین پایگاه داده و صف گم نشود.
- [ ] افزودن API Gateway، پایش توزیع‌شده و Contract Test، چون خطایابی بین سرویس‌ها بدون این‌ها سخت است.
- [ ] تحلیل دوباره‌ی نیاز به Redis یا صف پیام، چون ارتباط رویدادی شرایط تصمیم قبلی را تغییر می‌دهد.
