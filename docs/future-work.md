# کارهای آینده

این فهرست کارهای پیش روی پروژه است و فقط کارهایی را دارد که هنوز شروع نشده‌اند. کارهای انجام‌شده، یعنی پیاده‌سازی بکند نسخه‌ی اول، تکمیل تست‌های آن، مانیتورینگ (لاگ، متریک و trace)، داده‌ی تست و ماک (اولین کار با Spec Kit، در [specs/001-test-mock-data/](../specs/001-test-mock-data/))، پهن کردن ستون‌های قیمت برای ریال ([specs/002-rial-price-columns/](../specs/002-rial-price-columns/))، بازبینی روش Spec Kit (constitution نسخه‌ی 1.2.0) و بررسی ایندکس‌ها ([specs/003-index-review/](../specs/003-index-review/))، در [backend-design.md](backend-design.md)، [backend/README.md](../backend/README.md) و [observability/README.md](../observability/README.md) ثبت شده‌اند.

## ۱. تأیید آگهی توسط مدیر سیستم

**قاعده (تصمیم مالک پروژه، 2026-11-06):** آگهی تازه پس از تأیید مدیر سیستم به نمایش عمومی درمی‌آید. تا آن موقع در جستجو، صفحه‌ی عمومی آگهی و رزرو دیده نمی‌شود، و میزبان آن را با وضعیت «در انتظار تأیید» می‌بیند. امروز آگهی بلافاصله پس از ساخت عمومی است، و نقش مدیر سیستم وجود ندارد.

**دلیل:** کیفیت و درستی آگهی‌ها پیش از دیده شدن کنترل می‌شود، تا آگهی جعلی یا ناقص به مهمان نرسد.

**تصمیم‌های مالک پروژه (2026-11-06):**

| موضوع | تصمیم |
| --- | --- |
| ویرایش آگهی تأییدشده | دوباره تأیید می‌خواهد، و آگهی تا تأیید دوباره پنهان می‌شود. رزروهای موجود برقرار می‌مانند |
| تغییرهای بدون تأیید | تأیید نمی‌خواهند، و آگهی عمومی می‌ماند (جدول زیر) |
| آگهی ردشده | مدیر سیستم دلیل رد را می‌نویسد، و میزبان آن را می‌بیند، اصلاح می‌کند و دوباره برای بازبینی می‌فرستد |
| ساختن مدیر سیستم | فقط با فرمان CLI، تا کسی نتواند با ثبت‌نام خودش را مدیر کند |
| نمایش عمومی | آگهی فقط وقتی عمومی است که هم تأییدشده و هم فعال باشد. «تأییدشده» تصمیم مدیر است و «فعال» تصمیم میزبان |
| باخبر شدن میزبان | با ایمیل، که سرویسش در بخش ۴ می‌آید. تا آن موقع، وضعیت در صفحه‌ی آگهی‌های میزبان دیده می‌شود |

**کدام تغییر تأیید می‌خواهد (تصمیم مالک پروژه، 2026-11-06):** بازبینی برای درستی توصیف اقامتگاه است. تنظیم‌های عملیاتی و شرط‌های رزرو بدون تأیید عوض می‌شوند، چون هر تأیید دوباره آگهی را پنهان می‌کند و رزرو تازه را از دست می‌دهد.

| بدون تأیید | با تأیید (آگهی تا تأیید پنهان می‌شود) |
| --- | --- |
| قیمت هر شب و هزینه‌ی نظافت | عنوان و توضیح |
| فعال و غیرفعال کردن | نشانی و مکان روی نقشه |
| ترتیب عکس‌ها و انتخاب کاور از میان عکس‌های تأییدشده | عکس تازه، و عنوان یا برچسب اتاقِ عکس |
| ساعت ورود و خروج | امکانات |
| ظرفیت (مهمان، اتاق خواب، تخت، حمام) و اجازه‌ی حیوان خانگی | نوع اقامتگاه |

**آگهی‌های موجود (پاسخ spec):** آگهی‌های موجود، داده‌ی دمو و داده‌ی حجیم با migration تأییدشده حساب می‌شوند، تا امروز چیزی از جستجو نیفتد.

**ساختارهای تازه‌ی طراحی، دلیل وجود و اثرشان (plan در `specs/004-listing-approval/`، 2026-11-07):** هر چیز تازه‌ای که طراحی به سیستم اضافه می‌کند، این‌جا با دلیلش ثبت می‌شود، تا بعدها معلوم باشد چرا هست و حذفش چه چیزی را می‌شکند. هنگام پیاده‌سازی، همین متن به بخش‌های مربوط در `docs/backend-design.md` می‌رود.

| ساختار | چرا وجود دارد | اثرش |
| --- | --- | --- |
| شماره‌ی نسخه‌ی بازبینی آگهی (`listings.review_version`) | admin آگهی را می‌بیند و چند دقیقه بعد تصمیم می‌گیرد. در این فاصله، میزبان ممکن است عنوان یا عکس را عوض کند. بدون شماره‌ی نسخه، تأیید admin نسخه‌ای را عمومی می‌کرد که هرگز ندیده است. قفل ردیف کافی نیست، چون admin بین دیدن و تصمیم قفلی نگه نمی‌دارد. | هر ویرایش توصیفی (ستون «با تأیید» در جدول بالا) شماره را یکی بالا می‌برد، چه آگهی در انتظار باشد، چه تأییدشده، چه ردشده. صفحه‌ی بازبینی شماره را نشان می‌دهد، و تأیید یا رد همان را می‌فرستد. اگر عوض شده باشد، تصمیم با `409 listing_changed` رد می‌شود و admin نسخه‌ی تازه را دوباره می‌بیند. ویرایش‌های بدون تأیید (قیمت، ساعت ورود و…) شماره را عوض نمی‌کنند، تا تأییدی را بی‌دلیل رد نکنند. |
| تصمیم با UPDATE شرطی (`WHERE review_status = 'pending' AND review_version = :v`) | constitution اصل I: تغییر وضعیتی که دو درخواست هم‌زمان می‌توانند انجامش دهند، فقط با UPDATE شرطی تصمیم گرفته می‌شود. | از دو admin هم‌زمان فقط یکی برنده می‌شود، و دومی `409 listing_not_pending` می‌گیرد. |
| نوع حساب در `users.kind` (`member` یا `admin`)، نه جدول جدا | پایگاه داده با همان ایندکس یکتای ایمیل امروز جلوی یک ایمیل برای دو حساب را می‌گیرد، حتی وقتی ثبت‌نام و فرمان ساختن admin هم‌زمان اجرا شوند. با دو جدول، این تضمین فقط در کد می‌ماند. | ورود عادی حساب admin را نمی‌پذیرد، و admin از ورود جدای خودش توکنی با `type: admin` می‌گیرد. این توکن به هیچ endpoint میزبان یا مهمان نمی‌رسد، پس admin اصلاً نمی‌تواند آگهی ثبت کند یا رزرو کند. |
| `users.disabled_at` و بررسی حساب admin در هر درخواست | از کار انداختن admin باید سریع اثر کند. | admin از کار افتاده از درخواست بعدی کنار گذاشته می‌شود، و سابقه‌ی تصمیم‌هایش می‌ماند. admin توکن تمدید (refresh token) ندارد، و پس از ۱۵ دقیقه دوباره وارد می‌شود. |
| سابقه‌ی بازبینی (`listing_review_events`)، فقط افزودنی | باید معلوم باشد چه کسی کدام آگهی را کی تأیید یا رد کرد، و با چه دلیلی (FR-015). | trigger هر ویرایش یا حذف سابقه را رد می‌کند. میزبان فقط آخرین دلیل رد را روی آگهی می‌بیند (`listings.rejection_reason`)، و سابقه برای بررسی بعدی می‌ماند. |
| ثبت دیدن نشانی دقیق (`admin_address_views`) | constitution 1.3.0 اصل V: admin نشانی دقیق را می‌بیند، پس هر دیدن ثبت می‌شود تا این دسترسی پاسخ‌گو بماند. | هر بار باز کردن جزئیات آگهی توسط admin یک ردیف می‌نویسد، در همان تراکنش، پس پاسخی بدون ثبت وجود ندارد. ثبت در log نیست، چون نشانی در log ممنوع است. |
| پیش‌فرض ستون وضعیت: `approved` برای ردیف‌های موجود، `pending` برای ردیف تازه | آگهی‌های موجود باید بدون UPDATE روی ۱۰۰ هزار ردیف تأییدشده شوند. چنان UPDATE‌ای جدول را بازنویسی و bloat می‌کرد. | آگهی تازه حتی اگر کدی وضعیت را فراموش کند، در انتظار ساخته می‌شود. داده‌ی دمو و حجیم باید `approved` را صریح بنویسند. |
| تنظیم `CARAVANSARA_ADMIN_HOST` | constitution 1.3.0: ابزار admin فقط روی زیردامنه‌ی خودش از اینترنت در دسترس است. | وقتی پر است، endpointهای admin روی نشانی دیگر وجود ندارند (`404`). در development خالی است. محافظت اصلی همچنان ورود admin است. |
| عدد صف از worker، نه از API | هر نسخه‌ی API عدد خودش را به Prometheus می‌داد، و عددها تکراری یا کهنه می‌شدند. worker یک برنامه است و هر دقیقه اجرا می‌شود. | Grafana تعداد آگهی‌های در انتظار و قدیمی‌ترین انتظار را با حداکثر یک دقیقه تأخیر نشان می‌دهد. |
| نظرهای آگهی پنهان هم پنهان‌اند | آگهی پنهان برای دیگران باید مثل آگهی ناموجود باشد (FR-002). امروز صفحه‌ی آگهی غیرفعال پیدا نمی‌شود، اما نظرهایش دیده می‌شوند. | فهرست نظرها همان قاعده‌ی صفحه‌ی آگهی را دارد: میزبان و مهمانِ دارای رزرو آن را می‌بینند. |
| `seed-demo` در production اجرا نمی‌شود | داده‌ی دمو یک حساب admin با رمز شناخته‌شده دارد، تا صف بازبینی در دمو دیده شود. | این داده فقط در development و دمو بارگذاری می‌شود. |
| بازگرداندن migration، آگهی‌های تأییدنشده را غیرفعال و حساب‌های admin را حذف می‌کند | با حذف ستون‌ها، آگهی ردشده بی‌درنگ عمومی می‌شد، و حساب admin به کاربر عادی با رمز تبدیل می‌شد که می‌تواند رزرو کند. | هیچ آگهی، رزرو یا نظری حذف نمی‌شود. |

**کارها:**

- [ ] spec با Spec Kit (`/speckit-specify`) و پاسخ پرسش‌های بالا با مالک پروژه (`/speckit-clarify`).
- [ ] نقش مدیر سیستم در `users` و در توکن، و فرمان CLI برای ساختن آن. ثبت‌نام عمومی هرگز این نقش را نمی‌دهد.
- [ ] وضعیت بازبینی آگهی (مثلاً `pending`، `approved` و `rejected`) با migration. آگهی‌های موجود `approved` می‌شوند.
- [ ] فیلتر «فقط تأییدشده» در جستجو، صفحه‌ی عمومی آگهی، پین‌ها و رزرو. ایندکس partial جستجو (`WHERE is_active`) باید با شرط تازه بازبینی و اندازه‌گیری شود، چون شرطش عوض می‌شود.
- [ ] endpointهای مدیر: فهرست آگهی‌های در انتظار، تأیید و رد، اول در `openapi.json`.
- [ ] کد خطای تازه برای رزرو یا مشاهده‌ی آگهی تأییدنشده، و ترجمه‌اش در فرانت‌اند.
- [ ] متریک تعداد آگهی‌های در انتظار و زمان انتظار تا تأیید، تا صف بازبینی در Grafana دیده شود.
- [ ] اصلاح و ارسال دوباره‌ی آگهی ردشده با دیدن دلیل رد، و برگشتن آگهی تأییدشده به صف (و پنهان شدنش) پس از ویرایش فیلدهای ستون «با تأیید».
- [ ] تست: آگهی تازه در جستجو نیست، پس از تأیید هست، و پس از رد نیست؛ آگهی تأییدشده‌ی غیرفعال عمومی نیست؛ ویرایش فیلدهای «با تأیید» آگهی را پنهان می‌کند و دوباره به صف می‌برد، اما فیلدهای «بدون تأیید» نه؛ دلیل رد به میزبان نشان داده می‌شود؛ آگهی ردشده پس از اصلاح دوباره فرستاده می‌شود؛ فقط مدیر سیستم می‌تواند تأیید کند، و ثبت‌نام هیچ راهی به نقش مدیر ندارد؛ و رزرو آگهی تأییدنشده رد می‌شود.

**معیار پایان:** هیچ آگهی‌ای بدون تأیید در جستجو یا رزرو دیده نشود، مدیر سیستم صف بازبینی را ببیند، و قاعده در `docs/backend-design.md` از «هنوز پیاده نشده» به محل اجرای واقعی‌اش برسد.

## ۲. فرانت‌اند: رابط کاربری وب

**هدف:** ساخت سایت وب برای مهمان و میزبان، چون نسخه‌ی اول فقط API دارد و کاربر نهایی نمی‌تواند از آن استفاده کند. کد در پوشه‌ی `frontend/` همین repo قرار می‌گیرد، چون قرارداد API و تست‌ها همین‌جا هستند و تغییر API و صفحه‌ی مربوط به آن در یک pull request بررسی می‌شوند.

**پشته‌ی فنی (تصمیم مالک پروژه):** Next.js، TypeScript، shadcn/ui، Tailwind CSS و Vite (از طریق Vitest)، با زبان فارسی راست‌به‌چپ و فونت Vazirmatn، و زبان انگلیسی.

| بخش | انتخاب | نقش و دلیل |
| --- | --- | --- |
| فریم‌ورک | Next.js با App Router | رندر سمت سرور برای صفحه‌ی جستجو و آگهی، چون این صفحه‌ها باید در موتور جستجو دیده شوند و با اولین بار باز شدن سریع باشند؛ مسیرهای جدا برای هر زبان (`/fa/...` و `/en/...`)؛ و route handler سمت سرور برای نگه‌داری refresh token در cookie |
| زبان برنامه‌نویسی | TypeScript با حالت `strict` | خطای نوع پیش از اجرا گرفته می‌شود، مثل mypy در بکند |
| Vite | فقط از طریق Vitest برای تست کامپوننت | Next.js ابزار build خودش (Turbopack) را دارد و Vite کنار آن build نمی‌کند. Vitest روی Vite ساخته شده و تست را سریع و با همان تنظیمات TypeScript اجرا می‌کند |
| کامپوننت‌ها | shadcn/ui | کد کامپوننت‌ها داخل repo کپی می‌شود و قابل تغییر است، نه یک وابستگی بسته. روی Radix ساخته شده که دسترس‌پذیری (صفحه‌کلید، ARIA) و جهت راست‌به‌چپ را پشتیبانی می‌کند |
| استایل | Tailwind CSS با ویژگی‌های logical (`ms-*`، `me-*`، `ps-*`، `pe-*`) | راست‌به‌چپ و چپ‌به‌راست با یک کد، بدون CSS جدا برای هر جهت. shadcn/ui هم با Tailwind کار می‌کند |
| فارسی | زبان پیش‌فرض، `dir="rtl"` روی `<html>`، فونت Vazirmatn | Vazirmatn متن‌باز است و حروف فارسی و لاتین را دارد. با `next/font` از خود سایت بارگذاری می‌شود، تا به سرویس خارجی وابسته نباشد و صفحه هنگام بارگذاری فونت جابه‌جا نشود |
| انگلیسی | زبان دوم، `dir="ltr"` | همه‌ی متن‌ها از فایل ترجمه می‌آیند، چون API کد خطای ثابت می‌دهد و ترجمه‌ی آن در فرانت است |
| ترجمه | `next-intl` (پیشنهاد) | مسیر زبان، ترجمه‌ی متن و قالب عدد و تاریخ برای هر زبان را با App Router یکجا پوشش می‌دهد |
| کلاینت API | تولید خودکار از `backend/openapi.json` با `openapi-typescript` | هر تغییر قرارداد همان لحظه در فرانت خطای کامپایل می‌دهد، نه خطای بی‌صدا در مرورگر |
| داده از سرور | TanStack Query در کامپوننت‌های سمت کاربر | cache، تلاش دوباره و وضعیت بارگذاری بدون کد تکراری در هر صفحه |
| نقشه | MapLibre GL با کاشی OpenStreetMap | متن‌باز و بدون کلید پولی. فقط پین عمومی آگهی نمایش داده می‌شود، همان‌طور که API می‌دهد |

**کارها:**

- [ ] نوشتن spec این بخش با Spec Kit (`/speckit-specify`): صفحه‌ها، جریان‌ها و معیار پذیرش هر جریان.
- [ ] نحوه‌ی ذخیره‌ی توکن‌ها: access token فقط در حافظه و refresh token در cookie با `HttpOnly`، `Secure` و `SameSite`، که route handler سمت سرور Next.js آن را می‌گذارد و تازه می‌کند. دلیل: توکنی که در `localStorage` باشد با هر حمله‌ی XSS دزدیده می‌شود. اگر API هم باید cookie را بشناسد، آن تغییر اول در `openapi.json` می‌آید.
- [ ] راه‌اندازی `frontend/` با `create-next-app` (App Router، TypeScript، Tailwind، ESLint)، Prettier و `shadcn init`، تا کیفیت کد مثل بکند در CI کنترل شود.
- [ ] مسیر زبان با `next-intl`: `/fa` پیش‌فرض و `/en`، با `lang` و `dir` درست روی `<html>` برای هر زبان، و فایل ترجمه‌ی `fa.json` و `en.json`.
- [ ] کلاینت تولیدشده از `openapi.json` و بررسی در CI که با فایل قرارداد همگام است.
- [ ] طراحی راست‌به‌چپ از ابتدا با فونت Vazirmatn (`next/font`)، و بررسی هر کامپوننت shadcn/ui در هر دو جهت، چون آیکن‌های جهت‌دار، منوها و تقویم در راست‌به‌چپ باید برعکس شوند. اضافه کردن راست‌به‌چپ از اول کم‌هزینه‌تر از اصلاح بعدی است.
- [ ] نمایش عدد، قیمت و تاریخ با قالب هر زبان (`Intl`): ارقام فارسی و جداکننده‌ی فارسی در `/fa`، چون متن فارسی با ارقام لاتین برای کاربر ناآشناست.
- [ ] تصمیم درباره‌ی تقویم شمسی یا میلادی در انتخاب تاریخ، چون کاربر با آن تاریخ رزرو می‌کند. پیشنهاد: شمسی برای فارسی و میلادی برای انگلیسی، با ارسال همیشگی تاریخ میلادی به API.
- [ ] نمایش تاریخ‌ها و مهلت لغو به وقت شهر آگهی، نه وقت مرورگر، چون قانون‌های لغو و پایان اقامت به وقت شهر حساب می‌شوند.
- [ ] صفحه‌های مهمان: جستجو با شهر یا شعاع، نتایج و نقشه، آگهی، رزرو و پرداخت شبیه‌سازی‌شده، سفرها و ثبت نظر.
- [ ] صفحه‌های میزبان: مدیریت آگهی (با وضعیت «در انتظار تأیید»)، آپلود عکس، امکانات و رزروها.
- [ ] وضعیت بازبینی و دلیل رد در صفحه‌های میزبان (بخش ۱).
- [ ] پنل مدیر: برنامه‌ای جدا با UI خودش، روی زیردامنه‌ی جدا و بدون لینک از سایت اصلی (admin نشانی را می‌داند)، با همین پشته (Next.js، RTL و Vazirmatn)، برای صف بازبینی و تأیید یا رد. کار جدا با Spec Kit، پس از بکند بخش ۱ (تصمیم مالک پروژه، 2026-11-06). تا آن موقع، بازبینی از راه API و Swagger شدنی است.
- [ ] حساب کاربری: ثبت‌نام، ورود و پروفایل.
- [ ] آپلود عکس مستقیم به storage با presigned POST، با پیش‌نمایش، نوار پیشرفت و بررسی حجم و نوع فایل پیش از ارسال، چون فایل از API عبور نمی‌کند و خطای آن باید در مرورگر روشن باشد.
- [ ] نمایش پیام فارسی برای کدهای خطای API، چون API فقط کد ماشینی و متن انگلیسی می‌دهد.
- [ ] نمایش شمارش معکوس نگه‌داشت ۱۵ دقیقه‌ای، تا مهمان مهلت پرداخت را از دست ندهد.
- [ ] دسترس‌پذیری در سطح WCAG AA (کار با صفحه‌کلید، کنتراست، برچسب فرم‌ها) و نمای موبایل، چون بیشتر جستجوها با گوشی انجام می‌شود.
- [ ] تست کامپوننت با Vitest (روی Vite) و Testing Library، در هر دو زبان و جهت. تست مرورگر در بخش ۳ است.
- [ ] Dockerfile با خروجی `standalone` در Next.js و سرویس `web` در `docker compose`، و تنظیم `CARAVANSARA_CORS_ORIGINS` در API (یا proxy کردن `/api` از Next.js، تا مرورگر فقط یک مبدأ ببیند)، تا کل سیستم همچنان با یک فرمان بالا بیاید.
- [ ] CI برای فرانت: lint، typecheck، تست و build.
- [ ] ارسال خطاهای مرورگر و Core Web Vitals به مانیتورینگ موجود، تا کندی یا خطای سمت کاربر هم در Grafana دیده شود.

**معیار پایان:** مهمان و میزبان همه‌ی جریان‌ها را بدون Swagger انجام دهند، روی موبایل، به فارسی راست‌به‌چپ و به انگلیسی، و CI فرانت (lint، typecheck، Vitest و build) سبز باشد.

## ۳. تست با Playwright

**هدف:** اطمینان از کارکرد جریان‌های اصلی در مرورگر واقعی، چون تست‌های بکند مشکل‌های UI و اتصال آن به API را نمی‌بینند.

تست‌های Playwright برای API در `e2e/` از قبل وجود دارند (ثبت در راهبرد تست `docs/backend-design.md`). تست‌های مرورگر در همان پروژه و با همان تنظیمات و helperها اضافه می‌شوند.

**کارها:**

- [ ] اجرای تست‌ها روی سیستم کامل با `docker compose`، تا محیط تست به محیط واقعی نزدیک باشد.
- [ ] ساخت داده‌ی مستقل برای هر تست، تا تست‌ها به هم وابسته نشوند.
- [ ] مسیر کامل مهمان: جستجو، رزرو، پرداخت، پایان اقامت و ثبت نظر.
- [ ] مسیر کامل میزبان: ساخت آگهی، آپلود عکس و دیدن رزرو.
- [ ] رزرو هم‌زمان با دو مرورگر، چون مهم‌ترین قانون سیستم باید از دید کاربر هم ثابت شود.
- [ ] حالت‌های خطا: پایان نگه‌داشت، کلیک دوباره و قطع شبکه هنگام رزرو.
- [ ] بررسی راست‌به‌چپ و نمایش موبایل، چون این خطاها در تست‌های بکند دیده نمی‌شوند.
- [ ] افزودن به CI با ذخیره‌ی trace و اسکرین‌شات خطا، تا علت شکست بدون تکرار محلی پیدا شود.

## ۴. سرویس ایمیل

**هدف:** فرستادن ایمیل به کاربر، اول برای نتیجه‌ی بازبینی آگهی (بخش ۱): «آگهی شما تأیید شد» یا «رد شد»، و با دلیل رد. امروز سیستم هیچ ایمیلی نمی‌فرستد.

**کارها:**

- [ ] spec با Spec Kit: کدام رویدادها ایمیل می‌فرستند. اول نتیجه‌ی بازبینی. بعد، اگر مالک پروژه بخواهد، تأیید رزرو و دو موردی که امروز در «خارج از دامنه»ی سند طراحی‌اند: تأیید ایمیل و بازیابی رمز.
- [ ] interface ایمیل در `core`، با پیاده‌سازی SMTP و پیاده‌سازی آزمایشی که فقط ایمیل‌ها را نگه می‌دارد، تا تست‌ها ایمیل واقعی نفرستند.
- [ ] فرستادن از worker، نه وسط درخواست API، با ثبت در جدول و تلاش دوباره. دلیل: کند یا خاموش بودن سرور ایمیل نباید تأیید آگهی را کند کند یا بشکند، و ایمیلی که فرستاده نشده نباید گم شود.
- [ ] متن فارسی و انگلیسی، به زبان کاربر.
- [ ] یک سرویس ایمیل محلی (مثل Mailpit) در `docker compose`، تا ایمیل‌ها در توسعه دیده شوند.
- [ ] متریک ایمیل‌های فرستاده‌شده و شکست‌خورده در Grafana، و هشدار برای صف ایمیلی که پیش نمی‌رود.

**معیار پایان:** میزبان پس از تأیید یا رد آگهی‌اش ایمیل بگیرد. خاموش بودن سرور ایمیل نه تأیید را متوقف کند و نه ایمیل را گم کند.

## ۵. کش کردن داده با Redis

**هدف:** کم کردن زمان پاسخ و بار PostgreSQL در خواندن‌های پرتکرار. نسخه‌ی اول عمداً Redis ندارد (بخش «چرا Redis نداریم» در [backend-design.md](backend-design.md))، و همان‌جا کش جستجوی پرترافیک یکی از شرط‌های افزودن آن آمده است. بررسی ایندکس انجام شده است، و این کار از متریک‌های مانیتورینگ موجود استفاده می‌کند، چون اول باید با عدد معلوم شود کدام endpoint کند و پرتکرار است، و کوئری کند اول با ایندکس درست شود.

**عددهای بررسی ایندکس** ([measurements.md](../specs/003-index-review/measurements.md)، داده‌ی حجیم، میانه‌ی گرم روی لپ‌تاپ و با باتری):
- جستجوی شهری لندن با تاریخ ۶۵ ms است.
- جستجوی شعاعی ۵ km با تاریخ ۵۲ ms است.
- نامزد اصلی کش شمارش امکانات پنل فیلترها (`GET /search/filters`) است: ۱۸۳ تا ۲۳۳ ms. این کوئری ۶۵۷ هزار ردیف (آگهی، امکان) را برای ۴۵ هزار آگهی جمع می‌زند، پس ایندکس آن را سریع‌تر نمی‌کند، و شمارش‌ها برای یک شهر و تاریخ کم تغییر می‌کنند.
- شعاع ۲۰ km (۱۵۷ تا ۱۷۹ ms) و اقامت بیش از یک هفته در منطقه‌ی پرتراکم (۲۷۷ ms) هم بالاتر از هدف ۵۰ ms می‌مانند.

پیش از کش، دو تنظیم PostgreSQL هم با بار واقعی بررسی شود:
- **JIT.** وقتی یک اتصال یک بار JIT کند، کوئری‌های بعدی‌اش حدود ۳ برابر کند می‌شوند. `jit = off` یا `jit_above_cost` بالاتر برای این بار OLTP بررسی شود.
- **`shared_buffers`.** فعلاً ۱۲۸ MB پیش‌فرض است، در حالی که جدول رزرو با ایندکس‌هایش حدود ۱٫۴ GB است.

**قانون ثابت:** منطق رزرو به کش وابسته نمی‌شود. دسترسی‌پذیری هنگام رزرو همیشه از PostgreSQL و `EXCLUDE` بررسی می‌شود، چون داده‌ی کهنه‌ی کش نباید رزرو هم‌پوشان بسازد.

| داده | کش؟ | دلیل |
| --- | --- | --- |
| کشور، شهر و امکانات (پیشنهاد خودکار) | بله، با TTL بلند | تقریباً ثابت‌اند و فقط با seed تغییر می‌کنند |
| جزئیات عمومی آگهی، عکس‌ها و امتیاز | بله، با پاک شدن هنگام تغییر | زیاد خوانده و کم نوشته می‌شوند |
| نتیجه‌ی جستجو | فقط با TTL کوتاه، اگر اندازه‌گیری لازم بداند | با هر رزرو تغییر می‌کند و ترکیب پارامترهایش زیاد است |
| رزرو، دسترسی‌پذیری برای رزرو، توکن و داده‌ی هر کاربر | خیر | درستی مهم‌تر از سرعت است و داده‌ی شخصی نباید در کش مشترک بماند |
| نشانی دقیق آگهی | خیر | طبق سند طراحی خصوصی است |

**کارها:**

- [ ] انتخاب endpointهای هدف با متریک‌های موجود در Grafana (تعداد درخواست و p95 هر route)، چون کش روی endpoint کم‌ترافیک فقط پیچیدگی اضافه می‌کند.
- [ ] interface کش در `core`، با پیاده‌سازی Redis و پیاده‌سازی بی‌اثر برای تست، چون ماژول‌ها نباید مستقیم به Redis وابسته باشند و تست‌های فعلی باید بدون Redis هم اجرا شوند.
- [ ] الگوی cache-aside با کلید نسخه‌دار، مثل `v1:listing:{id}`، تا با تغییر شکل داده فقط پیشوند عوض شود و کش قدیمی خودبه‌خود کنار برود.
- [ ] پاک کردن کلید بعد از commit تراکنش در تغییر آگهی، عکس، امکانات و ثبت نظر (که `avg_rating` را تغییر می‌دهد). دلیل: پاک کردن پیش از commit اجازه می‌دهد درخواست دیگری داده‌ی قدیمی را دوباره در کش بگذارد.
- [ ] TTL با کمی پراکندگی تصادفی و جلوگیری از هجوم هم‌زمان روی کلید داغ، تا با انقضای هم‌زمان کلیدها همه‌ی درخواست‌ها با هم به PostgreSQL نرسند.
- [ ] رفتار هنگام از کار افتادن Redis: timeout کوتاه و خواندن مستقیم از PostgreSQL، چون کش نباید نقطه‌ی شکست کل سیستم شود.
- [ ] افزودن Redis به `docker compose` و CI با `maxmemory` و سیاست `allkeys-lru` و بدون persistence، چون داده‌ی کش از PostgreSQL بازسازی‌پذیر است.
- [ ] متریک نرخ hit و miss، زمان پاسخ Redis و evictionها، و `redis_exporter` در profile `observability`، تا اثر کش با عدد دیده شود.
- [ ] تست: hit دوم، پاک شدن کش پس از تغییر، کار کردن API با Redis خاموش، و اینکه کش کهنه رزرو هم‌پوشان نمی‌سازد.
- [ ] بررسی جداگانه‌ی انتقال rate limit به Redis، فقط اگر API با چند نمونه اجرا شود، چون شمارنده‌ی فعلی PostgreSQL برای یک نمونه کافی است.
- [ ] به‌روزرسانی بخش «چرا Redis نداریم» در `docs/backend-design.md` با تصمیم جدید و دلیلش.

**معیار پایان:** p95 endpointهای هدف روی داشبورد کاهش قابل اندازه‌گیری داشته باشد، نرخ hit دیده شود، و همه‌ی تست‌ها با Redis خاموش هم سبز باشند.

## ۶. میکروسرویسی کردن برنامه

**هدف:** جدا کردن ماژول‌ها به سرویس مستقل، فقط اگر نیاز واقعی وجود داشته باشد. میکروسرویس هزینه‌ی شبکه، استقرار، پایش و سازگاری داده دارد.

**شرط شروع؛ حداقل یکی باید با داده ثابت شود:**

- یک ماژول به مقیاس‌پذیری متفاوت نیاز دارد، مثلاً `search` بسیار پرترافیک‌تر از بقیه است.
- چند تیم مستقل روی ماژول‌ها کار می‌کنند و استقرار مشترک مانع کارشان شده است.
- خطای یک ماژول مکرراً کل سرویس را از کار می‌اندازد.

**چالش‌هایی که باید اول حل شوند:**

| وابستگی فعلی | مشکل بعد از جداسازی | جهت راه‌حل |
| --- | --- | --- |
| `EXCLUDE` روی `bookings` | باید در مالکیت یک سرویس بماند | سرویس `bookings` پایگاه داده‌ی خودش را داشته باشد |
| کلید خارجی `reviews` به `bookings` | بین دو پایگاه داده کلید خارجی ممکن نیست | بررسی رزرو با API یا رویداد |
| تریگر `avg_rating` روی `listings` | تریگر به جدول سرویس دیگر دسترسی ندارد | به‌روزرسانی امتیاز با رویداد |
| بررسی دسترسی‌پذیری در `search` | به داده‌ی رزرو نیاز دارد | ایندکس جستجوی جدا که با رویداد به‌روز می‌شود |
| JWT در `identity` | سرویس‌ها باید توکن را مستقل بررسی کنند | امضای نامتقارن و کلید عمومی مشترک |

**کارها:**

- [ ] اندازه‌گیری بار و خطا برای هر ماژول با متریک‌های موجود در Grafana، چون تصمیم جداسازی باید بر پایه‌ی داده باشد.
- [ ] انتخاب اولین سرویس برای جداسازی. `search` نامزد مناسبی است، چون فقط می‌خواند و ریسک کمی برای قانون رزرو دارد.
- [ ] جدا کردن تدریجی با الگوی Strangler Fig، چون بازنویسی یک‌جا ریسک بالایی دارد.
- [ ] افزودن رویدادها با الگوی Outbox، تا رویدادی بین پایگاه داده و صف گم نشود.
- [ ] افزودن API Gateway، پایش توزیع‌شده و Contract Test، چون خطایابی بین سرویس‌ها بدون این‌ها سخت است.
- [ ] تحلیل نیاز به صف پیام (Redis بخش ۵ یا ابزاری جدا)، چون ارتباط رویدادی شرایط تصمیم قبلی را تغییر می‌دهد.
